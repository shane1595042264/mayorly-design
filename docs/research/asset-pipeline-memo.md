# Asset pipeline: build or buy?

## Verdict

**No.** Nothing on the market does all seven steps, and the failure is not a coverage gap you can close with configuration. It is structural, and it lands squarely on step 3, the feature you named as most important. Across roughly forty products in seven categories (DAM, game pipeline, creative proofing, localization, community submission platforms, pixel-art tooling, and headless CMS/BaaS), **not one vendor claims, in its own documentation, to validate an uploaded image against an admin-defined pixel spec.** Zero support palette colour count. Zero support an alpha-channel requirement. Zero support animation frame count. The ceiling of the entire commercial market is filetype allowlist plus max file size plus a human approval queue. Worse, most of these products have no object representing art that does not exist yet, so there is no slot to hang a spec on, no open queue to claim from, and no "unfilled" column for a dashboard. The one platform that runs real automated technical validation before a human sees a file is Roblox, and its spec is Roblox's, immutable, 3D, and unavailable to you. Every remaining candidate is a substrate you would build on, not a tool you would adopt.

## The closest three

**1. GitHub public repo plus a validating Action.** Fit 7/10, the highest of anything evaluated.

Covers: step 1 as an issue form or a committed spec JSON, step 2 as an open issue queue, step 3 as a genuine structural gate, step 4 as PR review, step 7 as GitHub Projects. This is the only route where rejection is pre-acceptance rather than advisory, because [protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) require a status check to pass before a merge, and the merge *is* the acceptance.

Disqualifier: [GitHub ToS section D.5](https://docs.github.com/en/site-policy/github-terms/github-terms-of-service) grants every user "a nonexclusive, worldwide license to use, display, perform and reproduce (by forking)" the contents of a public repository. Free CI means publishing your entire hand-drawn sprite catalogue, the actual differentiator of the game, under permanent forking rights. Going private costs money, kills anonymous asset fetch, and breaks the fork-PR contribution model outright. Three secondary problems compound it: fork PRs run with a read-only token and no secrets, so a workflow [cannot post the rejection reason back to the artist](https://github.blog/news-insights/product-news/github-actions-improvements-for-fork-and-pull-request-workflows/) without a `pull_request_target` or `workflow_run` workaround; "all first-time contributors require approval to run workflows" by default, so every new artist's first submission sits unvalidated at the exact moment of maximum drop-off; and self-claiming a slot needs Triage permission, which you will not hand strangers, so `/claim` is a bot you write.

Price: **$0/month** public. **$80/month** at 20 artists on Team ($4/user/mo), because outside collaborators on private repos consume seats. Actions is free for public repos. Unauthenticated reads, including `raw.githubusercontent.com`, are capped at [60 requests per hour per IP](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api), so fetch one manifest and one atlas per build, never 400 individual sprites.

**2. Crowdin.** Fit 5/10 on capability, 9/10 on workflow shape.

Covers: steps 2, 4, and 7 better than anything else evaluated, because its entire data model is "many contributors submit competing candidates against one key, and a proofreader approves exactly one while the losers persist as visible alternates." That is your requirement with the nouns changed. It also has real role separation between a translate step and a proofread step, contributor reporting, and a rejection message surfaced in the contributor's own UI at upload time.

Disqualifier: it cannot see pixels. Every QA engine in localization operates on a (source string, target string) pair. Crowdin's [Asset Localization](https://support.crowdin.com/) treats a `.png` as an opaque blob to be swapped wholesale. The one thing worth an hour of testing is the File Pre-Import Processing module, whose docs say it is "triggered on file import, update, and translation upload" and can return `{"error": {"message": "..."}}` visible to the user, which is exactly the right shape. But the docs list only "TXT, XML, JSON, and many more" and never mention binary or image files, and nothing says an asset-classified PNG is routed through it. Separately, Crowdin's webhook catalogue fires on `file.translated` and `file.approved`, not on a contributor uploading, so you cannot even bolt on reliable post-hoc validation. Second disqualifier: tasks are manager-push (a manager assigns files to named translators), so there is no self-serve claim primitive anywhere in the category. Third: no per-submission licence or attribution field exists.

Price: **unverified.** Crowdin's pricing page is JavaScript-rendered and returned no figures to automated fetch; third-party aggregators contradict each other at $50/mo and $179/mo for Team. Do not budget against either number. For reference, [Weblate](https://weblate.org/en/hosting/) publishes real prices and is GPLv3, and [Lokalise](https://lokalise.com/pricing) publishes four headline prices but no plan limits.

**3. Payload CMS, self-hosted.** Fit 6.5/10.

Covers: step 3's mechanism, verifiably. I confirmed against current `main` that `packages/payload/src/collections/operations/create.ts` generates file data *before* running `beforeValidate` hooks, and that [`getBaseFields.ts`](https://raw.githubusercontent.com/payloadcms/payload/main/packages/payload/src/uploads/getBaseFields.ts) puts `width` and `height` on every upload collection (the prose docs omit this, listing only filename, mimeType, and filesize). So the hook fires with dimensions populated and `req.file.data` holding the raw buffer, and throwing there genuinely blocks the write. That is a real pre-persist gate, not post-hoc cleanup. It is also MIT, with no seat concept, so 20 artists cost $0 in licensing.

Disqualifier: only one auth collection can reach the admin panel, so **your 20 artists get no UI at all.** The open-slot queue, the claim button, the upload form, the rejection display, and the whole dashboard are a frontend you build from scratch. Payload's own upload validation is `mimeTypes` and `fileSize` only, declared per collection rather than per record, so it cannot express "this slot is 16x16" at any level. Payload contributes an auth system, an ORM, an admin table, and a well-timed hook. It contributes nothing to steps 4, 5, 6, or 7.

Price: **$0 license, roughly $15 to $40/month infrastructure.** [payloadcms.com/pricing](https://payloadcms.com/pricing) returns HTTP 404 and Cloud signups appear paused since the [June 2025 Figma acquisition](https://www.figma.com/blog/payload-joins-figma/); the $35/$199/$833 figures circulating on aggregator sites are stale scrapes of a dead page. One pixel-art-specific trap: Payload pipes uploads through sharp, which re-encodes. Do not configure `imageSizes` or `resizeOptions` on the art collection, or you will silently alter the exact bytes and palette you just validated.

Honourable mention worth reading before you design anything: **Faithful**, a volunteer Minecraft texture-pack project, is the only place in the world where a slot registry with stable ids, community submission against a specific slot, two-stage review, automatic publication into the shipping pack, and a public manifest API all coexist. It is AGPL-3.0, so it is a blueprint, not a dependency.

## What to steal

From **Crowdin**, take the submission model wholesale. One slot is a key. Many artists submit competing candidates against that key. All candidates persist and stay visible. A proofreader role, distinct from the contributor role, approves exactly one. Losers become alternates rather than being deleted. Also take the two-stage workflow split (submit versus review, with different roles assignable per stage) and, critically, the error contract: a machine-readable rejection message rendered directly in the contributor's own UI at the moment of upload. That last one is the entire UX of your step 3.

From **Lokalise**, take the queued-upload pattern: the upload endpoint returns a background process id you poll for status. That is the correct async shape once a validator has to decode multi-frame sheets.

From **Transifex**, take the "review once or twice" per-project toggle. It is the right granularity for whether a given slot needs a second pair of eyes, and it should be a field on the slot.

From **Roblox's validation documentation**, take the failure-feedback taxonomy: name the failing check, say how to fix it, say why the rule exists, and ship a visualiser. Artists who understand the rule resubmit correctly; artists who see a red X churn.

From **Minecraft Creator Tools**, take the output format for your validator: stable rule ids, a severity column (Error versus Warning), an auto-fixable flag, and failure data that carries both the offending path and the *actual* value found, not just "invalid". `npx mct validate` returning a specific exit code is the CI contract to copy.

From **Aseprite's JSON sprite-sheet schema**, take the manifest shape (`frames[]` with `frame`, `spriteSourceSize`, `sourceSize`, `duration`; `meta` with `frameTags` and `slices`), because Unity's first-party importer, Godot plugins, Phaser, and PixiJS already parse it, and there is a published JSON Schema to validate your output against. You get downstream tooling for free by not inventing a dialect.

From **LPC's style guide**, take the checklist of what a slot spec must actually carry. It is the best worked example available.

From **GitHub**, take the principle that the gate must be structural: acceptance and validation are the same event, not two events joined by good intentions.

Three things nobody has built, so expect no prior art: self-serve slot claiming with an expiry, per-submission licence and attribution capture, and a spec object that exists before any file does.

## If we build it

**PNG validation is not the hard part, and it is barely a part at all.** In the browser, `getImageData` hands you a `Uint8ClampedArray` of RGBA and you are done in about forty lines:

- **Dimensions**: `img.naturalWidth` and `naturalHeight`, no canvas needed.
- **Palette count**: build a `Set` of `(r<<24 | g<<16 | b<<8 | a) >>> 0` over the buffer and read `.size`.
- **Transparency**: scan every fourth byte for a value below 255.
- **Frame count**: `width / frameWidth` must be an integer and equal the spec.

Three precise caveats, each verified rather than assumed. First, canvas normalises everything to RGBA, so `getImageData` **cannot** tell you whether the file has an alpha channel; a fully opaque RGB PNG yields all-255 alpha. If the spec means "the file must carry alpha", read byte 25 of the `ArrayBuffer` (the IHDR colour type) directly, which is five lines, and remember that indexed PNGs carry transparency via a `tRNS` chunk rather than a colour-type flag, so a naive colour-type check rejects legitimate Aseprite exports. Second, the RGB-versus-RGBA counting decision changes the answer: four pixels comprising red at alpha 255, red at alpha 128, red at alpha 0, and green count as 4 distinct RGBA values but 2 distinct RGB values. Publish which one you mean or artists will resubmit blind. Third, APNG frame counts require parsing the `acTL` chunk; canvas will not tell you.

The client-side validator is for instant feedback, in milliseconds, before a byte leaves the artist's machine. It is **not** the gate, for the same reason Cloudinary's Upload Widget is not a gate: a `curl` POST walks straight past it. Re-run the identical ruleset server-side with Pillow or sharp, driven from the same spec JSON, and pin the semantics with a fixture suite (a 17x16, a 1024-colour 32x32, an indexed PNG with `tRNS`, a decompression bomb). Note that Pillow's `getcolors()` returns `None` above its 256-colour default, so `len(img.getcolors())` throws a 500 on exactly the input it is meant to reject; pass `maxcolors` explicitly.

Budget one to two days for all of that, client and server, including fixtures. Then spend your real time on the things that actually are hard:

**Identity and moderation at scale.** This is the genuine cost centre. Sybil accounts, ban evasion, spam, hostile payloads (a malformed PNG aimed at your decoder, a decompression bomb, NSFW content on a public queue), and the one you cannot solve technically: **verifying that art is hand-drawn.** No detector is reliable, and your entire market position depends on the claim. The only working levers are process, not code: require layered source files plus WIP or timelapse evidence for a first submission, build contributor reputation so trusted artists skip the friction, gate first-time contributors behind manual release, and capture a signed declaration you can point to if challenged. Design this before you design the upload form.

**Licence provenance.** No product in any category evaluated models this. You need versioned CLA text, an immutable record of which contributor accepted which version at what timestamp, attribution carried automatically into the shipped build's credits, a documented answer for a contributor who requests removal after ship, and a position on minors and jurisdiction. This is the requirement most likely to become a real problem years later, and it is the one that gets deferred.

**Storage, CDN, and orphan cleanup.** Rejected submissions must not linger in your bucket. Note that hook-level rejection in Payload, Directus, Appwrite, Supabase, and Firebase all leave the file written before your validator runs, so garbage collection is a permanent chore. Decide public-bucket-plus-CDN versus signed URLs early, because it changes your egress bill and your leak surface.

**Atlas generation, specifically determinism.** Packing is easy. *Stable* packing is not: if layout shifts between runs, every rebuild churns every UV in the game. And `free-tex-packer-core@0.3.9`, which I ran locally, **silently drops a file it cannot decode and returns a success callback with `error === null`**, because the read rejection is swallowed in a bare `.catch` that only calls `console.error`. If you use it, wrap it so an expected-versus-actual frame-key diff turns a silent drop into a hard failure. It also has no passthrough for per-sprite custom fields, so licence and attribution must be joined post-process; the filename is your only in-band carrier.

**Versioning approved art without breaking builds.** Content-address the files, keep asset ids immutable and human-stable, version the manifest, pin a manifest revision per game build, and deprecate rather than delete. Redrawing `chest_wooden_closed` after ship must not silently swap the sprite in a build someone is debugging.

The minimum viable version is small: two tables (slots with a spec JSON, submissions with a status and licence fields), GitHub OAuth for identity (free, and account age gives you a cheap anti-sybil signal), the shared validator, an admin review page showing the sprite at 1x and 8x beside the spec with approve/reject-with-note, a manifest endpoint, and a status dashboard that is a `GROUP BY`. Cut from v1: the atlas (do it as a CI step on approval once you pass fifty approved slots), community voting, and a claim-expiry cron (a seven-day claim with a manual release button is fine).

## Recommendation

**Build it, and run the GitHub route first as a deliberate two to three week v0.**

The reason is that the market has told you something unambiguous: the validator does not exist anywhere, but three independent projects (BUIValidator under CC0, Pixel Art Lint, and Lospec's gallery scanner) have each proved it is a small script. What nobody has built is the workflow around it, and that workflow is now well-specified because Crowdin has already solved the same problem for text. You are not doing research. You are doing a known build with a stolen data model.

But do not start by writing UI. The thing you cannot design in the abstract is the ruleset itself, and GitHub gives you a free harness to harden it against real artists: put twenty slots in a public repo as issue forms, put the validator in a required status check, and let artists submit for a month. You will learn what your spec fields actually need to say, what your rejection messages need to read like, and how many submissions fail on something you never anticipated. Then build the app with the ruleset already proven, and you save a rewrite. Publishing twenty community-tier sprites under ToS D.5 is an acceptable price for that learning; publishing the founder's core character art is not, so keep the core art out of the public repo entirely.

**When is GitHub alone the better permanent answer?** When all three of these hold: fewer than about a hundred slots, fewer than about ten artists who are already comfortable with git, and a founder genuinely willing to keep the community art tier public. In that world, building the app is strictly worse. It costs $0, the merge *is* the acceptance so step 3 is structurally airtight, issues give you steps 2 and 7 for free, and six to eight weeks of engineering would buy you a nicer upload form and very little else.

**When does it invert?** At roughly twenty non-technical artists, a couple of hundred slots, or the moment the founder says the catalogue cannot be public. At that point GitHub costs $80/month, the fork-PR model that made it work no longer applies to outside collaborators, anonymous asset fetch dies so the game build needs a token, and pixel artists who do not use git become the bottleneck. Those three conditions are exactly where this project is heading, which is why the honest answer is "build it", with GitHub as the proving ground rather than the destination.

If you decide today that the catalogue can never be public, skip the v0 and start building on Payload or plain Postgres. But still write the validator first, still test it against real submissions before you write a single screen, and still spend more of your planning time on licence provenance and hand-drawn verification than on counting pixels, because counting pixels is the afternoon and those two are the years.
