# Tauri v2 macOS packaging for todoFarm

Research date: 2026-09-04. Web search quota was exhausted on the first call, so everything below came from direct fetches of official docs, the crates.io API, and the GitHub API against `tauri-apps` source at the pinned branches. Every claim carries a URL or an exact file path.

---

## Bottom line

**Ship it with Tauri v2. The stack is sound for macOS. Five things will bite you, and four of them have cheap workarounds.**

1. **Tauri v2 is current and healthy.** Latest stable is `tauri 2.11.5`, published 2026-07-01. No v3 exists yet (only "remove in v3" TODOs in the source). Dual-licensed `Apache-2.0 OR MIT`, which is safe for a closed-source commercial app. No concerns here.

2. **Use `tauri-plugin-sql` with the `sqlite` feature, but do not treat it as a real database layer.** It exposes exactly four JS methods (`load`, `execute`, `select`, `close`). **There are no transactions** (open feature request since Jan 2024) and no SQLCipher. For a "SQLite as source of truth" design where the NPC batch-moves tasks between chests every morning and evening, this matters. **Recommendation: skip the plugin and write your own Tauri commands in Rust over `rusqlite` or `sqlx` directly.** You get transactions, prepared statements, WAL, and you keep the DB access out of the webview's reach. If you do use the plugin, run `PRAGMA journal_mode=WAL` yourself on first load, because sqlx does not set one.

3. **You do not need the macOS Keychain, given the Railway proxy.** There is no official Tauri keychain plugin at all. Since the Anthropic key lives on Railway, the only local secret is a per-user token for your own proxy. Store that in SQLite alongside everything else, or use the `keyring` crate (v4.2.0, MIT/Apache-2.0) from a Rust command if you want real Keychain storage later. Do not reach for `tauri-plugin-stronghold`: it is an encrypted `.hold` file, not the Keychain, and it drags in an argon2 password-hash requirement you have no user password to feed.

4. **Global hotkey is fine and, importantly, needs no Accessibility permission** as long as you use a modifier combo like `Cmd+Shift+Space`. I verified this in the source: `global-hotkey` uses Carbon `RegisterEventHotKey` for normal keys and only creates a `CGEventTap` (the thing that triggers the Accessibility prompt) when you register a **media key**. So quick-capture is a clean, promptless experience. Avoid binding F7/F8/F9.

5. **The one that will actually hurt: macOS notifications cannot be scheduled.** `tauri-plugin-notification` registers only three commands on desktop (`notify`, `request_permission`, `is_permission_granted`). Every scheduling API in its TypeScript surface (`schedule`, `pending`, `cancel`, `active`, `channels`, `onAction`) is mobile-only. **Your morning delivery must fire from a running process.** Practical answer: make todoFarm a menu-bar-resident app (tray icon + `ActivationPolicy::Accessory` + `tauri-plugin-autostart`) and run your own timer in Rust. That is a design decision, not a bug fix, so decide it now.

6. **Signing and notarization: budget $99/yr and do it from day one.** Since macOS Sequoia, users can no longer Control-click to bypass Gatekeeper. An unsigned or unnotarized todoFarm forces every user through System Settings > Privacy & Security > Open Anyway. For a paid consumer app that is a fatal first-run experience. Get a Developer ID Application certificate.

7. **Size and startup: expect roughly 10 to 35 MB per architecture** based on real shipped Tauri v2 apps, not the marketing "600KB". Universal binaries roughly double the Rust side. Phaser plus your pixel art will add to this. I could not find any authoritative startup-time benchmark and will not invent one.

8. **Mobile in 2026 is real but not clean, and Phaser is the risky part.** iOS and Android build and ship, but the updater, global-shortcut, autostart, and single-instance plugins are all `level = "none"` on mobile, and there are 47 open iOS and 87 open Android issues including WKWebView layout corruption after backgrounding. **Plan macOS-only. Treat iOS as a separate project, not a port.**

## 2. SQLite: official plugin vs alternatives, and where the file lives

### The official plugin

- Docs: https://v2.tauri.app/plugin/sql/. Crate `tauri-plugin-sql` version **2.4.1**.
- Backed by `sqlx 0.8`. Features: `sqlite = ["sqlx/sqlite", "sqlx/runtime-tokio"]`. Source: `plugins/sql/Cargo.toml` on the `v2` branch.
- Platform support (authoritative, from `[package.metadata.platforms.support]` in that Cargo.toml): windows/linux/macos/android/ios all `level = "full"`.

**Documentation inconsistency you should know about:** the plugin's own README at https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/sql/README.md renders a table saying `iOS | x` (unsupported), contradicting its Cargo.toml metadata and the docs site. The Cargo.toml metadata is what generates the docs site table, so I read the README as stale. I could not confirm empirically that it works on iOS.

### Where the DB file lives on macOS

The docs say: *"The path is relative to `tauri::api::path::BaseDirectory::AppConfig`."* (https://v2.tauri.app/plugin/sql/)

I traced the actual code. In `plugins/sql/src/wrapper.rs`:

```rust
fn path_mapper(mut app_path: std::path::PathBuf, connection_string: &str) -> String {
    app_path.push(
        connection_string
            .split_once(':')
            .expect("Couldn't parse the connection string for DB!")
            .1,
    );
    format!("sqlite:{}", app_path.to_str()...)
}
```

So `Database.load("sqlite:todofarm.db")` resolves to:

```
~/Library/Application Support/<your bundle identifier>/todofarm.db
```

`BaseDirectory::AppConfig` resolves to `BaseDirectory::Config/{bundle_identifier}`, and on macOS `Config` maps to `~/Library/Application Support` (https://docs.rs/tauri/latest/tauri/path/enum.BaseDirectory.html). Note that on macOS `AppConfig`, `AppData`, and `AppLocalData` all land in the same `~/Library/Application Support/<id>` directory, so the distinction is meaningless here.

That location is the right one. It is inside the user's home, it is backed up by Time Machine, and it survives app updates. Set your `identifier` in `tauri.conf.json` before first release, because changing it later strands every existing user's database.

An **absolute path works** as a side effect of `PathBuf::push` semantics (pushing an absolute path replaces the whole buffer), so `sqlite:/Users/x/foo.db` would resolve literally. This is undocumented and I would not rely on it.

### Real limitations of the plugin

These are the ones that matter for todoFarm:

- **No transactions.** The JS surface is only `Database.load()`, `.execute()`, `.select()`, `.close()` (verified in `plugins/sql/guest-js/index.ts`). Open feature request https://github.com/tauri-apps/plugins-workspace/issues/886, filed 2024-01-10, still open. Your "evening: put all unfinished tasks back into chests" operation is exactly the multi-statement atomic write this cannot give you.
- **No encryption.** SQLCipher request https://github.com/tauri-apps/plugins-workspace/issues/7, open since 2022-10-22. The Cargo.toml literally carries `# TODO: bundled-cipher etc`.
- **No calling it from Rust.** https://github.com/tauri-apps/plugins-workspace/issues/506, open. Your Rust-side morning scheduler cannot reach the same pool.
- **No connection tuning exposed.** The plugin calls `Pool::connect(conn_url)` with defaults. Per https://docs.rs/sqlx/latest/sqlx/sqlite/struct.SqliteConnectOptions.html: *"SQLx does not set a journal mode by default, to avoid unintentionally changing a database into or out of WAL mode."* Busy timeout defaults to 5 seconds, foreign keys are on, `synchronous` is `FULL`. So you get rollback-journal mode unless you issue `PRAGMA journal_mode=WAL;` yourself, and a multi-connection pool against a non-WAL SQLite file is a "database is locked" generator.

### Recommendation

Write thin Tauri commands in Rust over **`rusqlite`** (bundled SQLite, no system dependency) or `sqlx` directly. Reasons specific to todoFarm: you need transactions for the morning/evening batch moves, you need Rust-side DB access for the scheduled morning delivery, and keeping SQL out of the webview means an LLM-authored classification never gets to compose arbitrary SQL. Migrations you can hand-roll or take from the plugin's `Migration` pattern.

Alternatives in the community list (https://github.com/tauri-apps/awesome-tauri) are `tauri-plugin-libsql` (libSQL/Turso, with encryption and Drizzle ORM) if you later want sync, and `tauri-plugin-velesdb` for vector search. Neither is needed for v1.

## 3. macOS Keychain, and whether you need it

**There is no official Tauri Keychain plugin.** The complete official plugin list (https://v2.tauri.app/plugin/) has no keychain or keyring entry. The community list has none either; the only related hit is `tauri-plugin-auth`, which is an iOS `ASWebAuthenticationSession` wrapper, not general secret storage.

**`tauri-plugin-stronghold` is not the Keychain.** Per https://v2.tauri.app/plugin/stronghold/ it maintains its own encrypted `.hold` vault file via IOTA Stronghold, and *"must return a 32 bytes hash derived from"* a password you supply. todoFarm has no user password, so you would be inventing one and storing it somewhere, which defeats the purpose. It also has a documented build workaround (an upstream `scrypt` bug requiring `opt-level = 3` in dev). Skip it.

**If you do want the real Keychain:** the `keyring` crate, v4.2.0, published 2026-08-29, licensed `MIT OR Apache-2.0`, roughly 9.6M recent downloads (https://crates.io/api/v1/crates/keyring). Call it from a Tauri command. Note it is an optional-backend design (`apple-native-keyring-store`), and I could **not** confirm from its docs page what feature flags are required for macOS or whether re-signing invalidates existing Keychain items. Verify that before depending on it.

### Do you actually need it?

**No, not for v1.** Your Railway proxy design already solves the problem it exists for: the Anthropic API key never leaves your server, so no high-value secret ships in the binary. The remaining local secret is at most a per-install token authenticating todoFarm to your proxy. Threat model for that token: an attacker with local filesystem access could read it and burn your Railway quota. That is a rate-limiting and token-rotation problem on the server, not a Keychain problem on the client. Store it in SQLite, scope it per install, and make it revocable server-side.

Add Keychain later only if you introduce user accounts with real credentials.

## 4. Global hotkey for quick capture

**Plugin:** `tauri-plugin-global-shortcut`. Docs: https://v2.tauri.app/plugin/global-shortcut/

Platform support, verbatim from the docs table:

| Platform | Level | Notes |
|----------|-------|-------|
| windows | ✓ | |
| linux | ✓ | |
| macos | ✓ | |
| android | ✗ | |
| ios | ✗ | |

Confirmed against `plugins/global-shortcut/Cargo.toml`: `macos = { level = "full" }`, `android = { level = "none" }`, `ios = { level = "none" }`.

Usage:

```js
import { register } from '@tauri-apps/plugin-global-shortcut';
await register('CommandOrControl+Shift+C', () => { /* open inbox */ });
```

Nothing is allowed by default. You must grant `global-shortcut:allow-register`, `global-shortcut:allow-unregister`, `global-shortcut:allow-is-registered` in your capabilities JSON.

### What macOS permissions this triggers

**This is the part the Tauri docs do not answer, so I read the implementation.**

The docs say nothing about macOS permissions. The underlying crate's docs only mention a threading constraint: *"On macOS, an event loop must be running on the main thread so you also need to create the global hotkey manager on the main thread."* (https://docs.rs/global-hotkey/latest/global_hotkey/)

In `tauri-apps/global-hotkey`, `src/platform_impl/macos/mod.rs`:

- Normal hotkeys go through Carbon `RegisterEventHotKey` plus `InstallEventHandler` on `GetApplicationEventTarget()`. **This requires no TCC permission and produces no prompt.**
- A `CGEventTapCreate` call exists, but it lives **only** inside `fn start_watching_media_keys()` (line 197), which is reached only at line 148 via `} else if is_media_key(hotkey.key) {`. The tap masks `CGEventType::SystemDefined`, which is how macOS delivers play/pause/next.

**Conclusion:** register `Cmd+Shift+Space` or similar and todoFarm's quick capture works with **zero permission dialogs**. Register a media key and macOS will require Accessibility access under Privacy & Security, which is a much worse onboarding step. Do not offer media keys as bindable.

Two caveats I am confident about but which are not in the docs: registration fails silently if another app already owns the combo (there is no system-wide conflict UI on macOS), so surface a "that shortcut is taken" state in your settings UI; and the manager must be created on the main thread per the crate docs above.

## 5. Menu bar / tray presence

**Tray is core, not a plugin.** Guide: https://v2.tauri.app/learn/system-tray/

Enable the feature in `src-tauri/Cargo.toml`:

```toml
tauri = { version = "2", features = ["tray-icon"] }
```

Confirmed present in `crates/tauri/Cargo.toml` `[features]`: `tray-icon = ["dep:tray-icon"]`. Add `image-png` if your tray icon is a PNG.

Build with `TrayIconBuilder` in Rust or `TrayIcon.new()` in JS. Menus attach via `muda`. Click, double-click, enter, move, and leave events are supported on macOS (the documented gap is Linux, where *"the event is not emitted even though the icon is shown"*).

### Making it a true menu-bar app (no Dock icon)

The Tauri tray guide does not cover this. Two mechanisms, both verified in source:

1. **Runtime:** `App::set_activation_policy` / `AppHandle::set_activation_policy`, gated `#[cfg(target_os = "macos")]`. From the doc comment in `crates/tauri/src/app.rs` line 627: *"Sets the activation policy for the application. It is set to `NSApplicationActivationPolicyRegular` by default."* The example given is exactly your case:

```rust
tauri::Builder::default().setup(move |app| {
  #[cfg(target_os = "macos")]
  app.handle().set_activation_policy(tauri::ActivationPolicy::Accessory);
  Ok(())
});
```

2. **Bundle-time:** `bundle.macOS.infoPlist`, described in `crates/tauri-utils/src/config.rs` line 662 as *"Path to a Info.plist file to merge with the default Info.plist. Note that Tauri also looks for a `Info.plist` file in the same directory as the Tauri configuration file."* The merge loop in `crates/tauri-bundler/src/bundle/macos/app.rs` inserts your keys over the generated ones, so dropping `LSUIElement = true` into `src-tauri/Info.plist` works with no config change.

Pair this with `tauri-plugin-autostart` (macOS `level = "full"`) so todoFarm is resident at login and the morning delivery can actually fire, and `tauri-plugin-single-instance` (macOS `full`) so the global hotkey never spawns a second farm.

**Design note for todoFarm specifically:** if you were considering a transparent always-on-top farm window, be aware of https://github.com/tauri-apps/tauri/issues/15471, open since 2026-06-04: *"macOS: transparent:true causes continuous full-window recomposite (~8x GPU power) even when the page is fully static."* On a laptop running a Phaser render loop that is a battery problem. Prefer an opaque window.

## 6. Native notifications for the morning delivery

**Plugin:** `tauri-plugin-notification` v2.4.0. Docs: https://v2.tauri.app/plugin/notification/. macOS is `level = "full"` in its Cargo.toml metadata.

Standard flow, permission-gated like the web API:

```js
import { isPermissionGranted, requestPermission, sendNotification }
  from '@tauri-apps/plugin-notification';
```

### The finding that changes your architecture

**Scheduling does not exist on desktop.** In `plugins/notification/src/lib.rs`, the plugin registers exactly three commands, unconditionally:

```rust
.invoke_handler(tauri::generate_handler![
    commands::notify,
    commands::request_permission,
    commands::is_permission_granted
])
```

Meanwhile `plugins/notification/guest-js/index.ts` exposes `schedule`, `Schedule`, `ScheduleEvery`, `pending()`, `cancel()`, `cancelAll()`, `active()`, `removeActive()`, `createChannel()`, `registerActionTypes()`, `onAction()`, and `onNotificationReceived()`. Those are backed by the Swift and Kotlin sides of the mobile plugin, registered through `mobile::init`. `plugins/notification/src/desktop.rs` contains no `schedule` handling at all (I grepped it; the only notable functions are `notify` and a Windows 7 fallback).

The docs page corroborates this obliquely by calling interactive actions "Mobile-only", but it does not say scheduling is too. **It is.**

**Implication:** todoFarm's morning delivery cannot be handed to the OS as a scheduled local notification on macOS. It must be fired by a running process. Given that, the menu-bar-resident design from section 5 is not a nice-to-have, it is load bearing: tray icon, `ActivationPolicy::Accessory`, autostart at login, and a Rust-side timer (a `tokio` interval or a `tauri::async_runtime` task) that calls `notification().builder().show()` at the user's chosen hour. Handle sleep and wake, because a naive interval will drift or fire late after a closed lid.

### Other macOS notification limits

`plugins/notification/Cargo.toml` shows macOS uses `notify-rust = "4.11"`. Per https://docs.rs/notify-rust/latest/notify_rust/, on macOS these are **silent no-ops**: `appname()`, `icon()`, `hint()`, `urgency()`, `get_capabilities()`, `get_server_information()`. So you cannot put a custom pixel-art icon on the notification; macOS shows your app bundle's icon. `interruption_level()` is supported in place of urgency.

**Gap I could not close:** whether macOS requires a signed or bundled `.app` for notifications to be delivered. The Tauri docs, the plugin README, and the `mac-notification-sys` docs all fail to state it. The Windows note in the Cargo.toml metadata (*"Only works for installed apps"*) suggests the maintainers document this kind of thing when they know it, and they did not for macOS. Since `tauri dev` produces a bundle with your identifier anyway, this is unlikely to affect you, but **test notifications from a signed release build before you ship**, not just from `tauri dev`.

## 7. Code signing and notarization

Docs: https://v2.tauri.app/distribute/sign/macos/

### What you need

- **An Apple Developer Program membership: 99 USD per year.** Verbatim from https://developer.apple.com/programs/enroll/: *"The Apple Developer Program is 99 USD per membership year. Prices may vary by region and are listed in local currency during the enrollment process."* Fee waivers exist for nonprofits, accredited educational institutions, and government entities.
- A **Developer ID Application** certificate for distribution outside the Mac App Store. (**Apple Distribution** is the App Store certificate; you want the other one.) Only the Account Holder can create Developer ID certificates initially.
- The free Apple developer account is not sufficient. Apple's membership comparison (https://developer.apple.com/support/compare-memberships/) lists "Mac software notarization" as a paid-program benefit, and the Tauri docs state that with a free account *"it will still show up as not verified when opening the app."*

### How it works in Tauri

Signing environment variables:
- `APPLE_SIGNING_IDENTITY` (keychain entry name)
- `APPLE_CERTIFICATE` (base64 `.p12`) and `APPLE_CERTIFICATE_PASSWORD` for CI

Notarization, either via App Store Connect API key (`APPLE_API_ISSUER`, `APPLE_API_KEY`, `APPLE_API_KEY_PATH`) or Apple ID (`APPLE_ID`, `APPLE_PASSWORD` as an app-specific password, `APPLE_TEAM_ID`). With those set, notarization runs automatically during `tauri build`. `--skip-stapling` exists if you need to defer the staple.

The docs state: *"Notarization is required when using a Developer ID Application certificate."*

Relevant config keys, from `crates/tauri-utils/src/config.rs`:
- `bundle.macOS.hardenedRuntime`, **default `true`**, which is what notarization requires
- `bundle.macOS.signingIdentity`, `bundle.macOS.entitlements`, `bundle.macOS.providerShortName`
- `bundle.macOS.minimumSystemVersion`, **default `"10.13"`** (`fn macos_minimum_system_version()` returns `Some("10.13")`). Raise this. 10.13 High Sierra is ancient and you will get a better WKWebView floor by targeting something modern.

### What happens to users if you do not sign

This got materially worse and it is the strongest argument for paying the $99.

Apple, verbatim (https://developer.apple.com/news/?id=saqachfa):

> "In macOS Sequoia, users will no longer be able to Control-click to override Gatekeeper when opening software that isn't signed correctly or notarized. They'll need to visit System Settings > Privacy & Security to review security information for software before allowing it to run."

Apple's current user-facing instructions (https://support.apple.com/en-us/102445) confirm the flow: open System Settings, go to Privacy & Security, scroll down, click **Open Anyway**, then confirm at a second warning prompt. Users see either *"Apple cannot check 'Example App' for malware"* or an alert that the developer cannot be verified.

For a commercial consumer app, that is a three-step scary-dialog gauntlet before anyone sees the farm. Ad-hoc signing (the `-` pseudo-identity) does not help; the Tauri docs note it still requires users to whitelist in Privacy & Security.

### Universal binaries

`tauri build --target universal-apple-darwin` is documented in the CLI reference (https://v2.tauri.app/reference/cli/): *"It must be one of the values outputted by `$rustc --print target-list` or `universal-apple-darwin` for an universal macOS application."* Requires both `aarch64-apple-darwin` and `x86_64-apple-darwin` toolchains installed. Distribution targets available: App Bundle, DMG, and App Store (https://v2.tauri.app/distribute/).

### Auto-update

`tauri-plugin-updater` is `level = "full"` on macOS and **`level = "none"` on iOS and Android** (verified in `plugins/updater/Cargo.toml`; note the docs site table at https://v2.tauri.app/plugin/ renders checkmarks for mobile, which contradicts the source, and the source is authoritative). It produces `myapp.app.tar.gz` plus a `.sig`, using minisign keypairs from `tauri signer generate`. Signature verification *"cannot be disabled"*, and losing the private key means you can never ship another update, so back it up outside the repo. https://v2.tauri.app/plugin/updater/

If you go Mac App Store instead, note from https://v2.tauri.app/distribute/app-store/: *"Your app must include the App Sandbox capability to be distributed in the App Store."* Sandboxing plus a global hotkey plus autostart is a meaningfully harder configuration. Direct distribution with the updater is the lower-friction path for v1.

## 8. App size and startup time, honestly

### Size

Tauri's homepage claims *"By using the OS's native web renderer, the size of a Tauri app can be little as 600KB"* (https://tauri.app/). That is a hello-world floor, not a product.

Real shipped Tauri v2 macOS DMGs, pulled from the GitHub releases API on 2026-09-04:

| App | Version / date | macOS DMG |
|---|---|---|
| Pake (thin web wrappers, minimal JS) | V3.15.6, 2026-08-08 | 8.2 to 13.4 MB depending on target site |
| EcoPaste (real menu-bar clipboard app) | 1.1.1-nightly, 2026-08-13 | 9.9 MB (aarch64), 10.3 MB (x64) |
| pot-desktop (translation app) | 3.0.7 | 34 MB (aarch64), 35 MB (x64) |
| Clash Verge Rev (bundles a Go sidecar) | 2.5.2, 2026-07-19 | 58.1 MB (aarch64), 62.7 MB (x64) |

**Realistic estimate for todoFarm:** 15 to 30 MB per architecture. EcoPaste at ~10 MB is your closest structural analogue (tray-resident, SQLite, real UI), and you add Phaser (roughly 1.3 MB minified) plus a tilemap, a spritesheet, a character, chest sprites, and probably music. A universal binary roughly doubles the Rust portion but shares nothing on the asset side, so plan on 25 to 50 MB universal.

Size levers from https://v2.tauri.app/concept/size/: `lto = true`, `opt-level = "s"`, `strip = true`, `codegen-units = 1`, and *"remove commands that're never allowed in your capability files (ACL), so you don't have to pay for what you don't use"*. In practice your pixel art will dominate the Rust binary anyway, so spend the effort on texture atlases and PNG optimization rather than Cargo flags.

### Startup time

**I could not find an authoritative startup-time benchmark and I am not going to make one up.** The Tauri homepage makes no startup or memory claim. The size concept page makes none. The 2.0 stable announcement makes none. The v1-era benchmark page is not part of the v2 docs.

What I can say with grounding: on macOS the webview is WKWebView, the system engine, so there is no Chromium process tree to spin up the way Electron has, and no engine bytes to page in from your bundle. The cost that remains is process launch plus WKWebView initialization plus your JS and asset load. For todoFarm the dominant term will almost certainly be Phaser booting and decoding your texture atlas, not Tauri.

**If startup matters to you, measure it yourself**, and use the standard mitigation: configure the main window `visible: false` and show it from Rust once the Phaser scene signals ready, so users see nothing rather than a white flash. Since todoFarm should be tray-resident and autostarted anyway, the perceived cold start after login is a one-time cost.

## 9. Tauri v2 mobile in 2026: state, limitations, and whether Phaser + HTML ports cleanly

### Is it production ready?

**It works, and people ship with it, but the developer experience is still rough and it is not a free port.**

The 2.0 stable announcement remains the clearest official statement, and it is candid (https://v2.tauri.app/blog/tauri-20/):

> "We are not completely happy about the developer experience at the moment but are actively improving to bring it up to par with the desktop experience."

> "On mobile not all of the official plugins are supported. Some are by design not a good fit for mobile and some are just not implemented to support mobile yet."

I found **no newer official statement upgrading that assessment.** The Tauri blog's only 2025 and 2026 posts are board elections (2025-06-30, 2026-06-30) and "Experimental Tauri Verso Integration" (2025-03-17). There is no published mobile roadmap or "mobile is now stable" announcement. That silence is itself a data point.

### Toolchain and floors

- iOS builds **only on macOS** and require Xcode; targets `aarch64-apple-ios`, `x86_64-apple-ios`, `aarch64-apple-ios-sim` (https://v2.tauri.app/start/prerequisites/).
- iOS deployment target defaults to **15.0** (`fn ios_minimum_system_version()` in `crates/tauri-utils/src/config.rs`).
- Android `minSdkVersion` defaults to **24** (`fn default_min_sdk_version()`, same file). Android Studio, SDK Platform-Tools, NDK side-by-side, and four Rust targets required.
- Ship command: `tauri ios build --export-method app-store-connect`, then upload the IPA via `altool` with an App Store Connect API key (https://v2.tauri.app/distribute/app-store/).

### Would Phaser + HTML port cleanly?

**Partially, and the honest answer is "the code ports, the product does not."**

Arguments for:
- iOS uses WKWebView, the same engine as macOS. Your Phaser canvas and HTML overlay will render with the same engine family. That is the single best thing going for this port.
- Phaser is MIT licensed (https://github.com/phaserjs/phaser), actively maintained, and has first-class touch input. No licensing obstacle to a commercial closed-source app.
- The SQL and notification plugins both claim full mobile support, so your data layer and your morning delivery survive.

Arguments against, in order of severity:
1. **Input model.** "Walk a pixel character around a farm and press a key at a chest" is a keyboard interaction. On a phone there is no keyboard. You need a virtual d-pad or tap-to-move, plus a proximity-based action button. That is a real redesign of your core loop, not a media query.
2. **Screen size.** A Stardew-style farm world with readable chests assumes a wide viewport. A 390pt-wide portrait phone shows a fraction of it. Either you shrink the farm, add camera follow with aggressive zoom, or the app becomes landscape-only.
3. **Quick capture disappears.** The global hotkey is `level = "none"` on mobile. On iOS the equivalent is a Share Sheet extension or a Shortcuts action, which is native Swift work outside Tauri's abstraction.
4. **Android WebView fragmentation.** Unlike iOS's uniform WKWebView, Android's System WebView version varies by device and update state. Phaser's WebGL renderer will hit a wider variance of GPU drivers and WebGL implementations. I found no Tauri-specific data on this, but it is the well-known shape of the problem.
5. **The WKWebView-shrinks-after-backgrounding bug (#15367)** is precisely the failure mode a canvas game triggers constantly, because users background and foreground a todo app all day.
6. **Signing pain.** The July-August 2026 cluster of iOS signing issues against Xcode 26 suggests the mobile CI path is not yet boring.

**Recommendation:** build macOS as if mobile does not exist. Keep the discipline that would help a future port anyway (all game logic in TypeScript, all persistence behind a narrow Rust command interface, no Node or desktop-only browser APIs in the frontend), but do not pay any design tax for mobile now. When you get there, budget it as a new project with a redesigned input model, not a `tauri ios build`.

# Adversarial fact-check

## Corrections

**1. `pot-desktop 3.0.7` is a Tauri v1 app, not v2 — it does not belong in a table titled "Real shipped Tauri v2 macOS DMGs."**
- Claim: the size table lists pot-desktop 3.0.7 at 34/35 MB as a Tauri v2 datapoint, "pulled from the GitHub releases API on 2026-09-04."
- Truth: its `src-tauri/Cargo.toml` at tag 3.0.7 pins `tauri = { version = "1.8", features = [...] }` and pulls every plugin from `branch = "v1"`. The release was published **2025-05-10**, not recently. This is the datapoint anchoring the top of the report's "roughly 10 to 35 MB" range, so the range is built partly on a v1 binary with a v1 feature-allowlist build.
- URL: https://raw.githubusercontent.com/pot-app/pot-desktop/3.0.7/src-tauri/Cargo.toml
- (EcoPaste `tauri = "2"` and Pake `tauri = "2.10.2"` do check out. Clash Verge Rev uses `tauri = { workspace = true }`, so its version is not verifiable from that file — the report did not verify it either.)

**2. `notify-rust`'s `hint()` is not a "silent no-op" on macOS — it does not compile.**
- Claim: "on macOS these are **silent no-ops**: `appname()`, `icon()`, `hint()`, `urgency()`, `get_capabilities()`, `get_server_information()`."
- Truth: the platform-differences table marks `appname` and `icon` as silent no-ops on the macOS NSUserNotification backend, but marks `hint` with a dash, which the table's own legend means *will not compile*. Separately, the report cites `docs.rs/notify-rust/latest`, which is currently **4.18.0**, while the plugin pins `notify-rust = "4.11"` — the report attributes 4.18 documentation to a 4.11 pin without flagging the drift.
- URL: https://docs.rs/notify-rust/latest/notify_rust/
- The downstream conclusion (you cannot put a custom pixel-art icon on a macOS notification) survives — `desktop.rs` does pass `icon` to notify-rust, and notify-rust drops it on macOS.

**3. The notification-scheduling failure mode is described wrongly, and the wrong way is the more dangerous one.**
- Claim: "Every scheduling API in its TypeScript surface (`schedule`, `pending`, `cancel`, ...) is mobile-only," implying a scheduled notification on macOS hits a missing command.
- Truth, verified in source: there is **no exported `schedule` function**. `schedule` is a field on the `Options` object. `sendNotification(options)` does not invoke a `schedule` command at all — it calls `new window.Notification(options.title, options)`, which routes to `plugin:notification|notify`, and `notify` **is** registered on desktop. `desktop.rs`'s `show()` then reads only `title`, `body`, `icon`, `sound` off `self.data` and drops everything else. So on macOS a scheduled notification does not error — it **fires immediately, silently**. That is a materially worse and harder-to-catch bug than "the API is missing," and it is the one an implementer will actually hit.
- URLs: https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/notification/guest-js/index.ts (line ~371), https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/notification/src/desktop.rs (lines 26–53), https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/notification/src/commands.rs
- The architectural recommendation (run your own Rust timer) is correct and unaffected.

**4. The report's own "unverifiable" item #3 is answerable.**
- Claim: "I could **not** confirm from its docs page what feature flags are required for macOS."
- Truth: keyring 4.2.0's `default` feature is `["v1"]`, and `v1 = ["apple-native-keyring-store/keychain", "windows-native-keyring-store", "zbus-secret-service-keyring-store"]`. Default features already enable the macOS Keychain backend; no extra flag is needed.
- URL: https://crates.io/api/v1/crates/keyring/4.2.0 (`features` object)

**5. Minor numeric drift in the size table (does not change any conclusion).** Pake V3.15.6's DMG range is **8.0–13.4 MB**, not 8.2–13.4. The "9.9 / 10.3 MB" EcoPaste figures belong to the **2026-07-24** nightly; the 2026-08-13 release the report names is **10.0 / 10.4 MB**. Clash Verge 2.5.2 x64 is **62.8 MB**, not 62.7.

**6. Minor: the global-shortcut permission list is incomplete.** The plugin autogenerates five command permissions — `register`, `register_all`, `unregister`, `unregister_all`, `is_registered` — not the three the report lists. If you use the batch APIs you will need `allow-register-all` / `allow-unregister-all` too. (The "nothing allowed by default" claim is exactly right: `default.toml` ships `permissions = []` with the comment "No features are enabled by default, as we believe the shortcuts can be inherently dangerous.")
- URL: https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/global-shortcut/permissions/default.toml

## Omissions

**1. The report does no license diligence at all on the two community plugins it recommends. This is the single worst gap given the project's stated constraint.**

- **`tauri-plugin-velesdb` is not permissively licensed.** Its `LICENSE` reads "**VelesDB Core License 1.0 / Based on the Elastic License 2.0 (ELv2)**", Copyright Wiscale France, "All rights reserved." GitHub classifies it `NOASSERTION`. It carries: no-hosted-service and no-competitive-offering clauses; a ban on circumventing paid-feature licensing mechanisms; and — directly relevant to a distributed commercial `.app` — a **mandatory visible attribution requirement**: "If You deploy or make publicly available an Application or Service that uses the Software as a component — including SaaS products, web applications, mobile applications, or browser-based applications — You must include a visible attribution notice containing a hyperlink to https://velesdb.com," placed somewhere "accessible to end users without requiring a separate action" (About/Credits/Settings qualifies), and "Failure to comply with this attribution requirement constitutes a violation of this license." Redistribution also requires shipping a complete copy of the license. todoFarm probably would not trip the ELv2 clauses (it is not a hosted DB), but this is a source-available commercial license with a shipped-UI obligation, not the MIT-shaped thing the report's framing implies. https://github.com/cyberlife-coder/VelesDB/blob/main/LICENSE
- **`tauri-plugin-libsql` has no LICENSE file in its repository.** GitHub reports no license (`"license": null`). Only `license = "MIT"` in `Cargo.toml` asserts anything. Absent a license file, the default is all-rights-reserved, and the Cargo.toml string alone is thin cover for a distributed commercial binary. It is also v0.1.0 with 17 stars and a single maintainer. https://api.github.com/repos/HuakunShen/tauri-plugin-libsql

**2. The report never states the license of its own headline recommendation.** It tells you to drop the official plugin for `rusqlite` or `sqlx`, and then does not check either. For the record: rusqlite 0.40.2 is **MIT**, bundled SQLite is public domain, sqlx is Apache-2.0 OR MIT — all safe. But this is the one license check the report's own advice made necessary and it is the one it skipped.

**3. `tauri-plugin-autostart` has a macOS launcher choice that partially undercuts the "zero permission dialogs" story the report builds.** `MacosLauncher` has two variants, `LaunchAgent` (`#[default]`) and `AppleScript`. The AppleScript path drives System Events to add a Login Item, which is an Apple Events / Automation TCC surface. The report makes autostart load-bearing for the entire morning-delivery design and never mentions the enum exists. Keep the default. https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/autostart/src/lib.rs (lines 24–29, 191–197)

**4. `bundle.createUpdaterArtifacts` is not mentioned.** The report covers the updater in detail — minisign, `--skip-stapling`, key backup — and omits the one config flag without which `tauri build` produces no updater artifacts at all: "Setting this to `true` tells Tauri's app bundler to create updater artifacts." https://v2.tauri.app/plugin/updater/

**5. `removeUnusedCommands` is quoted as if it were free.** The size page's ACL line requires `"removeUnusedCommands": true` in the config and Tauri 2.4 or later. https://v2.tauri.app/concept/size/

**6. `minimumSystemVersion: "10.13"` is meaningless for the arm64 slice of a universal build.** Apple Silicon's floor is macOS 11.0 regardless of what you set. The report says "raise this" without noting the two slices have different real floors, which matters because it also recommends `--target universal-apple-darwin`.

**7. Window transparency requires a private-API opt-in, which interacts with the App Store path the report also discusses.** `app.macOSPrivateApi` in `tauri.conf.json` is documented as "MacOS private API configuration. Enables the transparent background API and sets the `fullScreenEnabled` preference to `true`," and it flips on a `macos-private-api` Cargo feature. The report warns about transparency purely on GPU-power grounds (#15471) and never mentions that transparency is gated behind private API usage — a second, independent reason to avoid it, and a submission risk if the Mac App Store ever becomes the path. https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-utils/src/config.rs (line 3194)

**8. Nothing on CSP or webview network egress to the Railway proxy.** `SecurityConfig.csp` is `Option<Csp>` and defaults to `None`, so an unconfigured app has no CSP and the proxy call works — but the moment anyone hardens the config, `connect-src` must name the Railway origin. For a packaging report on an app whose only network dependency is that proxy, this deserves a line.

**9. The tray Cargo feature is auto-derived from config.** The report tells you to hand-add `features = ["tray-icon"]` to `Cargo.toml`. `AppConfig::features()` pushes `"tray-icon"` automatically when `app.trayIcon` is set in `tauri.conf.json` (config.rs:3219-3221). Harmless either way, but the manual step is not required if you configure the tray declaratively.

**10. Phaser's version is never named.** "Phaser" is a decided stack element; current is 4.2.1 and the 3.x line is still published (3.90.0 min = 1.14 MB vs 4.2.1 min = 1.31 MB). A packaging report that costs the bundle from Phaser should say which Phaser it costed. Both are MIT, so there is no licensing consequence — only a size and renderer-choice one.

**11. Migrations *are* transactional, which slightly softens the "no transactions" framing.** The SQL plugin docs state: "All migrations are executed within a transaction, ensuring atomicity." The JS surface still has no user-facing transaction API — the report's conclusion is right — but the flat "no transactions" phrasing overstates it by one case.

---

## Net assessment

**Trustworthy, and unusually so — I went looking for fabrication and did not find any.** Roughly 95% of the checkable claims verified exactly, including the kinds of detail that are normally where invented reports fall apart: eleven GitHub issue numbers all real, open, and correctly titled; issue counts matching to the digit (47 iOS / 87 Android / 197 macOS); source line numbers landing on the right code; doc comments and Apple quotes verbatim; crates.io timestamps to the second. The report's declared-uncertainty section is honest rather than decorative, and its central architectural finding — that macOS has no OS-level notification scheduling, so the morning delivery forces a tray-resident autostarted design — is correct and correctly load-bearing.

**Two real defects.** One bad datapoint in the size table (pot-desktop is Tauri v1), and the notification-scheduling failure mode described as "API missing" when it is actually "silently ignored, fires immediately" — the latter being the more expensive mistake to inherit.

**One structural blind spot, and it is in exactly the category the project flags as highest-stakes.** The report performs careful license verification on Tauri, wry, and Phaser, then recommends two community plugins with zero license checking — one of which (VelesDB) is Elastic-License-derived with a mandatory in-app attribution link, and the other of which (tauri-plugin-libsql) ships no license file at all. Neither is needed for v1 by the report's own account, so nothing is broken today; but the pattern matters, because it means the report's license diligence tracks *how well-known the project is* rather than *whether it would ship in the binary*. Apply the same scrutiny to every dependency that reaches the `.app`, not just the famous ones.
