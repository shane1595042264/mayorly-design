## The two questions that actually matter

### (a) Binary alpha, no anti-aliasing

Anti-aliasing means softening an edge with partly transparent or blended pixels. Your standard forbids it, so every pixel must be either fully opaque or fully invisible, nothing in between.

Every dedicated pixel editor here draws hard edged by default. The risk is never the pencil, it is these five things, and they apply to Aseprite, Pixelorama, LibreSprite and PixiEditor alike:

- layer opacity or cel opacity set below 100
- an eraser or pencil with opacity below 100
- blend modes other than Normal
- rotating or scaling a selection with interpolation
- gradient and blur tools

Working in **Indexed** colour mode structurally prevents most of these, because an indexed image stores one palette slot per pixel plus a single transparent index, so a half transparent pixel cannot be represented. That is why I recommend Indexed as your working mode even though you export RGB.

The genuine failures are Photoshop, Procreate and Krita. They are painting applications where anti-aliasing is the default on nearly every tool, and Pixelmash, whose entire premise is downsampling high resolution art, which generates blended edge pixels by design.

### (b) ICC profile on export

An ICC profile is a colour description block embedded in the file. Your validator rejects it. There is a distinction that matters enormously here and that most comparisons miss:

- **`iCCP`** is a real embedded ICC profile, typically several kilobytes.
- **`sRGB`** is a single byte marker saying "these colours are sRGB." It is not an ICC profile.

If your validator rejects only `iCCP`, more tools pass. If it rejects any colour chunk, only Aseprite with Color Management off is clean. **Confirm which rule your validator implements**, because it changes the answer for Pixelorama, PixiEditor and Piskel. My script checks both ways.

**Aseprite, verified in source.** In `src/app/file/png_format.cpp`, the profile writer runs only behind a gate:

```c
if (fop->preserveColorProfile() && spec.colorSpace()) {
    saveColorSpace(png, info, spec.colorSpace().get());
}
```

`preserveColorProfile()` returns `m_config.preserveColorProfile`, which `file_op_config.cpp` fills as `preserveColorProfile = pref.color.manage();`. And `data/widgets/options.xml` binds that preference to exactly one checkbox:

```xml
<check text="@.color_management" id="color_management" pref="color.manage" />
```

whose label in `data/strings/en.ini` is `color_management = Color Management`. Untick it and `saveColorSpace` is never reached, so no `iCCP`, no `sRGB`, no `gAMA`, no `cHRM`.

Even with it left on, only one branch writes an actual ICC profile. Setting the sprite's own profile to None gives you this branch:

```c
case gfx::ColorSpace::None:
  // Do just nothing (png file without profile, like old Aseprite versions)
  break;
```

Only `case gfx::ColorSpace::ICC:` calls `png_set_iCCP`. The default sRGB setting calls `png_set_sRGB`, which writes the harmless marker, not a profile.

**Pixelorama, verified in source.** It is built on Godot, which saves PNGs through `drivers/png/png_driver_common.cpp` using libpng's simplified API, `png_image_write_to_memory`. In libpng's `pngwrite.c` that path always executes:

```c
else if ((image->flags & PNG_IMAGE_FLAG_COLORSPACE_NOT_sRGB) == 0)
   png_set_sRGB(png_ptr, info_ptr, PNG_sRGB_INTENT_PERCEPTUAL);
```

Godot never sets that flag. So **Pixelorama always writes an `sRGB` chunk and never writes `iCCP`**, and there is no setting to change it. Good news on the same path: Godot maps `FORMAT_RGBA8` straight to `PNG_FORMAT_RGBA`, so Pixelorama exports stay 32 bit regardless of content.

**Procreate fails this outright.** Its handbook requires a colour profile on every canvas, chosen at creation, and states "Once you've set your Color Profile to be RGB or CMYK for a piece of art, there's no way to change it." There is no "none" option. Same for Photoshop and Krita, which embed by default.

### The PNG-32 trap in Aseprite, which nothing documents

PNG-32 means four channels at 8 bits each, red, green, blue and alpha. Aseprite will silently give you PNG-24 instead, and here is exactly when. From `png_format.cpp`:

```c
case ColorMode::RGB:
  color_type = (img->needAlpha() || fix_one_alpha_pixel ? PNG_COLOR_TYPE_RGB_ALPHA :
                                                          PNG_COLOR_TYPE_RGB);
  break;
...
case ColorMode::INDEXED:
  ...
  color_type = PNG_COLOR_TYPE_PALETTE;
```

And in `src/doc/sprite.cpp`:

```c
bool Sprite::isOpaque() const {
  Layer* bg = backgroundLayer();
  return (bg && bg->isVisible());
}

bool Sprite::needAlpha() const {
  switch (pixelFormat()) {
    case IMAGE_RGB:
    case IMAGE_GRAYSCALE: return !isOpaque();
    default:              return false;
  }
}
```

Read those together and the rule is mechanical, and it surprises people:

- A **visible Background layer** makes the sprite "opaque," which drops the alpha channel and gives you **PNG-24**. This happens even if you never touch transparency, so your fully opaque 16x16 terrain tiles are exactly the assets most likely to fail.
- **No Background layer** gives you **PNG-32** every time, even on a fully opaque tile.
- **Indexed mode** gives you a palette PNG, which is PNG-8, not PNG-32.

Bit depth is hardcoded to 8 in the `png_set_IHDR` call, so 8 bits per channel is guaranteed. The practical workflow: draw in Indexed to hold your 8 to 24 colours, then **Sprite > Color Mode > RGB** before exporting, and never use a Background layer.

## The Aseprite licence question, precisely

Aseprite is source-available, not open source. It was GPLv2 until August 2016. Three things are true, and people routinely conflate them.

**What the EULA says.** Clause 2(g), quoted exactly:

> "You may only compile and modify the source code of the SOFTWARE PRODUCT for your own personal purpose or to propose a contribution to the SOFTWARE PRODUCT."

And clause 2(b):

> "You may not distribute copies of the SOFTWARE PRODUCT to third parties."

**What compiling it yourself does permit.** The wording "personal purpose" in 2(g) reads as though it might exclude commercial work. The vendor's own FAQ resolves that directly, and this is the sentence that matters to you:

> "You can still compile the source code, and use the program to create your assets for commercial games."

Reinforced elsewhere on the same page:

> "you can still download its source code, compile it, and use it for your personal purposes. You can make commercial art/assets with it too."

> "Yes, you can use your own creations (sprites, animations, graphics, assets, etc.) in any product (personal or commercial) you want."

**What it does not permit.** Redistribution of the binary you built, to anyone. The FAQ is blunt: "No. From August 2016 you cannot redistribute compiled versions of Aseprite." So you may not hand your build to a collaborator, commit it to a shared repository, or bake it into a CI image others pull.

**My read, stated as opinion rather than fact:** the FAQ is the vendor's public interpretation, not contract text, and it is more permissive than a literal reading of 2(g). It is strong evidence of intent and nobody has been pursued for this. But at $19.99 against the hours you would spend on the build, and given you are the sole artist on a commercial project, the paid licence removes an ambiguity you gain nothing from carrying.

**If you build it anyway**, the official instructions are real work but tractable: Xcode 16.3 with the macOS 15.4 SDK, CMake, Ninja, plus a compiled Skia from the `aseprite-m124` branch, for which prebuilt packages exist. The Apple Silicon invocation is documented, using `-DCMAKE_OSX_ARCHITECTURES=arm64` and `-DPNG_ARM_NEON:STRING=on`. Budget an evening, mostly waiting on Skia.

**LibreSprite** is the clean escape hatch: a GPLv2 fork of Aseprite 1.1 from before the licence change, genuinely free, with an arm64 macOS build. The cost is that it forked before 1.3, so **it has no tilemap support**, which is precisely the feature your seamless terrain tiles want. Its last release was March 2025 and the project has asked publicly for macOS maintainers.

## The validator, installed and tested

I wrote `/Users/juntaoli/todoFarm/tools/pngcheck_art.py`. Pure Python standard library, no dependencies, parses PNG chunks and unfilters scanlines directly. It checks all your constraints at once: colour type 6 at depth 8, alpha values restricted to 0 and 255, unique opaque colour count, `iCCP` presence, other colour chunks, exact canvas size, and interlacing.

I tested it against six fixtures I built with known defects, and it caught every one: a soft anti-aliased edge, an RGB-24 file, a wrong canvas size, an injected `iCCP` profile, an injected `sRGB` plus `gAMA` pair, and a clean control that passed.

Then I ran it on your real placeholders:

```
FAIL assets/placeholders/tile.terrain.grass_a@1x.png
       x colour count 2 outside 8-24
FAIL assets/placeholders/tile.anim.water@1x.png
       x size is 16x64, expected 16x16
       x colour count 2 outside 8-24
```

Two useful signals there. The colour-count failures are correct and expected, they are two-colour placeholders. The 16x64 flag is just your four-frame water strip meeting a 16x16 rule I passed on the command line, so give strips their own size argument. **More importantly, nothing failed on PNG-32, binary alpha, or ICC**, which means whatever currently generates your placeholders is already emitting compliant files. That is your baseline to preserve.

Usage:

```
python3 tools/pngcheck_art.py 'assets/**/tile.*@1x.png' --size 16x16 --colors 8-24
python3 tools/pngcheck_art.py 'assets/**/*.png' --size 64x64 --colors 8-24 --strict-nocolor
```

Add `--strict-nocolor` to also fail on `sRGB` and `gAMA`. Run it once with and once without against a test export from any editor you are evaluating, and you will know in one second whether that editor can meet your standard. Exit code is 1 on any failure, so it drops straight into a pre-commit hook or CI.

# How a beginner actually gets good at pixel art, fast

## Bottom line: do this today

Total spend, about **$8**. Everything else on this list is free.

1. **Buy Pixel Logic ($2.99, "or more", verified today)** at https://knowledgebook.itch.io/pixel-logic-a-guide-to-pixel-art. 242 pages, almost entirely diagrams. It is the single most-cited beginner-to-competent reference among working pixel artists, and Lospec features it at the top of its 586-tutorial index. Skim the whole thing in one sitting without trying to absorb it. You are building an index of "things that have names" so you can look them up when your art looks wrong.
2. **Read Saint11's 8-article beginner series (free, ~2 hours)** at https://saint11.art/pixel_articles/. Pedro Medeiros did the art on Celeste and TowerFall. Articles 4, 5 and 6 (Basic Shading, Anti-Alias and Banding, Basic Color Theory) are the three that will change your output immediately.
3. **Read four Slynyrd Pixelblog posts (free)**, in this order: #1 Color Palettes, #6 Light and Shadow, #20 Top Down Tiles, #43 Top Down Tiles Part 2. Raymond Schlitter writes the most technically specific top-down-RPG tutorials on the internet, and #20 is literally about 16x16 grass and dirt tiles in a 3/4 top-down projection, which is your first task.
4. **Then make one 16x16 grass tile** using the recipe in the "Seamless tile" section below. Do not read anything else until you have a tile that repeats without a visible grid.

Bookmark for later, not today: AdamCYounis's "Pixel Art Class" YouTube playlist (60 free videos, verified count). Watch episodes on demand, not in order. The six that map to your asset list are named in the "Curriculum" section.

**Skip:** any "top 10 pixel art tips" listicle, and the AI-generated SEO sites that dominate these search results (sprite-ai.art, spritesheets.ai, pixnote.net, generalistprogrammer.com, pixelartapp.com). They paraphrase the sources above, badly, and they invent specifics.

Four directions, but only **three unique poses**, because the side view is mirrored for left and right. Walk cycle is **4 frames**. His run cycle is 8 frames, and the walk borrows from it by omitting the full-stride frames.

Note the tension with your spec: you said 64x64 walk sheets. A 64x64 *cell* holding a ~16x32 or ~24x40 character with headroom is a normal layout. A character that actually fills 64x64 pixels is roughly 4 tiles tall, which is a different game (more Octopath than Stardew) and roughly 4x the animation labor per frame. Decide which you meant before you draw anything, because it sets the pixel density for every other asset.

## The ten skills that separate professional from amateur

Jargon is defined on first use. Each item is: what the mistake looks like, then the fix.

### 1. Palette discipline

**The term.** A palette is the fixed, small set of colors you are allowed to use for a piece. "Limited palette" means you decided the list before you started drawing and you do not add to it.

**The mistake.** You pick each color with an eyedropper or a color wheel as you need it. After an hour your tileset has 60 colors, 9 of which are nearly-identical greens. Nothing looks like it belongs to the same world, and your assets do not sit next to each other correctly.

**Why limited reads better.** Two mechanical reasons, not aesthetic ones. First, reuse forces color *relationships* to repeat across assets, and the eye reads repeated relationships as "one world". Second, a small palette forces every color to earn a distinct job (this is the shadow, this is the midtone, this is the accent), so shapes stay separable at 16px. Saint11 states the goal directly: "My main objective when it comes to colors is to do as much as I can with as little as possible."

**The fix.** Build **ramps** before you draw. A ramp is an ordered run of colors from dark to light that describes one material (one ramp for grass, one for wood, one for skin). Slynyrd builds 8 ramps of 9 swatches each for a 128-color master palette; you will want far fewer. For your 8 to 24 cap:

- A 16x16 terrain tile: 3 to 5 colors, all from one ramp plus maybe one accent. Slynyrd's exact warning in Pixelblog #20 is "You only need a few colors to make a rich texture. Too many colors and the texture will become blurry."
- A 16x16 or 32x32 prop: 6 to 10, typically two ramps of 3 to 4 plus an outline color.
- A 64x64 character: 12 to 20, three or four ramps (skin, hair, clothing, accent).

Do not start from scratch. Pull a ready-made palette from https://lospec.com/palette-list, filter by color count, and work inside it for your first month. The most-used ones there are apollo, dawnbringer-32, pico-8, resurrect-64, aap-64, slso8, endesga-64, lost-century, endesga-32 and oil-6. For a cozy farm game, start from a 32-color set and pull 8 to 24 per asset from it. Lospec exports `.gpl` and `.ase` files directly.

**Programmer's check.** Your 8-to-24 cap is trivially enforceable in CI. Count unique RGBA tuples per PNG and fail the build over 24. Do this from day one; it will catch anti-aliasing leaks too.

### 2. Hue shifting instead of adding black

**The term.** Hue is the "which color is it" axis (red, green, blue), separate from saturation (how vivid) and brightness. Hue shifting means the darker end of a ramp is a *different hue*, not just a darker version of the same one.

**The mistake.** You take your grass green, drag the brightness slider down, and call it the shadow. Slynyrd names this a **"straight ramp"**: a ramp that "transitions only brightness and saturation without hue variation". The result, in his words, is colors that "lack interest and be difficult to harmonize with ramps of a different hue". Worse is mixing in pure black, which flattens the piece and kills the sense that light is coming from anywhere.

**The fix.** As a swatch gets darker, rotate its hue toward the cool side; as it gets lighter, rotate toward warm. Saint11's version, plainly: "I made the shadow a little more blue and less saturated (colder), and the light a little more yellow and saturated (warmer)."

Slynyrd's concrete numbers: **20 degrees of positive hue shift between adjacent swatches**, and "20 is about as high as I go". His saturation "peaks around the middle and never fully goes to 100, or 0"; his brightness "consistently increases from left to right and usually never starts at 0, unless I want black". His named cardinal error is "combining high saturation and brightness, unless you want to burn some eyeballs". Saint11 adds: "if you're not sure, avoid using 100% saturation in colors."

**Practical rule for you.** Build every ramp in HSB, not RGB. Step brightness up in decreasing increments, and rotate hue 15 to 20 degrees per step. Warm light means cool shadows; cool light means warm shadows. Pick one and hold it across the whole game.

### 3. Readable silhouette

**The term.** The silhouette is the shape of your sprite if you filled every non-transparent pixel with solid black.

**The mistake.** You start with details, drawing a face and buttons on a blob. At 16x32 on a 1080p screen with the game running, the player never sees the buttons; they see a vertical smudge. Every prop on your farm looks like the same rounded rectangle with different colors.

**The fix.** Build silhouette first, details last. Adam Younis's #3 "Constructing a Character" and #5 "Character Sprite Details" are the right order to work in, and Slynyrd's #22 says the same: start with "a dummy sprite composed of clearly defined solid color body parts" before adding lighting.

**The test, which is cheap and you should automate it.** Flatten your sprite to pure black on white, view it at 1x, and ask whether you can name the object. A chest and a barrel must differ in outline, not just in surface. For animation frames, the silhouettes must differ *between* frames, or the motion will not read. Do the same for your 16x16 icons: at 16px, an icon is essentially only its silhouette plus two values.

Derek Yu's related rule for props and characters: pick "two or three main colors" so the eye is not distracted, and avoid "colors that are very similar to one another".

### 4. Banding

**The term.** Banding is when two color regions meet along a long, parallel, equal-length run of pixels, so the border between them reads as a hard stripe rather than as a curving surface.

**The mistake.** You shade a round barrel by drawing three long diagonal strips of green in parallel. It looks flat and slightly blurry, and it draws the eye to the strips instead of to the form. Saint11's definition: banding is "when we have multiple color bands that are clearly distinct from one another," which is "usually very problematic and makes the object look flat and sometimes blurry". Pixel Parmesan's framing is sharper and more useful: banding is when parallel lines of equal length **reinforce the pixel grid** instead of the form.

**The fix.** Saint11 gives two: compress the bands into a smaller area, or rotate the gradient direction (a horizontal slope wants horizontal transitions; a vertical slope wants vertical). Concretely: break the parallel runs by varying their lengths, and never let two adjacent color boundaries run the same length in the same direction. This is also why "shade with fewer colors" is good advice for beginners; his own note in the shading article is "I only used two colors because I want to keep it simple and the banding effect to a minimum."

### 5. Jaggies

**The term.** A jaggy is an irregular step in what is supposed to be a smooth line or curve. Note this is *not* the same as aliasing in the graphics-programming sense; here it means specifically an *inconsistent* staircase.

**The mistake.** You freehand a curve and get pixel run lengths of 3, then 1, then 3. Derek Yu's exact diagnostic: "the clean-looking curve goes 6 > 3 > 2 > 1, whereas the curve with the jaggy goes 3 > 1 < 3." Your grass edge looks chewed.

**The fix.** Run lengths along a curve must be **monotonic**: strictly decreasing or strictly increasing, never up-then-down. A 45-degree line is all 1s. A shallow line is all 4s. A curve goes 6, 4, 3, 2, 1, 1. Learn to count the runs; this one is arithmetic, not talent.

Turn on your editor's **pixel-perfect pencil mode**, which removes the doubled corner pixel an L-shaped drag produces. Then fix the remaining runs by hand. Lospec's tag page https://lospec.com/pixel-art-tutorials/tags/lines collects tutorials on this specifically.

### 6. Selective outlining

**The term.** A full outline wraps the entire sprite in one color (usually black). A selective outline varies the outline color around the sprite, or omits it entirely in places.

**The mistake.** Every asset gets a uniform 1px black border. Your game reads as a coloring book, and because black is maximally dark, the outline visually outweighs the actual art inside a 16x16 sprite. This is roughly 30 percent of the total pixels on a small icon spent on a border.

**The fix.** Derek Yu: "Rather than using black outlines throughout, apply colors closer to the sprite itself. Vary brightness along edges based on your light source." So the lit top-left edge of a chest gets a mid-brown outline; the shadowed bottom-right gets near-black; where the chest sits on grass, the outline can darken toward the grass's dark ramp instead of going black. This is how you get form and light out of the outline instead of just a border.

**For a cozy farm game specifically:** a consistent dark-but-not-black outline (a very dark desaturated version of the object's own hue) is the safest house style, because it survives being placed on grass, dirt, wood floor, and water without clashing. Decide the rule once and put it in your art standard next to the color cap.

The reference set, all archived on Lospec's selective-outlining tag: Tsugumo's "So You Want To Be A Pixel Artist?" Chapter 12 (`yarrninja.com/pixeltutorial/chapter12.htm`) and the Pixel-Zone selout tutorial (archive.org). **Caveat: yarrninja.com refused a connection when I tried it on 2026-09-04**, so treat that one as possibly dead; use the Derek Yu tutorial and Saint11's Outlines post instead.

### 7. Dithering, and when it is wrong

**The term.** Dithering interlaces two colors in a pattern (checkerboard, or thinning stripes) to simulate a third color that is not in your palette.

**The mistake, in three flavors.**
- Dithering because it "looks like pixel art". It is a 1990s workaround for hardware color limits, not a style requirement.
- Dithering a 16x16 tile or a small sprite. Pixel Parmesan is explicit: "certain dithering patterns inherently require a certain amount of adjacent available pixels," and small sprites do not have them. The pattern turns into noise.
- Dithering something that animates. Direct quote: avoid it on "most character sprites, especially those that will need to be animated." The pattern crawls between frames and reads as static.

**The fix.** For your project, the honest answer is: **do not dither at all for now.** At 16x16 with an 8-to-24 color budget, the correct move is almost always to add one more color to the ramp rather than to fake it with a pattern. If you later want it for a large background or a sky gradient, the two rules that matter are: pick one or two patterns and vary the number of rows between steps rather than cycling through many different patterns; and "the greater the contrast between the two colors you are blending, the more dithering steps you will need (and in turn the greater the resolution required)."

The failure test is trivial: view at 1x. If the dithered region reads as static rather than as a smooth transition, it is wrong.

### 8. Hand anti-aliasing, and why your binary-alpha rule forbids the kind that hurts

**The term.** Anti-aliasing (AA) means placing an intermediate color between two contrasting colors to soften a stepped edge. Saint11: "the process of using a color in between to fill some of those pixels to create the illusion of a softer transition." In pixel art you place these pixels **by hand**, one at a time. You never let a filter do it, because a filter produces hundreds of unique colors and semi-transparent pixels.

**Your project rule.** "Binary alpha only, no anti-aliasing" means every pixel's alpha is either 0 or 255. There is no such thing as a 40 percent transparent pixel in your PNGs.

**This is not a handicap. It is what professionals do anyway on the outer edge.** Two independent sources say so:

- Derek Yu, on AA: "do not anti-alias outer edges to prevent halos on varying backgrounds."
- Pixel Parmesan: "AA on outer edges of game art in particular may not always look the way you intend depending on the background," and recommends "keeping anti-aliasing inside sprites for better readability."

The reason is mechanical. A semi-transparent or blended edge pixel is computed against *one* assumed background. Your chest will sit on grass, on dirt, on a wooden floor, and in front of water. Against every background except the one you blended for, that softened pixel reads as a dirty halo. This is a real, visible artifact, not a purity argument. It is also why your art standard is correct to forbid it globally rather than case by case.

**What you can still do.** Internal AA, between two opaque colors that are both in your palette, is fully legal under binary alpha and is where most of the benefit lives: smoothing a long shallow curve on a character's shoulder, or the transition on a curved barrel. The rules for doing it well:

- Only AA a step that is longer than 1 pixel. Saint11: do not AA 45-degree lines (the 1-by-1 staircase) or straight lines. There is nothing to smooth.
- "The longer the segment, the longer the AA" (Pixel Parmesan). A 6-pixel run gets a longer intermediate strip than a 3-pixel run; Saint11 says to vary halftone strip length proportionally to step length.
- Do not overdo it. Over-application makes the sprite blurry and, at 16px, illegible. Saint11's stop condition: stop "when it reduces readability rather than improving it."
- The intermediate color must actually sit between the two it bridges in perceived value, and it counts against your 8-to-24 budget.

**Enforce it in code.** Assert that every pixel's alpha is exactly 0 or 255. A one-line check catches an accidental soft brush, a scaled-down layer, or an export setting change months from now.

### 9. Consistent light direction

**The term.** One light source, one direction, for every asset in the game.

**The mistake, which has a name.** **Pillow shading**: shading an object by putting the light in the middle and darkening evenly toward all edges, which happens "when trying to shade an object with no clear light source" (Saint11, Basic Shading). The result is a puffy, inflated look with no form. The second-order mistake is subtler and worse for a game: each asset individually shaded fine, but the chest is lit from the left and the barrel from the right, so the room looks incoherent even though no single sprite is wrong.

**The fix.** Pick a direction and write it into the art standard alongside the canvas sizes. Slynyrd favors "primary light from the top right or left hand side of the composition" because it "creates dynamic highlights and shadows while remaining balanced and natural." Top-left is the most common convention in 2D games. Pick one, put it in the standard, and never revisit it.

Then, per asset: identify the plane facing the light (highlight), the plane facing away (shadow), and the plane in between (midtone). That is your 3-color minimum. Add a cast shadow underneath at a consistent offset so props sit on the ground rather than floating; the direction of that offset is dictated by the same light rule.

For a top-down 3/4 game there is an extra wrinkle: 3/4 projection means you see both the top face and the front face of objects. The top face is always lighter than the front face, regardless of side lighting, because it faces the sky. Bake that into every prop.

### 10. Pixel density consistency

**The term.** Pixel density is how large a single art pixel appears on screen. Two assets have consistent density when their pixels are the same size on the player's monitor.

**The mistake.** You draw a character at 64x64, decide the house looks small, and scale the house sprite to 1.5x in the engine. Now the house's pixels are 1.5 screen-pixels wide, some of them get a fractional edge, and the house reads as slightly blurry next to a crisp character. Same failure if you rotate a sprite by 30 degrees, or if you scale down.

Saint11's article on this is blunt: "Every time someone mixes pixel art resolutions, an angel dies."

**The fix, four rules.**
- **Integer scale only.** "You can scale up pixel art forever without losing quality. The bad news is that you can only do this in 100% increments of the original image." 2x, 3x, 4x. Never 1.5x, never 2.5x.
- **Nearest neighbor filtering only.** Use "Nearest Neighbor, Point, or None". Never "Bilinear, Linear, or Bicubic". This is a texture import setting in your engine and a default you must change; it is also why a browser or image viewer showing your PNG blurry does not mean your PNG is wrong.
- **Never scale down.** "You shouldn't scale pixel art down, it will ruin it." The only exception is scaling back down to a known original size.
- **At most two source resolutions in a project**, on separate canvases, at integer multiples of each other. Your spec already implies this: 16, 32, 64 are all multiples of 16, so you are fine as long as every asset is authored at 1x and the *engine* does the uniform zoom.

Adam Younis's #43 "The Importance of Character Scale" and #35 "What's The Right Canvas Size?" cover this from the game-design side. Decide your global zoom factor (3x and 4x are the usual choices for a 16px grid) before you draw asset number two.

## Making a 16x16 tile that tiles seamlessly

This is your first task, so here is the whole thing.

### The concept

A tile is seamless when its right edge continues into its own left edge, and its bottom edge into its own top edge. Two failure modes, and beginners usually only think about the first:

1. **Visible seams.** The edges do not line up, so you see a grid of hard lines. Easy to spot, easy to fix.
2. **Visible repetition.** The edges line up perfectly, but there is one bright pixel cluster in the tile, and when 400 copies are laid out you see 400 identical bright dots in a perfect lattice. Your eye is extremely good at finding this, and it is what makes amateur tilesets look amateur. It is the harder problem.

### The build recipe

Distilled from Slynyrd Pixelblog #20 and #43, and the Aseprite brick walkthrough at https://agatedragon.blog/2024/06/19/brick-texture-in-aseprite/:

1. **Turn on tiled preview.** In Aseprite: `View > Tiled Mode > Tiles in Both Axes`. The canvas now shows your 16x16 repeating in all directions and updates live as you paint. This is not optional; you cannot judge a tile by looking at one copy of it.
2. **Fill with the midtone.** One flat color, the base of your grass ramp.
3. **Add a darker value and a lighter value.** Three colors total at this stage. Resist adding a fourth.
4. **Draw in clusters, not in noise.** A cluster is a small connected blob of the same color, maybe 2 to 6 pixels. Slynyrd's rule: define a few key clusters and repeat them, but "avoid touching key clusters with other key clusters." Random single-pixel speckle reads as dirt on the screen, not as texture.
5. **Deliberately run clusters off the edge.** This is the actual technique for hiding seams. Slynyrd: incorporate clusters that "overlap the edges and loop around the tile to help hide the seams." A blade of grass that starts at x=15 and continues at x=0 makes the seam structurally invisible, because there is real content crossing it.
6. **Balance the visual weight.** No corner or side should be denser or brighter than the others. Uneven weight is what creates the lattice pattern when tiled.
7. **Break up the repetition with negative space.** Slynyrd's rule for this: mix "spaces of flat green with textured areas of differing vegetation density." A tile that is uniformly textured tiles into a buzzing carpet. A tile with a couple of calm empty regions tiles into something that looks like ground.
8. **Do not make the pattern obvious.** Explicit don'ts from #20: do not make patterns "too obvious", and do not put two busy textures next to each other.
9. **Then build the variants.** Pixelblog #43's method: "the base repeating texture must loop well on all four sides", and then "all side and corner variants can be made by shaving off portions of the base texture." Mirror tiles for opposite orientations rather than redrawing them. Then draw **transition tiles** that "gracefully merge" grass into dirt, since a hard boundary between two terrains is the other thing that screams amateur.

### The offset check, and an Aseprite gotcha worth knowing

The classic verification, used for decades: shift the image by half its width and half its height, wrapping around. The former edges now meet in the middle of the canvas where you can see them clearly. Anything that was hidden at the border becomes obvious.

**Aseprite's Tiled Mode does not do this for you, and it does not wrap when you move things.** It is a *preview only*. A community thread describes it as: it "just duplicates your art around, and updates it live." And a selection dragged past the edge is deleted, not wrapped. The feature request to make moves wrap ([aseprite/aseprite#4924](https://github.com/aseprite/aseprite/issues/4924), opened 2025-01-09) is **closed as a duplicate**, so it is a known gap, not a setting you missed.

Since you are a developer, do not fight the editor. Add this to your asset pipeline instead:

```python
# tilecheck.py — 3x3 tiled preview + half-offset seam view + spec assertions
from PIL import Image
import sys

im = Image.open(sys.argv[1]).convert("RGBA")
w, h = im.size

# spec assertions from the art standard
assert (w, h) in {(16,16), (32,32), (64,64)}, f"bad canvas size {w}x{h}"
alphas = {p[3] for p in im.getdata()}
assert alphas <= {0, 255}, f"non-binary alpha present: {sorted(alphas)}"
colors = {p for p in im.getdata() if p[3] == 255}
assert 1 <= len(colors) <= 24, f"{len(colors)} opaque colors, cap is 24"

# 3x3 tiled sheet: reveals lattice/repetition, not just seams
sheet = Image.new("RGBA", (w*3, h*3))
for y in range(3):
    for x in range(3):
        sheet.paste(im, (x*w, y*h))
sheet.resize((w*3*8, h*3*8), Image.NEAREST).save("tiled_3x3.png")

# half-offset: former edges now meet in the centre
off = Image.new("RGBA", (w, h))
off.paste(im.crop((w//2, h//2, w, h)), (0, 0))
off.paste(im.crop((0, h//2, w//2, h)), (w - w//2, 0))
off.paste(im.crop((w//2, 0, w, h//2)), (0, h - h//2))
off.paste(im.crop((0, 0, w//2, h//2)), (w - w//2, h - h//2))
off.resize((w*16, h*16), Image.NEAREST).save("offset_seam.png")
print(f"ok: {w}x{h}, {len(colors)} colors, alpha {sorted(alphas)}")
```

Run it on every tile before you commit. The 3x3 sheet is the one that catches the lattice, because a single tile at 8x zoom will always look fine.

**One thing to watch:** a 16x16 tile has very few edge pixels, so it is genuinely harder to make seamless than a 32x32 one. If a grass tile fights you, it is not your skill; it is the pixel budget. Slynyrd calls 16x16 "probably the most common size" and caps his recommendation at 32x32 (beyond which tiles become "laborious"). The professional solution to a 16px grid looking repetitive is not a cleverer single tile, it is **four or five variant tiles** scattered randomly by the engine, plus edge and corner variants. His own Top Down RPG asset pack ships **44 grass and dirt tiles at 16x16**. That is the real number. One tile is never the answer.

**Tool note:** Slynyrd names Pyxel Edit alongside Aseprite specifically because both show tile connections in real time. If tile work becomes the bulk of your day, it is worth a look; I have not priced it here.

## The practice loop that actually produces improvement

Reading does not make you better at this; volume with feedback does. Concretely:

1. **One asset per day, timeboxed to 45 minutes.** Small canvases mean a finished asset is genuinely a day's work, not a week's. Adam Younis's #52 "Why smaller pixel art is actually harder" is worth watching for why this is not a soft start.
2. **Copy before you invent.** Open a Stardew Valley or Sword of Ditto screenshot, zoom in, and reproduce a single tile or prop pixel by pixel. You are not stealing it (do not ship it); you are reverse-engineering decisions. Count the colors. Find the light direction. Find where they used selective outlining. This is the single highest-yield exercise for someone who has never drawn, because it removes "what should this look like" and leaves only "how did they do that". Adam Younis #26 "How To Use References Effectively" covers doing this deliberately.
3. **Judge at 1x, always.** Keep a second window showing the sprite at final in-game size. Every mistake in this document is invisible at 800% zoom and obvious at 100%.
4. **Get critique from strangers.** Your own eye is calibrated to your own mistakes. Lospec's community index is at https://lospec.com/pixel-art-communities, and the ones it flags as good for feedback are:
   - **Lospec Discord** (https://discord.gg/QjsgTQM, verified redirect from lospec.com/discord) — has dedicated feedback channels. Best first stop, lowest friction.
   - **Pixel Art Official Discord** (https://discord.gg/NkYWDXr) — grew out of r/PixelArt, described as "a pretty active place to get live feedback".
   - **PixelJoint** (https://pixeljoint.com) — running since 2004, weekly challenges, the highest quality bar of the lot. Weekly challenges are a good forcing function. *Caveat: pixeljoint.com returned HTTP 403 to my fetch, so the 264,581-member / 109,890-artwork figures I saw come from a search result rather than a page I read directly.*
   - **r/PixelArt** (https://reddit.com/r/pixelart) — 100,000+ members, described as "great for beginners", but expect encouragement more than critique.
   - **Pixelation** (https://pixelation.org) — Lospec describes it as "old but still active" with deep technical threads. *Caveat: the domain refused connections from this machine on 2026-09-04 (both a WebFetch and a curl failed). Treat as possibly offline.*

   When you post, ask a specific question ("is my light direction consistent across these three props?") rather than "thoughts?". You get technical answers instead of thumbs-ups.
5. **Encode the standard as tests, not as prose.** You already have a written art standard. Turn the canvas sizes, binary alpha, color cap, and absence of an ICC chunk into assertions that run on commit. This is the one genuine advantage you have over a self-taught artist, and it means you never ship a violation because you were tired at 1am.

Briefing: "Slynyrd builds 8 ramps of 9 swatches each for a 128-color master palette." 8 × 9 = 72. ## (b) Established public palettes (Lospec)

**Verdict: this works, it is nearly free, and it is routinely oversold.**

### What a palette actually buys you

A palette buys **cohesion**: every asset looks like it belongs to the same game, shadows agree with each other, and nothing clashes. That is the difference between "clashing hobbyist" and "coherent hobbyist", and it is genuinely large.

A palette does **not** buy you form, volume, anatomy, perspective, or animation timing. Those are drawing. Anyone telling you palette is 80% of the professional look is selling something. My honest estimate: palette is the cheapest 20% of the gap and the most under-invested one, so do it first, but do not expect it to carry you.

Slynyrd (Raymond Schlitter, whose [Pixelblog series](https://www.slynyrd.com/pixelblog-catalogue) is the standard free tutorial reference) puts the payoff as consistency rather than skill substitution: "We've been able to depict an incredible range of environments and characters while maintaining a consistent look overall." ([Pixelblog 1, Color Palettes](https://www.slynyrd.com/blog/2018/1/10/pixelblog-1-color-palettes))

### How to pick one, concretely

The [Lospec Palette List](https://lospec.com/palette-list) holds 4,454 palettes, filterable by exact colour count. Most-used ones are apollo, dawnbringer-32, pico-8, resurrect-64, aap-64, slso8, endesga-64, lost-century, endesga-32 and oil-6.

**Pick a 16 to 32 colour master palette, not a 64.** Your per-asset cap is 8 to 24 colours. A 64-colour palette invites you to exceed that on every sprite and then fight your own export validator. A 32-colour master lets you sub-select 8 to 24 per asset naturally.

Two concrete starting points for cozy farm:
- **[Sweetie 16](https://lospec.com/palette-list/sweetie-16)** by GrafxKid, 16 colours, 67,437 downloads, and the default palette of the TIC-80 fantasy console. Warm, saturated, reads as friendly. Hex values: `#1a1c2c #5d275d #b13e53 #ef7d57 #ffcd75 #a7f070 #38b764 #257179 #29366f #3b5dc9 #41a6f6 #73eff7 #f4f4f4 #94b0c2 #566c86 #333c57`.
- **[Endesga 32](https://lospec.com/palette-list/endesga-32)**, a warmer and more saturated 32-colour set, if 16 feels too tight for four seasons of terrain.

Downloads come in PNG, JASC PAL, Photoshop ASE, GIMP GPL and plain hex, so importing into Aseprite is a two-click job.

### The licence question on palettes

**Lospec publishes no site-wide licence statement.** I checked the palette list page and there is none. In general a list of colour values is not a copyrightable work, which is why the site distributes them freely for exactly this purpose. But a **small number of individual palettes state their own licence** (I saw MIT and CC-BY-4.0 on specific entries), so open the specific palette's page and look before you commit your whole game to it. Verified as an absence, not as a permission, so treat it accordingly.

### Why this also solves your technical constraints

Set the Aseprite sprite to **Indexed** colour mode with your chosen palette loaded. Indexed mode makes it structurally impossible to exceed your colour cap, and it makes anti-aliasing impossible to introduce by accident, since every pixel must be one of the N palette entries plus the single transparent index. Your "binary alpha only, no anti-aliasing, 8 to 24 colours" standard stops being a discipline you have to police and becomes a property of the file format.

## (c) Tracing and rotoscoping from 3D or photos

**Definitions first.** *Tracing* means drawing on a layer above a reference image and following its outlines. *Rotoscoping* means doing that frame by frame over a moving reference, so the motion is real rather than guessed. *Prerendering* means rendering a 3D scene at low resolution and shipping the render itself as the sprite.

**Verdict: legitimate, professionally used, and less useful to you than it sounds.**

### It is legitimate

Saint11, a professional pixel artist who worked on Celeste, publishes his own 3D-reference workflow: "I roughly modelled this 3D shape in Blender and used ShareX to record the screen while I rotated the model", then imported it, cut the resolution and palette, kept a few key frames, and "went on and just drew everything on another layer" ([saint11.art/blog/3d-ref](https://saint11.art/blog/3d-ref/)). His summary of the point: "when blocking things for reference, don't waste too much time... just focus on the important part, the perspective!"

Prerendered 3D as shipped sprites has decades of precedent (Donkey Kong Country being the famous case) and is still done, for example [this Blender-to-Sega-Genesis prerender pipeline devlog](https://joejoejoejoe.itch.io/redlinereaver/devlog/295782/prerendering-blender-to-sega-genesis). Nobody serious considers reference use cheating. Rotoscoping is how Prince of Persia and Another World were animated.

Aseprite supports this directly. `Layer > New > New Reference Layer from File` creates a layer that displays reference imagery at higher resolution than the canvas and that "cannot be drawn on or edited" ([Aseprite reference layer docs](https://www.aseprite.org/docs/reference-layer/)).

### Where the line actually is

Tracing **your own render, your own photo, or a licensed 3D animation** is fine. Tracing **someone else's finished sprite or artwork** is copyright infringement, and in pixel art it is also obvious to anyone who has seen the original. That is the whole distinction.

For licensed motion reference, **Mixamo** (free with an Adobe account) provides rigged characters and walk cycles. Per third-party licence summary, commercial use is allowed with no royalties and editing is permitted, with the main restriction being that "characters and animations cannot be redistributed as standalone assets. They must be incorporated into a larger project" ([licenseorg.com/guide/3d-assets/mixamo](https://www.licenseorg.com/guide/3d-assets/mixamo)). Using a Mixamo walk as timing reference for a hand-drawn sprite is comfortably inside that. **Caveat: I could not load Adobe's own FAQ page (it timed out), so verify against Adobe's terms directly before you rely on this.** Mixamo has also been described as no longer actively supported, so do not build a pipeline that depends on it staying up.

### Why it will help you less than you expect

At your sizes, the reference resolution swamps the target. A 16x16 tile has 256 pixels total. There is no photo detail that survives the trip down, so tracing gives you nothing a rectangle would not. Even a 64x64 character cell holding a ~32px tall figure has roughly one pixel per two centimetres of a human body, which means the entire drawing is silhouette plus three or four value steps.

**Where it does pay off, specifically:**
- **Walk cycle timing.** Which foot is forward on frame 2, how much the body bobs. This is the thing beginners get wrong and reference fixes instantly.
- **Rotation and unusual perspective on props.** A chest opening, a windmill turning, a cart at three-quarter view. This is exactly Saint11's use case.
- **Nothing else.** Do not trace terrain tiles or icons.

### One trap to avoid

Automatic pixelation add-ons exist ([Pixelize for Blender](https://github.com/LeonardoDocs/Pixelize) does resolution downscaling and colour quantization). **Do not ship their output.** Auto-quantized renders produce soft edges, semi-transparent pixels, and dozens of near-duplicate colours, which violates all three of your hard constraints at once (binary alpha, no anti-aliasing, 8 to 24 colours) and reads as "3D pretending to be pixel art" to anyone who knows the medium. Use 3D for the reference layer, then redraw by hand on top. Every frame.

### Doing the arithmetic on your actual asset

Your spec: 64x64, four directions, 4-frame strips. That is **16 frames** for a walk alone.

- At $5/frame plus a $25 character base: **$105**
- At $8/frame plus a $25 base: **$153**
- Realistic band for competent indie work: **$80 to $250**
- Strong work with idle, walk, and two tool-use animations: **$300 to $600**

### The comparison that should decide it

Mana Seed's Farmer Sprite System is **$29.99 for 150+ animations in 4 directions** on the exact 64x64 grid you need. No commission at any price in the bands above competes with that on volume. Commission only if:

- Your character design is genuinely non-standard (non-human, unusual proportions, a specific IP look), or
- You have shipped enough of the game to know the art direction and the bought base is fighting it.

### If you do commission, buy this instead of just a walk sheet

Buy **a walk sheet plus a style bible**: the artist's palette file, one finished 16x16 terrain tile, one finished 32x32 prop, and a short note on their shading rules. That way the $150 buys you a target you can match for the next two years of props, rather than one orphaned sprite sheet your own tiles clash with.

Make these terms explicit in writing before paying:
- Full commercial rights, worldwide, perpetual, including sequels and DLC. Not a licence.
- **Layered .aseprite source files**, not just PNGs. Without sources you cannot fix a frame later.
- Exact cell size 64x64, indexed to your palette, binary alpha, no anti-aliasing. Give them the standard as a written spec, because most artists default to anti-aliased RGBA and will hand you something your build rejects.
- 50% up front, 50% on delivery is the norm on these boards.

## (e) Style choices that hide weak drawing

Ranked honestly by how much they actually do.

### These work

**1. Smaller sprites. Strongest lever, and free.**
Stardew Valley's overworld characters are **16x32 pixels**, on 16x16 tiles, with 64x64 reserved for the big portrait art. Your 64x64 spec is the *cell size*, not the character size. Draw a roughly 32px tall character centred in a 64x64 cell, which is exactly what Mana Seed does ("~32 pixels high, centered in 64x64 cells"), and you satisfy the standard while cutting the drawing area by three quarters. Fewer pixels means fewer places to be wrong. Nobody looks at Stardew and thinks the art is weak.

**2. Strong silhouette. Second strongest, also free.**
Test: fill the sprite with a single flat colour and look at it at 100% zoom. If you cannot tell a chest from a crate, no amount of shading will save it. Beginners fail on silhouette and try to fix it with detail, which makes it worse. Read-in-one-colour is a five-second check you can run on every asset.

**3. Limited palette. Real but moderate.** See section (b). Cohesion, not form.

**4. Outlines.** Slynyrd notes that outlines "are often necessary to preserve readability within a limited palette" and help separate sprites from background ([Pixelblog 5, Back to Basics](https://www.slynyrd.com/blog/2018/5/16/pixelblog-5-back-to-basics)). A consistent dark outline also hides a multitude of shaky interior shading, because the eye reads the boundary first.

**5. Avoiding faces at small sizes.** At 32px tall a face is about 4x4 pixels. Two dark pixels for eyes, no nose, no mouth. This is not a compromise, it is what every cozy game including Stardew actually does, and it is why they read as charming rather than uncanny. Save expression for portraits, and if you need portraits, commission those (they are a single static image, so cheap) rather than trying to animate faces.

**6. Fewer animation frames.** Your 4-frame strips are already the right call. Every extra frame is another chance for a bad in-between, and bad in-betweens read as amateur far more loudly than a simple 4-frame loop does. 4 frames done cleanly beats 8 frames done unevenly.

**7. Overlap and layering.** Slynyrd's point that "overlap and the use of subtle outlines allow a lot to be achieved with a 16 color limit" is practical: a fence in front of a bush reads as depth without you drawing either object well.

### These do not work

**Heavy dithering.** Beginners reach for it to fake gradients. It reads as noise at 16x16, it blows your 8 to 24 colour budget's *perceptual* value even when it technically fits, and experienced eyes read it as compensation. Use it sparingly or not at all.

**Anti-aliasing.** Forbidden by your standard anyway, and hand-placed AA is itself an advanced skill. The constraint is doing you a favour.

**Adding detail.** The universal beginner instinct, and it always makes things worse at these sizes. If a tile looks wrong, remove pixels.

**Complex perspective props.** A three-quarter-view staircase will expose you. Design your prop list around front-facing and simple top-down objects, and use the bought pack for anything requiring real perspective.

### The uncomfortable honest note

Eric Barone made Stardew Valley's art as a beginner. It took him four and a half years, "thousands of hours" of pixel art practice, and multiple total asset overhauls where he "redrew sprites" and discarded months of work because his standards had outrun his earlier output. His own account: "I just persevered and forced myself to learn. You realize the thing that you thought was good actually isn't." None of the shortcuts above compress that. What they do is let you ship a good-looking game *while* it happens, instead of after.

5. **No validation script.** Four machine-checkable constraints and the recommendation is discipline plus a colour mode. A pre-commit check in Pillow or ImageMagick asserting canvas size, unique colour count between 8 and 24, alpha values restricted to 0 or 255, and absence of an `iCCP` chunk would enforce all four, and is a twenty-minute job for this reader.

7. **Sunnyside's character animations are labelled work in progress** on the product page, which matters if he uses it for anything beyond tiles and props.
