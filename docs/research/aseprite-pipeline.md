# Aseprite CLI, scripting, and solo pipeline ergonomics

# CLI

## Bottom line

Three commands cover all nine todoFarm classes, and the whole loop is a one liner per slot. The critical, non obvious constraints (all verified in Aseprite's own source at the released tag `v1.3.18.1`) are:

1. **Never use a Background layer.** Aseprite writes PNG colour type 2 (RGB, no alpha) instead of 6 (RGBA) when the sprite has a visible Background layer. Your `png.colorType` check is blocking, so a Background layer fails every submission, including fully opaque tiles.
2. **Keep the `.aseprite` in RGB colour mode**, or pass `--color-mode rgb` after the filename. An Indexed source produces an Indexed (colour type 3) PNG from both `--save-as` and `--sheet`.
3. **`--sheet-type vertical` is exactly your strip layout** (frame 1 at y=0, `y += frame_height` per frame), and **`--sheet-type rows --sheet-columns 4`** is exactly your 4x4 char grid.
4. **Aseprite does not embed iCCP unless the sprite carries a real ICC profile.** Default (sRGB) writes a tiny `sRGB` chunk, which your validator ignores. There is no `--color-profile` CLI flag; the fix, if ever needed, is a one line Lua script.
5. **`--scale` is nearest neighbour**, so `@2x`/`@4x` packs are safe.
6. **No CLI flag differences between Steam, itch and self compiled.** All ship the same binary. The trial cannot save at all.

I could not empirically run any of this: Aseprite is not installed on this machine (`/Applications/Aseprite.app` absent, nothing in the Steam path, nothing on `PATH`). Everything below is from the published docs plus the pinned source. Every claim marked "source" is code you can click through.

**Argument order is load bearing and the docs are explicit about it.**

- *Before* the filename: `--split-layers` ("Warning: The `--split-layers` option must be before your sprite"), `--ignore-layer` ("You must specify this parameter before opening the .aseprite file"), `--layer`, `--all-layers`, `--tag`, `--split-tags`, `--oneframe`, `--split-grid`, `--export-tileset`.
- *After* the filename: `--color-mode`, `--scale`, `--palette` (all defined as acting on "previously opened sprites"), plus `--save-as`, `--sheet`, `--data`.

**Four flags exist in the shipped binary but are missing from the docs page.** Verified present in `v1.3.18.1`'s `src/app/cli/app_options.cpp`:

| flag | source description, verbatim |
|---|---|
| `--shrink-to width,height` | "Shrink each sprite if it is larger than width or height" |
| `--power-of-two-size` | "Round up the width and height of the sprite sheet to the nearest power of 2" |
| `--play-subtags` | "Play subtags and repeats when saving the frames of an animated sprite" |
| `--disable-wintab` | "Don't load wintab32.dll library" (Windows only, `#ifdef _WIN32`) |

Also undocumented: `--dithering-algorithm error-diffusion` is accepted by the CLI parser (`src/app/cli/cli_processor.cpp` line 460) even though the docs list only `none`, `ordered`, `old`. Irrelevant to you (never convert to Indexed), but noted for accuracy.

Two doc list corrections worth knowing:
- `--sheet-columns` is **"Fixed # of columns for `-sheet-type rows`"** and `--sheet-rows` is **"Fixed # of rows for `-sheet-type columns`"**. The docs page shows the flags with no description at all.
- `--sheet-pack` is literally **"Same as `-sheet-type packed`"**.

Source: https://github.com/aseprite/aseprite/blob/v1.3.18.1/src/app/cli/app_options.cpp

**Flags you must never pass**, because each one breaks a fixed grid or a fixed canvas: `--trim`, `--trim-sprite`, `--trim-by-grid`, `--ignore-empty`, `--merge-duplicates`, `--extrude`, `--sheet-pack`, `--power-of-two-size`, `--crop`, `--slice`, `--shrink-to`. `--ignore-empty` in particular sets the sample to `Rect(0,0,0,0)` and the frame simply vanishes from the layout (`src/app/doc_exporter.cpp` line 537), silently shifting every later frame. Your `frames.allDrawn` check would never even see the blank frame.

## (b) Vertical strip, frames stacked top to bottom

`--sheet-type vertical`. This is not an inference, it is the layout loop:

```cpp
// src/app/doc_exporter.cpp, SimpleLayoutSamples::layoutSamples, line 619
if (m_type == SpriteSheetType::Vertical || m_type == SpriteSheetType::Columns) {
  framePt.y += size.h + shapePadding;
}
else if (m_type == SpriteSheetType::Horizontal || m_type == SpriteSheetType::Rows) {
  framePt.x += size.w + shapePadding;
}
```

`framePt` starts at `(borderPadding, borderPadding)` and samples are walked in frame order, so frame 1 lands at y=0 and x never moves. With all three paddings at 0 the sheet size is the exact union of the frame rects (`calculateSheetSize`, line 1253), so a 16x16 sprite with 4 frames gives exactly 16x64. That is `tile.anim` and `crop`.

**Runnable** (`tile.anim.water`, source is a 16x16 sprite with 4 frames):

```bash
ASEPRITE="/Applications/Aseprite.app/Contents/MacOS/aseprite"

"$ASEPRITE" -b --all-layers src/tile.anim.water.aseprite \
  --color-mode rgb \
  --sheet-type vertical \
  --border-padding 0 --shape-padding 0 --inner-padding 0 \
  --sheet art/tile.anim.water@1x.png
```

Do **not** use `--save-as` for strips. `--save-as` on a multi frame sprite writes one file per frame, not a strip.

Aside, since your filenames all contain `@1x`: the digit in `@1x` is harmless. `split_filename()` only strips *trailing* digits from the file title (`src/app/file/split_filename.cpp`), and `@1x` ends in `x`, so Aseprite will not mistake the `1` for a frame counter and start emitting `@2x.png`. Separately, `get_frame_info_from_filename_format()` matches only the literal `{frame` token, never bare digits (`src/app/filename_formatter.cpp` line 71).

## (c) 4 direction char sheet as a 4x4 grid

Source sprite: 16x16 canvas, 16 frames, tagged `down` 0-3, `up` 4-7, `left` 8-11, `right` 12-15 to match the slot brief. Then:

```bash
"$ASEPRITE" -b --all-layers src/char.player.walk.aseprite \
  --color-mode rgb \
  --sheet-type rows --sheet-columns 4 \
  --border-padding 0 --shape-padding 0 --inner-padding 0 \
  --sheet art/char.player.walk@1x.png \
  --data art/char.player.walk.json --format json-array \
  --list-tags --filename-format '{frame}'
```

Result: exactly 64x64, row 0 = down, row 1 = up, row 2 = left, row 3 = right.

Mechanism, from the same `layoutSamples`:

```cpp
if (m_type == SpriteSheetType::Rows && m_maxCols > 0)
  itemsPerBand = m_maxCols;                       // line 528
...
else if (m_type == SpriteSheetType::Rows) {
  if (width == 0) {                               // no --sheet-width given
    if (nextBand) {                               // nextBand includes itemInBand == itemsPerBand
      framePt.x = borderPadding;
      framePt.y += rowSize.h + shapePadding;
      itemInBand = 0;
    }
  }
  else if (framePt.x + size.w > width - borderPadding) { ... }
}
```

**Do not also pass `--sheet-width`.** Read the branch: `--sheet-columns` is only consulted when `width == 0`. Passing `--sheet-width 64` takes the other branch and the column count is ignored (it happens to produce the same 4x4 here, but it is a coincidence you should not rely on).

`nextBand` also fires on a sprite, layer, or tag change, so **do not add `--split-tags`** to this command. It would break the band on every tag and you would get a different geometry.

## (d) The `--data` JSON, schema and tag survival

**Frame tags do not survive by default.** You must pass `--list-tags`. Same for `--list-layers` / `--list-layer-hierarchy` (layers) and `--list-slices` (slices). This is the single most common surprise moving from the GUI Export dialog to the CLI, because the dialog has "Meta: Tags" checkboxes and the CLI defaults them all off. Confirmed by `if (m_listTags)` guarding the entire `frameTags` block in `createDataFile()`, `src/app/doc_exporter.cpp` line 1529.

Exact emitted shape, read straight off the writer (lines 1442 to 1640):

```jsonc
{ "frames": {                        // "{" for json-hash (default), "[" for json-array
   "<key>": {                        // json-hash: filename as key; json-array: "filename" attr
    "frame":            { "x": 0, "y": 0, "w": 16, "h": 16 },
    "rotated":          false,       // always literally false
    "trimmed":          false,
    "spriteSourceSize": { "x": 0, "y": 0, "w": 16, "h": 16 },
    "sourceSize":       { "w": 16, "h": 16 },
    "duration":         100          // milliseconds, from sprite->frameDuration(frame)
   }
 },
 "meta": {
  "app":     "https://www.aseprite.org/",
  "version": "1.3.18.1",
  "image":   "char.player.walk@1x.png",   // basename only, omitted if --sheet not given
  "format":  "RGBA8888",                  // or "I8" if the texture is Indexed
  "size":    { "w": 64, "h": 64 },
  "scale":   "1",                         // always the string "1"
  "frameTags": [                          // ONLY with --list-tags
   { "name": "down", "from": 0, "to": 3, "direction": "forward" }
  ],
  "layers": [ { "name": "Layer 1", "opacity": 255, "blendMode": "normal" } ],  // ONLY with --list-layers
  "slices": [ ... ]                       // ONLY with --list-slices
 }
}
```

A tag entry gains `"repeat": "<n>"` only when `tag->repeat() > 0`, and appends the tag's user data (colour, data string) inline. `meta.format` reports the *texture's* pixel format, which is not the same thing as the PNG colour type on disk. Do not use it as a validator input.

Official worked examples, both linked from the docs page: json-hash https://gist.github.com/dacap/db18e5747a4b6e208d3c , json-array https://gist.github.com/dacap/a32adb9248320326733a .

**Default JSON keys are ugly.** With no `--filename-format`, the sheet uses `get_default_filename_format_for_sheet()` (`src/app/filename_formatter.cpp` line 213), which builds `{title}` + ` ({layer})` + ` #{tag}` + ` {frame}` + `.{extension}`, giving keys like `"char.player.walk 0.aseprite"`, carrying the *source* extension. Pass `--filename-format '{frame}'` to get `"0"`, `"1"`, ... which your manifest generator can index directly.

**Stdout works**: `--data=""` writes the JSON to stdout instead of a file, which is documented and lets `build-manifest.mjs` consume it without a temp file.

## (e) Exact palette, no resampling, no ICC

**Resampling: `--scale` is nearest neighbour.** `--scale` runs the `SpriteSize` command with only a `scale` param (`cli_processor.cpp` line 442-450), and `SpriteSizeParams::method` defaults to `ResizeMethod::RESIZE_METHOD_NEAREST_NEIGHBOR` (`src/app/commands/cmd_sprite_size.cpp` line 62-66). So `--scale 2` and `--scale 4` are exact pixel duplication, safe for your S=1/2/4 rule. Nothing in the export path resamples otherwise.

**Palette: nothing rewrites your RGB.** Do not pass `--palette`, `--color-mode indexed`, `--dithering-*`. `--color-mode rgb` on an Indexed sprite is a palette lookup, not a quantisation, so it is lossless.

**ICC: there is no `--color-profile` flag.** I checked the complete `add(...)` list in `app_options.cpp` at `v1.3.18.1`. It does not exist. But you almost certainly do not need one:

```cpp
// src/app/file/png_format.cpp line 575
if (fop->preserveColorProfile() && spec.colorSpace())
  saveColorSpace(png, info, spec.colorSpace().get());

// line 748, saveColorSpace()
case gfx::ColorSpace::None: break;                             // no chunk at all
case gfx::ColorSpace::sRGB: png_set_sRGB(...); return;         // sRGB chunk, NOT iCCP
case gfx::ColorSpace::RGB:  png_set_cHRM_fixed / png_set_gAMA_fixed
case gfx::ColorSpace::ICC:  png_set_iCCP(...);                 // <-- the only iCCP path
```

Defaults are `color.manage = true`, `color.working_rgb_space = "sRGB"`, `color.files_with_profile = EMBEDDED` (`data/pref.xml` lines 455-462, wired in `src/app/file/file_op_config.cpp`). So a normally created sprite exports with an `sRGB` chunk, which your `png.iccp` check ignores because it only looks for `iCCP`. **Your validator and Aseprite's defaults already agree.**

The one way to trip rule 7: open a PNG that carries an ICC profile. `files_with_profile = EMBEDDED` keeps it on the sprite, and it is written back out as `iCCP` on export. Two fixes, both real:

```lua
-- assets/bin/strip-profile.lua
local s = app.sprite
if s then s:assignColorSpace(ColorSpace()) end   -- ColorSpace() == no profile at all
```

```bash
"$ASEPRITE" -b src/foo.aseprite --script assets/bin/strip-profile.lua --sheet art/foo@1x.png
```

`ColorSpace()` creating an empty (None) colour space and `Sprite:assignColorSpace()` assigning without touching pixels are both documented: https://github.com/aseprite/api/blob/main/api/colorspace.md and https://github.com/aseprite/api/blob/main/api/sprite.md . **Not verified by execution** (no binary here); specifically I have not confirmed that `app.sprite` is populated at the point `--script` runs in this argument order. Test once. The alternative, verified only at the source level, is turning off Edit > Preferences > Color > colour management, which sets `preserveColorProfile = false` and skips `saveColorSpace` entirely, producing a PNG with no colour chunk of any kind.

### The two blocking traps your validator will catch and nobody will understand

**Trap 1: a Background layer makes the PNG colour type 2, not 6.**

```cpp
// src/doc/sprite.cpp
bool Sprite::isOpaque()  const { Layer* bg = backgroundLayer(); return (bg && bg->isVisible()); }
bool Sprite::needAlpha() const { case IMAGE_RGB: return !isOpaque(); }

// src/app/file/png_format.cpp line 521
case ColorMode::RGB:
  color_type = (img->needAlpha() || fix_one_alpha_pixel ? PNG_COLOR_TYPE_RGB_ALPHA
                                                        : PNG_COLOR_TYPE_RGB);
```

A visible Background layer means `isOpaque()`, means no alpha channel, means colour type 2, means your blocking `png.colorType` check fires with the useless message `RGB`. Draw on ordinary layers only. In Aseprite: Layer > "Convert Background to Layer" if one exists. This bites hardest on `tile`, which is legitimately 100% opaque and where an artist's instinct is to use a Background.

This is why `--sheet` is immune: the sheet texture is built by `Sprite::MakeStdSprite`, whose lambda is commented `// Create a transparent layer.` and names it `Layer 1` (`src/doc/sprite.cpp` line 153-158). A `--sheet` export is therefore always RGBA when the texture colour mode is RGB, regardless of what the source did.

**Trap 2: an Indexed source makes an Indexed sheet.** `createEmptyTexture()` starts at `ColorMode::INDEXED` and only escapes to RGB if a source sprite is non Indexed or palettes differ (`doc_exporter.cpp` line 1301-1345). One Indexed source with one palette gives you a colour type 3 PNG. `--color-mode rgb` after the filename is the guard, and costs nothing when the sprite is already RGB.

Note this also means your `assets/STANDARD.md` prose and `assets/lib/validate.mjs` disagree. STANDARD.md says "Aseprite exports are fine ... an indexed PNG carrying transparency in a tRNS chunk passes", but `validate.mjs` adds `png.colorType` with `soft` defaulting to `false`, so colour type 3 is **blocking**. One of the two is wrong. Given rule 1 ("PNG-32 only. Indexed PNG and JPG are rejected on sight") the code is right and the "Aseprite exports are fine" paragraph is stale. Worth a one line fix so the artist is not told the opposite of what CI does.

## (f) Steam, itch, self compiled, and what the licence permits

**Same binary, same CLI, all three.** The CLI is built into the main executable; there is no separate tool and no build flag that removes it in the shipped builds.

- **Direct / itch**: the itch page sells "a signed macOS .dmg package" published by David Capello and Igara Studio, currently `Aseprite-v1.3.18.1-macOS.dmg`, and "Your purchase comes with a Steam key." https://dacap.itch.io/aseprite . The docs give the macOS invocation `/Applications/Aseprite.app/Contents/MacOS/aseprite --help`. **Flagged as inference, not doc confirmed**: the docs never name itch specifically. The reasoning is that itch delivers the same signed Igara .dmg, so the app bundle and its executable are identical. Verify in one second with `--version`.
- **Steam**: officially documented, with the binary path spelled out. macOS: `~/Library/Application Support/Steam/steamapps/common/Aseprite/Aseprite.app/Contents/MacOS/aseprite`. See "In the case of Steam" at https://www.aseprite.org/docs/cli/ . The `--noinapp` flag exists precisely so scripted Steam invocations do not count playtime or show you as in game, which is what you want for a per save export hook.
- **Self compiled**: same source, same `app_options.cpp`, so same flags. Build instructions at https://github.com/aseprite/aseprite/blob/main/INSTALL.md .
- **Trial**: cannot be used. "You CANNOT SAVE files with the trial version", https://www.aseprite.org/trial/ . Saving is what `--save-as` and `--sheet` do.

**Licence.** Aseprite is proprietary under the Aseprite EULA, https://github.com/aseprite/aseprite/blob/main/EULA.txt (also at https://www.aseprite.org/terms/). The source is public but not open source. Relevant clauses, verbatim:

- 2(g): "You may only compile and modify the source code of the SOFTWARE PRODUCT for your own personal purpose or to propose a contribution to the SOFTWARE PRODUCT." So a self compiled build for your own pipeline is fine.
- 2(b): "You may not distribute copies of the SOFTWARE PRODUCT to third parties."
- 1(a): install and use on "your computer running a validly licensed copy of the operating system".

**Nothing in the EULA restricts scripting, automation, batch mode, or commercial use of the art you make.** There is no clause about output, no clause about CLI use, no per seat automation limit.

**The one clause that touches your architecture is 2(b), and it matters for CI.** You cannot bake the Aseprite binary into a Docker image or a GitHub Actions runner image that anyone else can pull. That is distributing a copy. Consequences for `assets/.github/workflows/validate.yml`:

- **Keep CI validator only.** Your validator parses PNG bytes with zero dependencies and has no idea Aseprite exists. CI stays clean, which is the right design anyway.
- **Aseprite runs only on the founder's licensed Mac**, at commit time, not in CI. That is exactly the loop described below.
- If you ever want Aseprite in CI, it has to be a self hosted runner on a machine with a licensed install, and the binary must not travel with the image.

## The loop: one command from Aseprite save to validated commit

Aseprite is not installed here, so I could not execute this. It is assembled entirely from the flags and behaviours cited above.

Save as `/Users/juntaoli/todoFarm/assets/bin/export.mjs`. It reads `slots/<id>.json` and `classes.json`, so the artist never has to remember a canvas size or a sheet type, which is the "zero confusion" half of the goal.

```js
#!/usr/bin/env node
// Export one slot from Aseprite and validate it. Usage: node bin/export.mjs <slot-id>
// Run from the assets/ repo root.
import { readFileSync, existsSync } from 'fs';
import { execFileSync } from 'child_process';

const ASE = process.env.ASEPRITE ||
  '/Applications/Aseprite.app/Contents/MacOS/aseprite';

const id = process.argv[2];
if (!id) { console.error('usage: node bin/export.mjs <slot-id>'); process.exit(2); }

const slot = JSON.parse(readFileSync(`slots/${id}.json`, 'utf8'));
const cls  = JSON.parse(readFileSync('classes.json', 'utf8')).classes[slot.class];
if (!cls) { console.error(`unknown class ${slot.class}`); process.exit(2); }

const src = `src/${id}.aseprite`;
const out = `art/${id}@1x.png`;
if (!existsSync(src)) { console.error(`missing ${src}`); process.exit(2); }

// Flags that must precede the filename, then the file, then flags that act on it.
const pre  = ['-b', '--all-layers'];
const post = ['--color-mode', 'rgb'];

let layout;
if (cls.strip)            layout = ['--sheet-type', 'vertical'];
else if (cls.frames > 1)  layout = ['--sheet-type', 'rows', '--sheet-columns', '4'];
else                      layout = null;   // single frame, plain --save-as

const args = layout
  ? [...pre, src, ...post, ...layout,
     '--border-padding', '0', '--shape-padding', '0', '--inner-padding', '0',
     '--sheet', out,
     '--data', `art/${id}.json`, '--format', 'json-array',
     '--list-tags', '--filename-format', '{frame}']
  : [...pre, src, ...post, '--save-as', out];

console.log(`$ ${ASE} ${args.join(' ')}`);
execFileSync(ASE, args, { stdio: 'inherit' });
execFileSync(process.execPath, ['scripts/validate-art.mjs', out], { stdio: 'inherit' });
```

Wire it up, then the entire loop is two words:

```jsonc

```


## Bottom line

Build **one Aseprite extension with three commands** and stop there. Everything the loop needs is in the documented API; nothing requires a fork or a hack.

| Command | Menu | What it does |
|---|---|---|
| `todoFarm: New from slot` | File > Scripts | Reads `slots/*.json` + `classes.json`, shows the open slots, creates the sprite at the exact canvas size, saves it as `art/<id>@1x.png` |
| `todoFarm: Check against slot` | File > Scripts, bind to F5 | Pure-Lua pre-flight of every rule Aseprite can see, in a dialog, no terminal |
| (optional) save hook | none | `app.events:on('aftercommand', ...)` filtering `ev.name == "SaveFile"`, runs the same check automatically |

**Yes, a "check this against the slot spec" command invoked without leaving Aseprite is possible.** It can read your JSON specs directly (`json.decode` is built in, `io.open` is allowed after one permission click), and it can shell out to your existing Node validator via `io.popen` if you want the authoritative answer. Recommendation: make the in-Lua check the fast path bound to F5, and keep `node scripts/watch.mjs` as the authority, because duplicating the PNG-byte rules in Lua would drift.

Three findings that change the design, in order of importance:

1. **A fully opaque sprite exports as PNG colour type 2, and your validator rejects it.** `png_format.cpp:522` reads `color_type = (img->needAlpha() || fix_one_alpha_pixel ? PNG_COLOR_TYPE_RGB_ALPHA : PNG_COLOR_TYPE_RGB)`, and `lib/validate.mjs:147` is `add('png.colorType', m.color === 6, ...)`. Your `tile` class is ground tiles, which are exactly the assets with no transparent pixel. Verify or refute in 10 seconds with the command in "Traps" below.
2. **Aseprite's default sRGB does not write `iCCP`, so your ICC check will not false-fail.** `PngFormat::saveColorSpace` writes `png_set_sRGB` for sRGB and `png_set_iCCP` only for `ColorSpace::ICC`. But if he ever opens a PNG that carries an ICC profile, Aseprite adopts it (`png_format.cpp:402-404`) and re-emits `iCCP` on save. One Lua line fixes it: `spr:assignColorSpace(ColorSpace())`.
3. **Do not work in Indexed mode.** `png_format.cpp:533` writes `PNG_COLOR_TYPE_PALETTE` for indexed sprites, which fails `png.colorType`. Indexed mode is the natural way to enforce a master palette, and it is closed to you unless the script converts to RGB before export.

## (a) Sprite size and creating at an exact size with an exact palette

All verified in [`api/sprite.md`](https://github.com/aseprite/api/blob/main/api/sprite.md) and [`api/palette.md`](https://github.com/aseprite/api/blob/main/api/palette.md).

```lua
local spr = Sprite(16, 64, ColorMode.RGB)      -- Sprite(width, height, colorMode)
spr.width, spr.height                          -- read/write, does not resample
spr:resize(w, h)                               -- resizes layers and cels
spr:setPalette(Palette{ fromFile = "master.gpl" })
spr:assignColorSpace(ColorSpace())             -- ColorSpace() is the empty/None space
spr:saveAs("art/crop.wheat.stages@1x.png")
```

Palette file formats are **`act`, `col`, `gpl`, `hex`, `pal`**, plus any readable image format. Verified from source, not guessed: [`src/app/file/palette_file.cpp:37`](https://github.com/aseprite/aseprite/blob/main/src/app/file/palette_file.cpp) is `static const char* palExts[] = { "act", "col", "gpl", "hex", "pal" };`.

`.hex` is one hex triplet per line, so `build-manifest.mjs` can emit `assets/master.hex` from whatever you make the source of truth, and Aseprite and Node then read the same file. **Your repo has no master palette today**, only a per-class cap (`classes.json` `colors: 16|20|24|12|8`) and a magenta ban, so this is a new artefact you would be creating.

## (b) Enumerating and validating palette entries

Two independent things, and it matters which you mean.

**The document's palette swatches:**
```lua
local pal = spr.palettes[1]
for i = 0, #pal - 1 do
  local c = pal:getColor(i)                    -- Color with .red .green .blue .alpha .index
end
```

**The colours actually used in pixels**, which is what your `palette.cap` check counts. Mirror `analyse()` from `lib/validate.mjs` exactly:

```lua
local img = Image(spr)                         -- renders frame 1 of the sprite
local pc, used, n, magenta, semi, stale = app.pixelColor, {}, 0, 0, 0, 0
for it in img:pixels() do
  local v, a = it(), 0
  a = pc.rgbaA(v)
  if a == 0 then
    if pc.rgbaR(v) ~= 0 or pc.rgbaG(v) ~= 0 or pc.rgbaB(v) ~= 0 then stale = stale + 1 end
  elseif a < 255 then semi = semi + 1
  else
    local k = pc.rgbaR(v) * 65536 + pc.rgbaG(v) * 256 + pc.rgbaB(v)
    if k == 0xFF00FF then magenta = magenta + 1 end
    if not used[k] then used[k] = true; n = n + 1 end
  end
end
```

`Image:pixels()` iterator and `app.pixelColor.rgbaR/G/B/A` are documented in [`api/image.md`](https://github.com/aseprite/api/blob/main/api/image.md) and [`api/pixelcolor.md`](https://github.com/aseprite/api/blob/main/api/pixelcolor.md). This reproduces `lib/validate.mjs:109-121` exactly, including "alpha 255 only counts toward the palette".

To validate against a master palette rather than a cap, load it and diff:
```lua
local master, allowed = Palette{ fromFile = "assets/master.hex" }, {}
for i = 0, #master - 1 do
  local c = master:getColor(i)
  allowed[c.red * 65536 + c.green * 256 + c.blue] = true
end
-- any key in `used` missing from `allowed` is an off-palette colour
```

## (e) Running on save, and hooks generally

**There is no `onsave` hook, but there is a general command hook that gives you one.** `app.events` supports `'beforecommand'` and `'aftercommand'`, both carrying `ev.name` and `ev.params`; `beforecommand` additionally has `ev.stopPropagation()` ([`api/app.md`](https://github.com/aseprite/api/blob/main/api/app.md#appevents), added v1.3-rc4, apiVersion 24).

```lua
app.events:on('aftercommand', function(ev)
  if ev.name == "SaveFile" or ev.name == "SaveFileAs" then check() end
end)
```

Caveat I could not verify from docs: `aftercommand` presumably fires even when the save failed or the user cancelled the file dialog, so guard on `app.sprite.isModified == false` before trusting it.

Other event surfaces, all documented:
- `Sprite.events`: `'change'` (with `ev.fromUndo` since v1.2.41), `'filenamechange'`, `'layerblendmode'`, `'layername'`, `'layeropacity'`, `'layervisibility'` ([`api/sprite.md`](https://github.com/aseprite/api/blob/main/api/sprite.md#spriteevents)).
- `app.events`: `'sitechange'`, `'beforesitechange'`, `'fgcolorchange'`, `'bgcolorchange'`.
- `Timer{ interval=, ontick= }` ([`api/timer.md`](https://github.com/aseprite/api/blob/main/api/timer.md)) for polling. This is the cheapest way to get a live HUD: have `watch.mjs` write `art/.status.json`, and poll it every 0.5s into a background `Dialog:show{ wait=false }`, updated with `dlg:modify{ id="line1", text=... }`. Zero shelling out, one Read permission click.

There is no `Plugin:newFileFormat` hook you can attach to `.png`, because [`api/plugin.md`](https://github.com/aseprite/api/blob/main/api/plugin.md#pluginnewfileformat) says extensions "cannot overlap with an existing format that Aseprite supports (for example, 'png')".

## (f) Registering a command so it appears in the UI

**Two ways, and the simple one is genuinely enough.**

**Way 1, no extension at all.** Drop a `.lua` file in `~/Library/Application Support/Aseprite/scripts/` and it appears in **File > Scripts**, labelled with the filename minus extension, and it is bindable to a key. Verified in source: [`src/app/app_menus.cpp:375`](https://github.com/aseprite/aseprite/blob/main/src/app/app_menus.cpp) is `rf.includeUserDir("scripts")`, and `loadScriptsSubmenu` builds one `AppMenuItem(get_file_title(fn), CommandId::RunScript(), params)` per `.lua`. Subdirectories become submenus and dotfiles are skipped. `File > Scripts > Rescan Scripts Folder` is the `Refresh` command ([`data/gui.xml:730-733`](https://github.com/aseprite/aseprite/blob/main/data/gui.xml)). This is documented for users at [aseprite.org/docs/scripting](https://www.aseprite.org/docs/scripting/).

**Way 2, an extension**, when you want named commands, persisted settings, and a startup hook:

```lua
function init(plugin)
  plugin:newCommand{
    id      = "TodoFarmCheckSlot",
    title   = "todoFarm: Check against slot",
    group   = "file_scripts",              -- the File > Scripts group

    onenabled = function() return app.sprite ~= nil end,

end
```

## The script security model, which you will hit immediately

Verified from [`src/app/script/security.cpp`](https://github.com/aseprite/aseprite/blob/main/src/app/script/security.cpp):

- Gated behind a permission dialog: `io.open`, `io.popen`, `io.lines`, `io.input`, `io.output`, `os.execute`, `os.remove`, `os.rename`, `package.loadlib` (lines 65-74).
- **Removed entirely**: `os.exit` and `os.tmpname` (line 280). Do not write code that calls them.
- Access modes are Read, Write, Execute, LoadLib, Full. Ticking "Don't show again" persists to config under section `script_access`, keyed by the **SHA1 of the script's filename** (`get_key(script)` where `script` comes from `lua_Debug.source`). Moving or renaming the script revokes the grant; editing its contents does not.
- **`ask_access` only prompts when `App::instance()->context()->isUIAvailable()`** (line 308). In `-b`/`--batch` there is no prompt and access is granted. That is why the CLI path is frictionless and the GUI path costs one click per script per mode.

```lua
local ASSETS = "/Users/juntaoli/todoFarm/assets"

local function slurp(p)
  local f = io.open(p, "rb"); if not f then return nil end
  local s = f:read("*a"); f:close(); return s
end

local function readJson(p)
  local s = slurp(p); if not s then return nil end
  local ok, v = pcall(json.decode, s)
  if ok then return v end
end

local function slotIdOf(spr)
  if not spr.filename or spr.filename == "" then return nil end
  return (app.fs.fileTitle(spr.filename):gsub("@1x$", ""))   -- "crop.wheat.stages@1x" -> id
end

local function check()
  local spr = app.sprite
  if not spr then return { "no sprite open" } end

  local root = readJson(app.fs.joinPath(ASSETS, "classes.json"))
  if not root then return { "cannot read " .. ASSETS .. "/classes.json" } end

  local id = slotIdOf(spr)
  if not id then return { "sprite has never been saved, so it has no slot id" } end

  local slot = readJson(app.fs.joinPath(ASSETS, "slots", id .. ".json"))
  if not slot then
    return { "FAIL  no slot with id \"" .. id .. "\"",
             "      filename must be <slot-id>@1x.png" }
  end
  local cls = root.classes[slot.class]
  if not cls then return { "FAIL  unknown class \"" .. tostring(slot.class) .. "\"" } end

  -- canvasOf() in lib/validate.mjs stacks strips VERTICALLY
  local wantW = cls.w
  local wantH = cls.strip and (cls.h * cls.frames) or cls.h

  local out, n = { id .. "   " .. slot.class .. " / " .. slot.status }, 1
  local function line(ok, s) n = n + 1; out[n] = (ok and "ok    " or "FAIL  ") .. s end

  line(spr.width == wantW and spr.height == wantH,
       ("canvas %dx%d, want %dx%d"):format(spr.width, spr.height, wantW, wantH))
  line(spr.colorMode == ColorMode.RGB, "colour mode is RGB")

  local img = Image(spr)
  local pc, used, colors, magenta, semi, stale, opaque = app.pixelColor, {}, 0, 0, 0, 0, 0
  for it in img:pixels() do
    local v = it()
    local a = pc.rgbaA(v)
    if a == 0 then
      if pc.rgbaR(v) ~= 0 or pc.rgbaG(v) ~= 0 or pc.rgbaB(v) ~= 0 then stale = stale + 1 end
    elseif a < 255 then
      semi = semi + 1
    else
      opaque = opaque + 1
      local k = pc.rgbaR(v) * 65536 + pc.rgbaG(v) * 256 + pc.rgbaB(v)
      if k == 0xFF00FF then magenta = magenta + 1 end
      if not used[k] then used[k] = true; colors = colors + 1 end
    end
  end

  line(semi == 0,    ("binary alpha (%d semi-transparent px)"):format(semi))
  line(stale == 0,   ("transparent px are RGB 0,0,0 (%d stale)"):format(stale))
  line(colors > 0 and colors <= cls.colors,
       ("%d colours, cap %d"):format(colors, cls.colors))
  line(magenta == 0, ("no #FF00FF sentinel (%d px)"):format(magenta))
  line(opaque / (spr.width * spr.height) > 0.03,
       ("%d%% opaque, not blank"):format(math.floor(100 * opaque / (spr.width * spr.height))))
  -- warning only: a fully opaque sprite exports as PNG colour type 2, not 6
  line(opaque < spr.width * spr.height,
       "has at least one transparent pixel (else PNG is colour type 2)")

  return out
end

function init(plugin)
  plugin:newCommand{
    id = "TodoFarmCheckSlot",
    title = "todoFarm: Check against slot",
    group = "file_scripts",
    onenabled = function() return app.sprite ~= nil end,
    onclick = function()
      app.alert{ title = "todoFarm", text = check(), buttons = "OK" }
    end,
  }
end
```

## Adversarial fact-check

## Corrections

**1. Finding #1 is wrong about its mechanism, and the test it proposes cannot detect the thing it is testing for.** This is the report's own top-ranked finding and it drives a proposed edit to `lib/validate.mjs`, so it matters most.

The briefing says "a fully opaque sprite exports as PNG colour type 2." The quoted line at [`png_format.cpp:522`](https://github.com/aseprite/aseprite/blob/main/src/app/file/png_format.cpp) is real and quoted correctly, but the report never resolved `needAlpha()` (it says so in its own "not verified" list). Following the chain:

- `FileAbstractImage::needAlpha()` is `{ return m_sprite->needAlpha(); }` ([`src/app/file/file.cpp:111`](https://github.com/aseprite/aseprite/blob/main/src/app/file/file.cpp))
- `Sprite::needAlpha()` returns `!isOpaque()` for RGB ([`src/doc/sprite.cpp:228-235`](https://github.com/aseprite/aseprite/blob/main/src/doc/sprite.cpp))
- `Sprite::isOpaque()` is, in full: `Layer* bg = backgroundLayer(); return (bg && bg->isVisible());` (`sprite.cpp:222-226`)

So the switch is **"does this sprite have a visible Background layer"**, which has nothing to do with pixel opacity. Painting every pixel of a normal layer still gives colour type 6. And a script-created sprite can never trip it: the Lua `Sprite()` constructor calls `Sprite::MakeStdSprite` (`sprite_class.cpp:139`), whose layer factory is commented `// Create a transparent layer.` and builds a plain `LayerImage` (`sprite.cpp:153-158`).

The real triggers are three, none of them named in the briefing:
- File > New with any Background other than Transparent: `if (bgColor.getType() != app::Color::MaskType) layerImage->configureAsBackground();` ([`cmd_new_file.cpp:219-222`](https://github.com/aseprite/aseprite/blob/main/src/app/commands/cmd_new_file.cpp))
- Layer > Convert Layer to Background
- Opening a PNG that is *already* colour type 2: `if (!m_seq.has_alpha && !m_avoidBackgroundLayer) m_seq.layer->configureAsBackground();` (`file.cpp:892-895`)

The Traps-1 command is therefore circular. I checked the file it names: `placeholders/tile.terrain.grass_a@1x.png` is already `colorType 6` (read locally, byte 25). It loads with alpha, gets no Background layer, and saves back as 6 no matter what. Running it will print `6` and confirm nothing. A test that could actually falsify the claim has to create the Background layer first (File > New with white background, or Layer > Convert Layer to Background), then save and read byte 25.

Two downstream consequences:
- The Lua guard `line(opaque < spr.width * spr.height, ...)` is checking the wrong quantity. The correct predicate is `spr.backgroundLayer == nil or not spr.backgroundLayer.isVisible` (`Sprite.backgroundLayer` is a documented read-only property, [sprite.md](https://github.com/aseprite/api/blob/main/api/sprite.md)).
- The suggested fix to `lib/validate.mjs:147` ("accept type 2 when `semi === 0 && clear === 0`") loosens the validator in exactly the case where transparency was destroyed by a Background layer, which is the case you want it to catch.

**2. `group = "file_scripts"` does not put a command inside File > Scripts.** The briefing's table, its inline comment (`-- the File > Scripts group`), and its "Way 2" prose all place the extension commands there.

For any `gui.xml` element carrying a `group=` attribute, `AppMenus::convertXmlelemToMenuitem` sets `m_groups[group].menu = menu; m_groups[group].end = menuitem;` ([`app_menus.cpp:735-737` and `777-780`](https://github.com/aseprite/aseprite/blob/main/src/app/app_menus.cpp)), where `menu` is the **parent** menu and the tagged item is only an insertion anchor. The re-add loop then does `insertIndex = menu->getChildIndex(group.end); ... menu->insertChild(++insertIndex, item);` (`app_menus.cpp:411-423`). `gui.xml:730` tags `<menu id="scripts_menu" text="@.file_scripts" group="file_scripts">`, whose parent is the File menu, so the command lands in **File**, immediately after the "Scripts" submenu entry. The `addMenuGroup()` function at `app_menus.cpp:587` does use `menuItem->getSubmenu()`, but that path serves `Plugin:newMenuGroup{}`, not gui.xml groups.

**3. The `aftercommand` guard breaks on the export path, and the command filter misses it.** `SaveFileCopyAsCommand::onExecute` passes `MarkAsSaved::Off` ([`cmd_save_file.cpp:378`](https://github.com/aseprite/aseprite/blob/main/src/app/commands/cmd_save_file.cpp)); `document->markAsSaved()` runs only under `MarkAsSaved::On` (lines 228, 260-261). So File > Export leaves `isModified` true, and the proposed guard `app.sprite.isModified == false` suppresses the check precisely when the PNG was just written. Separately, the filter `ev.name == "SaveFile" or ev.name == "SaveFileAs"` omits `SaveFileCopyAs`, which is the command an artist working in `.aseprite` actually uses to produce `art/<id>@1x.png`.

The briefing's stated caveat is now answerable rather than presumed. `Context::executeCommand` fires `AfterCommandExecution(ev)` after `command->execute()` returns ([`context.cpp:190-205`](https://github.com/aseprite/aseprite/blob/main/src/app/context.cpp)). It therefore **does** fire on a cancelled Save As dialog, and it also fires when `beforecommand` cancelled the command. It does **not** fire when the command was disabled (early `return` at line 202) or when a `base::Exception` escapes.

**4. Issue 5058 is mischaracterized.** Its title is "New app mode for the purpose of interacting with the active window on CLI", and it asks for a CLI mode in which `app.sprite` resolves to the active window's sprite. It is not "an open request for exactly that" (IPC into a running instance). The conclusion the briefing draws from it (treat CLI scripting as out of process, no documented flag exists) is still correct on the CLI docs alone, but the citation does not support the claim as written. The issue also surfaces something the briefing omits: in `-b` there is no active sprite unless a file is passed on the command line.

**5. `%q` is Lua quoting, not shell quoting.** The `io.popen` snippet builds a shell command with `("cd %q && %q ... %q"):format(...)`. Per the Lua manual, `%q` writes a string "in a format that can be safely read back by the Lua interpreter", escaping quotes, newlines, zeros and backslashes. It does not escape `$`, backticks or `!`, and it escapes a newline as backslash-newline, which a shell reads as a line continuation. For the fixed paths shown it happens to work, but it is presented as ready-to-run code and is not a shell-quoting function.

**6. Two small citation slips.** `ask_access`'s UI check is at `security.cpp:313`, not 308 (the function itself starts at 306). And the four-line CLI block is verbatim `aseprite --help` output, whose strings live in [`src/app/cli/app_options.cpp:29, 31, 146, 148-151`](https://github.com/aseprite/aseprite/blob/main/src/app/cli/app_options.cpp) (including the embedded newline in the `script-param` description), not the prose at aseprite.org/docs/cli that it is attributed to. The flags themselves are all real and spelled correctly.

**7. "Aseprite's default sRGB" is a user preference, not a constant.** `Sprite_new` ends with `spec.setColorSpace(get_working_rgb_space_from_preferences())` ([`sprite_class.cpp:130`](https://github.com/aseprite/aseprite/blob/main/src/app/script/sprite_class.cpp)). If the working RGB space preference is set to an ICC profile, even a script-created sprite emits `iCCP`. The briefing frames inherited profiles from opened files as the only ICC risk.

## Omissions

7. **The design has an unstated Aseprite 1.3 floor.** `json.decode` is "Since Aseprite v1.3-rc5" ([json.md](https://github.com/aseprite/api/blob/main/api/json.md)), `app.events` command hooks are v1.3-rc4 / apiVersion 24, `Timer` is v1.3-rc1 / apiVersion 21 ([Changes.md](https://github.com/aseprite/api/blob/main/Changes.md)). None of this is stated.
8. **`placeholders/` and `manifest.json` are gitignored** in `/Users/juntaoli/todoFarm/assets/.gitignore`. The Traps-1 test file is a generated, uncommitted artifact, and the suggestion that `build-manifest.mjs` emit `assets/master.hex` puts a file Aseprite must read at startup behind a generator whose sibling output is deliberately not committed.
9. **macOS TCC is a second permission layer.** `/Users/juntaoli/todoFarm` is not protected, so the paths shown are fine, but the user's other repos live under `~/Documents`, which is. Moving the assets repo there would add a system consent prompt on top of Aseprite's own.
10. **The loop stops at "validated".** The stated goal is "validated **and committed**"; nothing in the design touches the commit half.

## Bottom line

Six changes, in value order. The first three are the ones that will actually bite this repo, and all three are verified against Aseprite's own source.

1. **Add `src/*.aseprite` as the committed source of truth, keep `art/*.png` as a generated-but-committed artifact, and add a hash stamp so the two can never silently drift.** Right now `scaffold.mjs` writes a PNG and the artist is expected to draw into it and save PNG over PNG. 2. **Add an Aseprite Lua preflight to the export step.** Two of the validator's hard-blocking rules fire on perfectly reasonable Aseprite settings, and the error message does not tell the artist which Aseprite setting to change. Details in "Three landmines" below.
3. **Fix the contradiction in `STANDARD.md`.** It says indexed PNG is "rejected on sight" in rule 1 and that indexed PNGs "pass" three paragraphs later. The code rejects them. An artist who works in Indexed mode (the natural mode for a hard colour cap) hits this on their first save.

## (a) Source files versus exports, and how people stop them drifting

**What practitioners do.** The dominant pattern is: commit both, keep them adjacent, and generate the export rather than hand-saving it.

- Cobalt Core (Rocket Rat Games) keeps one `.ase` per character and runs a script that exports into a sibling folder named after the character, next to the source: `riggs.ase` beside `riggs/riggs_neutral_0.png`. Described by dev Ben Driscoll in ["Using the Aseprite CLI to Export Sprites"](https://medium.com/@daisyowl/using-the-aseprite-cli-to-export-sprites-3d79ac4e7b91). Flagged: Medium returned HTTP 403 to my fetcher, so I have this via search snippets only, not the full text.
- Nick Rodgers' animation pipeline writeup recommends mirroring the art source tree and the game resource tree so "finding the source for an exported asset" is mechanical ([Medium](https://medium.com/@nicholasRodgers/animation-naming-conventions-and-folder-structures-for-game-development-2e87f3d0668f), also 403 to my fetcher, search snippet only).
- The stated reason people commit the PNG rather than only the source: tooling can diff and preview PNG and cannot preview `.aseprite` ([Game Dev Dungeon, auto-export plugin writeup](https://justalexi.com/en/posts/2021-10-19-unity-aseprite-exporter/), [justalexi/unity_aseprite_exporter](https://github.com/justalexi/unity_aseprite_exporter)).
- Aseprite's own docs say to keep the source: exports are "for publishing purposes or to use your assets in a game", and you "keep the original .aseprite in a safe place to modify the sprite when it's required" ([aseprite.org/docs/files](https://www.aseprite.org/docs/files/)).

**Drift is real and documented.** A user reported sprite sheet exports showing "an old iteration" of the art, traced to a specific combination of Visible Layers plus All Frames plus Split Tags ([community.aseprite.org/t/export-sprite-sheet-showing-the-wrong-sprites/6004](https://community.aseprite.org/t/export-sprite-sheet-showing-the-wrong-sprites/6004)). Manual export UI state is a drift source in its own right, which is an argument for CLI export only.

**Recommendation for this repo.** Commit both. `src/<slot-id>.aseprite` and `art/<slot-id>@1x.png`, flat, same basename, so the mapping needs no rule. Add `art/.exported.json` recording a hash pair per slot and make `npm run check` fail on any mismatch. Git LFS is not worth it at this size: these files are single-digit kilobytes. LFS `lockable` exists for unmergeable binaries (`*.psd filter=lfs diff=lfs merge=lfs -text lockable`) but its value is preventing two artists colliding, and there is one artist.

Tested drift guard, all four failure cases exercised on this machine:

```js
// scripts/drift.mjs  (zero-dependency, Node >= 18)
import { readFileSync, readdirSync, existsSync, writeFileSync, mkdirSync } from 'fs';
import { createHash } from 'crypto';

const STAMP = 'art/.exported.json';
const sha = f => createHash('sha256').update(readFileSync(f)).digest('hex').slice(0, 16);
const load = () => existsSync(STAMP) ? JSON.parse(readFileSync(STAMP, 'utf8')) : {};

export function record(id) {
  const s = load();
  s[id] = { src: sha(`src/${id}.aseprite`), png: sha(`art/${id}@1x.png`) };
  mkdirSync('art', { recursive: true });
  writeFileSync(STAMP, JSON.stringify(s, null, 2) + '\n');
}

export function drift() {
  const stamp = load(), bad = [];
  const srcs = existsSync('src')
    ? readdirSync('src').filter(f => f.endsWith('.aseprite')).map(f => f.replace(/\.aseprite$/, ''))
    : [];
  for (const id of srcs) {
    const png = `art/${id}@1x.png`;
    if (!existsSync(png))              { bad.push([id, 'source exists, never exported']); continue; }
    const rec = stamp[id];
    if (!rec)                          { bad.push([id, 'exported outside the pipeline, no stamp']); continue; }
    if (rec.src !== sha(`src/${id}.aseprite`)) bad.push([id, 'source edited since last export']);
    else if (rec.png !== sha(png))             bad.push([id, 'PNG edited by hand, source no longer matches']);
  }
  for (const f of (existsSync('art') ? readdirSync('art') : []))
    if (f.endsWith('@1x.png')) {
      const id = f.replace(/@1x\.png$/, '');
      if (!srcs.includes(id) && stamp[id]) bad.push([id, 'source deleted, PNG orphaned']);
    }
  return bad;
}

if (import.meta.url === `file://${process.argv[1]}`) {
  const bad = drift();
  if (!bad.length) { console.log('art matches src, nothing stale'); process.exit(0); }
  for (const [id, why] of bad) console.log(`STALE  ${id}  ${why}`);
  console.log(`\n${bad.length} stale. Run: npm run export`);
  process.exit(1);
}
```

```
--- after editing source ---   STALE  icon.coin  source edited since last export        exit=1
--- hand-edited png ---        STALE  icon.coin  PNG edited by hand, source no longer matches   exit=1
--- orphaned png ---           STALE  icon.coin  source deleted, PNG orphaned          exit=1
```

## (b) Naming and folders that survive a few hundred assets

The repo's `<class>.<family>.<variant>[.<state>]` scheme is already better than most. Evidence that it is the right shape:

## (d) Placeholders, and the magenta versus grey box claim

**The claim is correct, and there is a better quote for it than the engine convention.** Josh Sawyer (Obsidian, *Pentiment*): "Placeholder assets in a game should look obnoxiously temporary, so obvious that no one would mistake it for the final asset," and, decisively for the grey-box comparison, **"If you use a temp asset that seems passable, it may stay there."** His studio used "hot pink versions of characters" and the CEO's head. Dr. Miko Charbonneau (*The Spirit Lift*): "Placeholder assets should be obviously not final so you don't 'accidentally' leave them in." ([Kotaku, 2026](https://kotaku.com/crimson-desert-ai-art-placeholder-game-devs-share-assets-images-genai-2000681053))

That is the mechanism, stated by a shipping developer: a plausible placeholder is not merely harder to spot, it is *survivable*, and survivable placeholders ship. A grey box has exactly the property that makes it dangerous.

**The engine convention corroborates it.** Unity's manual: "The default error shader is magenta (bright pink)," used "when there's a problem with that object's material or shader; for example, if no material is assigned" ([docs.unity3d.com](https://docs.unity3d.com/6000.3/Documentation/Manual/shader-error.html)). Minecraft: "The most known, the missing texture, is a texture composed of a black and magenta checkerboard, and turns up anytime a texture or model reference could not be correctly resolved" ([minecraft.wiki](https://minecraft.wiki/w/Placeholder_texture)). Unity even reserves a *second* unmistakable colour for a different state: "The loading shader is cyan (bright blue)."

The repo's `#FF00FF`-is-a-blocking-colour rule is the sharpest version of this idea I have seen written down. The sentinel is not merely conspicuous, it is *unforgeable*: because real art can never contain it, a magenta pixel in a shipped build is proof of a missing asset rather than a judgement call. Keep it exactly as is.

**The one real counter-argument, worth knowing so you can decide deliberately.** Unity's own blog argues placeholder art corrupts playtest feedback: "A player's perception of responsiveness, weight, and overall game feel is affected by what they see on the screen," and testers cannot "accurately evaluate the physics code driving it without being influenced by the lack of visual polish." Their stated boundary is that greybox "remains appropriate for isolated mechanics testing or very early concepts" but becomes a problem "when you start gathering playtest feedback on the holistic feel of your game" ([unity.com/blog/placeholder-asset-problem](https://unity.com/blog/placeholder-asset-problem)).

Note the source's own incentive: two of its three recommended alternatives are AI generation and the Unity Asset Store. The argument is still sound within its scope, and the scopes do not actually conflict:

- **Placeholder for the developer, so a gap cannot ship:** magenta, always. This is the repo's case.
- **Placeholder for a playtester, when you want honest feel feedback:** a magenta checkerboard field will dominate the session.

If you ever put the game in front of an outside playtester, the resolution is a build flag, not a change to the sentinel: `npm run placeholders -- --neutral` emitting flat mid-grey silhouettes at the correct canvas size, never committed, never the default, and blocked in the publish workflow. The sentinel stays the thing the validator enforces.

## (e) Contact sheets and style review with no art director

The written-standard half of this problem the repo has already solved, and the OpenGameArt consensus is exactly the list `STANDARD.md` already covers: palette, base sizes, perspective and scale, outlines, dithering, shading, animation frame counts, with the caveat that "a style guide is a guide book not a law book" ([opengameart.org forum](https://opengameart.org/forumtopic/maintaining-a-consistent-art-style)). The reference implementations to steal specifics from are the LPC style guide ([lpc.opengameart.org](https://lpc.opengameart.org/static/lpc-style-guide/styleguide.html), [ElizaWy/LPC wiki](https://github.com/ElizaWy/LPC/wiki/Style-Guide), [OpenGameArt/LPC-Style-Guide](https://github.com/OpenGameArt/LPC-Style-Guide)). LPC pins the same things the repo does and two it does not: explicit row order for directional sheets ("back, left, front, right"), and a stated lighting rule ("lighting should primarily come from above, and if there is any side directionality, it should come from the left"). Note LPC's row order differs from this repo's `down, up, left, right` in `char.player.walk.json`. That is fine, but it means anyone importing LPC-shaped art will get it wrong, so the brief should keep saying it out loud, which it does.

The review half is `sheet.mjs`, and its header comment already states the correct rationale. Two upgrades grounded in what the sources say drift actually looks like ("outlines drifting, palettes shifting, shading styles changing"):

1. **A world strip, not just a card grid.** Drift is an adjacency phenomenon. Render one row of every `tile` at 1x butted edge to edge, and one row of every `prop` standing on a grass tile, at the game's real zoom. A card grid with 12px of padding around each sprite hides exactly the mismatch you are looking for. This is what the LPC and Universal LPC generator demos do: assemble the parts and look at the assembled thing.
2. **A palette rail.** You already compute `r.palette` sorted by frequency in `validate.mjs`. Render every slot's palette as a swatch strip under its card, sorted by luminance, and the "palette drift" warning tier in `STANDARD.md` becomes visible instead of numeric. Two greens that are 3% apart are invisible as hex and obvious as adjacent swatches.

# WATCH

# Bottom line

**Watch the directory, never the file. Ignore `eventType`. Debounce ~120 ms, then settle on `stat`, then confirm the PNG's `IEND` trailer before you read. Print an ANSI-redrawn board to a pinned terminal; do not build the loop on notifications.**

Concretely, for this repo:

1. `fs.watch(artDir, { recursive: true })` — one FSEvents handle, works on macOS, reports `subdir/file.png` relative paths.
2. Throw away the `eventType` string. On macOS a directory watch reports a plain in-place write as `'rename'`. I confirmed this on your machine.
3. Never `fs.watch(theFile)`. The moment anything replaces the file via rename, that watcher goes permanently silent (Node's "Inodes" caveat). I confirmed this too.
4. Aseprite does **not** do atomic saves. It `fopen(path,"wb")`s the destination directly, so it truncates-then-grows in place. Your watcher will see the file at size 0 and at every intermediate size. This is the real hazard, not the rename problem.
5. Gate the read on: debounce → `size+mtimeNs+ino` stable across 2 polls → `fstat`/read/`fstat` on the same fd → PNG signature at head **and** the 12-byte `IEND` trailer at tail. Then SHA-1 dedupe so duplicate events and metadata touches cost nothing.
6. Notifications: `osascript` only, never `terminal-notifier` (it is an app bundle you'd have to install — that is a dependency). Use it for FAIL only, as a secondary channel. It is unreliable by design: macOS drops it silently when your terminal lacks Notifications permission, and `osascript` still exits 0.

# (a) What macOS actually does

## Backend, from the source

Node docs, [fs.watch Availability](https://nodejs.org/docs/latest/api/fs.html#availability):

> On macOS, this uses `kqueue(2)` for files and `FSEvents` for directories.

Verified against libuv, which is where this is decided — [`src/unix/kqueue.c`](https://github.com/libuv/libuv/blob/v1.x/src/unix/kqueue.c), `uv_fs_event_start`:

```c
  if (uv__fstat(fd, &statbuf))
    goto fallback;
  /* FSEvents works only with directories */
  if (!(statbuf.st_mode & S_IFDIR))
    goto fallback;
```

## `eventType` is noise, not signal

The single most useful thing I found. Same file, `uv__fs_event`:

```c
  if (fflags & (NOTE_ATTRIB | NOTE_EXTEND))
    events = UV_CHANGE;
  else
    events = UV_RENAME;
```

`NOTE_WRITE` is not in the `UV_CHANGE` branch, so a plain write can surface as `'rename'`. And on the FSEvents path it is worse. Measured on **macOS 26.5.1 / Node v25.6.1**, watching a directory with `{recursive:true}`:

```
   11ms DIR recursive  change  watchprobe-HlOcFl     <- startup burst, nothing happened yet
   11ms DIR recursive  rename  nested
   11ms DIR recursive  rename  sprite.png
--- A: in-place truncate+write, 3 chunks ---
  151ms FILE           change  sprite.png            <- kqueue, per-file watch
  161ms DIR recursive  rename  sprite.png            <- FSEvents says "rename" for a write
  211ms FILE           change  sprite.png
  273ms FILE           change  sprite.png
  334ms DIR recursive  rename  sprite.png
--- B: atomic save (write tmp, rename over) ---
  937ms FILE           rename  sprite.png
  946ms DIR recursive  rename  sprite.png.tmp
  946ms DIR recursive  rename  sprite.png
  946ms DIR recursive  rename  sprite.png
--- C: in-place write AFTER the atomic replace ---
 1544ms DIR recursive  rename  sprite.png            <- FILE watcher is DEAD, no event
--- D: nested file create+write ---
 2152ms DIR recursive  rename  nested/deep.png
--- E: pure metadata touch (utimesSync only) ---
 2755ms DIR recursive  rename  sprite.png            <- no content changed at all
```

Every directory event is `'rename'`. Branching on it is a bug.

## The four real problems, each confirmed

**Duplicates.** One 3-chunk write produced 3 `FILE` events and 2 `DIR` events. Root cause is that a write raises `NOTE_EXTEND` and `NOTE_WRITE` separately, and libuv re-arms `EV_ONESHOT` after each. Long-standing and won't-fix: [nodejs/node#3042](https://github.com/nodejs/node/issues/3042), [nodejs/node#21902](https://github.com/nodejs/node/issues/21902). Chokidar's README lists "events are not reported twice" as a reason it exists: <https://github.com/paulmillr/chokidar>.

**Metadata-only events.** Step E fired an event for a pure `utimes`. Known bug: [nodejs/node#49916](https://github.com/nodejs/node/issues/49916), "on MacOS, `fs.watch` emits `change` event when access timestamp is updated". A content hash is the only clean fix.

**Startup burst.** 3 events at 11 ms before any write. libuv documents it: "On macOS, events collected by the OS immediately before calling `uv_fs_event_start` might be reported to the callback" — <https://docs.libuv.org/en/v1.x/fs_event.html>.

**The atomic-save / inode trap.** Step C is the important one. After a temp-file-plus-rename, the per-file watcher emitted nothing ever again, silently. Node documents why ([Inodes caveat](https://nodejs.org/docs/latest/api/fs.html#inodes)):

> On Linux and macOS systems, `fs.watch()` resolves the path to an inode and watches the inode. If the watched path is deleted and recreated, it is assigned a new inode. The watch will emit an event for the delete but will continue watching the *original* inode. Events for the new inode will not be emitted. This is expected behavior.

This is why you watch the directory. The directory's inode is stable across all of it.

## Recursive on macOS: yes

libuv: "Currently the only supported flag is `UV_FS_EVENT_RECURSIVE` and only on OSX and Windows" (<https://docs.libuv.org/en/v1.x/fs_event.html>). Node's changelog confirms macOS predates Linux here — v19.1.0 "Added recursive support for Linux, AIX and IBMi". Step D above proves it works and gives you the subdirectory in the path (`nested/deep.png`).

Caveat worth knowing: libuv sets FSEvents latency to 0.05 s with `kFSEventStreamCreateFlagNoDefer | kFSEventStreamCreateFlagFileEvents` ([`src/unix/fsevents.c`](https://github.com/libuv/libuv/blob/v1.x/src/unix/fsevents.c) lines 340/354). So ~50 ms of OS-level coalescing already happens before Node sees anything.

## `fs.watchFile` — the fallback, and only that

Polls `stat` by **path**, so it survives everything that kills `fs.watch`. Measured:

```
566ms  watchFile size=1234 ino=99220450 prevIno=99220450   (in-place write)
1170ms watchFile size=4321 ino=99220458 prevIno=99220450   (atomic replace — still fires)
1973ms watchFile size=0    ino=0        prevIno=99220458   (delete)
2576ms watchFile size=77   ino=99220463 prevIno=99220458   (recreate — still fires)
```

Default `interval` is **5007 ms**, and Node says outright: "Using `fs.watch()` is more efficient than `fs.watchFile` … `fs.watch` should be used instead … when possible." Use it only if the art dir ever lives on a network share or a Docker/VM mount, where `fs.watch` is explicitly unreliable.

# (b) The debounce + settle pattern

Two stages, because neither alone is sufficient. Debounce collapses the burst; settle proves the writer finished.

```js
const DEBOUNCE_MS       = 120;  // collapse one save's event burst
const SETTLE_POLL_MS    = 40;
const SETTLE_STABLE_N   = 2;    // consecutive identical stats == quiet
const SETTLE_TIMEOUT_MS = 5000;

const timers = new Map();   // rel -> Timeout
function touch(rel) {
  clearTimeout(timers.get(rel));
  timers.set(rel, setTimeout(() => { timers.delete(rel); enqueue(rel); }, DEBOUNCE_MS));
}

// One run per file at a time. A save landing mid-validation queues, never races.
const inflight = new Map();
function enqueue(rel) {
  const prior = inflight.get(rel) ?? Promise.resolve();
  const next = prior.then(() => process_(rel)).catch(e => log(`ERR ${rel}: ${e.message}`));
  inflight.set(rel, next);
  next.finally(() => { if (inflight.get(rel) === next) inflight.delete(rel); });
}
```

120 ms is chosen against measurement, not vibes: my chunked write spread events over 151→334 ms with ~60 ms gaps, and FSEvents already coalesces at 50 ms. For reference, chokidar's `awaitWriteFinish` defaults to a 2000 ms stability threshold with a 100 ms poll — far too slow for a save-validate loop, which is exactly why the structural check below lets you go faster.

Then dedupe by content, which kills residual duplicates *and* metadata-only events in one line:

```js
const hash = crypto.createHash('sha1').update(buf).digest('hex');
if (lastHash.get(rel) === hash) return;   // duplicate event, or a utimes touch
lastHash.set(rel, hash);
```

Prime `lastHash` with a full scan at startup and the FSEvents startup burst becomes a no-op for free.

# (c) Aseprite's save on macOS

**Not atomic. It writes the destination file in place.** From `main`:

- [`src/app/file/png_format.cpp:494`](https://github.com/aseprite/aseprite/blob/main/src/app/file/png_format.cpp#L494) — `FileHandle handle(open_file_with_exception_sync_on_close(fop->filename(), "wb"));`
- [`src/app/file/ase_format.cpp:230`](https://github.com/aseprite/aseprite/blob/main/src/app/file/ase_format.cpp#L230) — identical call.
- `fop->filename()` is the user's target path. No temp path, no `rename`. I grepped `src/app/file/file.cpp`, `src/app/commands/cmd_save_file.cpp`, `gif_format.cpp`, `cmd_export_sprite_sheet.cpp` and `file_formats_manager.cpp` for `temp_file|move_file|::rename(|.tmp` — zero hits in all five.
- The "sync_on_close" name overpromises on macOS. [`aseprite/laf` `base/file_handle.cpp`](https://github.com/aseprite/laf/blob/main/base/file_handle.cpp), `close_file_and_sync`, is `fflush(file)` then `fclose(file)`; the actual flush-to-device (`FlushFileBuffers`) is inside `#if LAF_WINDOWS`. **No `fsync`, no `F_FULLFSYNC` on macOS.**

So what a watcher observes on ⌘S:

1. `"wb"` truncates → the file is momentarily **0 bytes and still a valid path**.
2. libpng writes row by row (`fop->setProgress` per row), so multiple `NOTE_WRITE`/`NOTE_EXTEND` fire during one save. A 4-chunk write in my rig produced 4 kqueue events.
3. `fclose`. Inode never changes.

Two consequences. Good news: a per-file `fs.watch` would actually survive Aseprite, because the inode is stable. Bad news: **any watcher that reads on the first event reads a truncated or empty PNG.** That is the bug you would ship. It is also why I still say watch the directory — you also need creates for new slots, and you should not depend on Aseprite never changing this.

*Not verified:* Aseprite 1.3.x binary behavior on your machine (it isn't installed here — `ls /Applications | grep -i aseprite` was empty), and I did not audit every one of the ~40 format writers, only the five above. If you ever route exports through a different tool that *does* rename-save, the directory-watch design already covers it.

# (d) Detecting a fully-written file without a race

There is no lock to observe. Aseprite's `fopen` takes no `flock`/`O_EXLOCK`, so advisory locking gives you nothing. You need three guards stacked:

**1. Stat settle.** `size + mtimeNs + ino` identical across 2 polls, 40 ms apart. Use `{ bigint: true }` — `mtimeNs` only exists on `BigIntStats` and gives nanosecond resolution, so a fast second write inside the same millisecond can't hide.

**2. Bracketed read.** `fstat` the fd, read, `fstat` again, on the *same* descriptor. If size or `mtimeNs` moved, or `buf.length !== size`, a write landed mid-read — discard and loop. Using the fd, not the path, means a replacement can't fool you.

**3. Structural completeness — the one that makes it exact for PNG.** A PNG is complete iff it starts with the signature and ends with the `IEND` chunk:

```js
const PNG_SIG  = Buffer.from([0x89,0x50,0x4e,0x47,0x0d,0x0a,0x1a,0x0a]);
const PNG_IEND = Buffer.from([0x00,0x00,0x00,0x00,0x49,0x45,0x4e,0x44,0xae,0x42,0x60,0x82]);

function isCompletePng(b) {
  return b.length >= 20
      && b.subarray(0, 8).equals(PNG_SIG)
      && b.subarray(b.length - 12).equals(PNG_IEND);
}
```

Per the [W3C PNG Third Edition](https://www.w3.org/TR/png-3/): §5.2 gives the signature as `89 50 4E 47 0D 0A 1A 0A`; §11.2.4 gives IEND as a zero-length chunk with type bytes `49 45 4E 44`, required last. I verified the CRC by computing CRC-32 over `"IEND"` → `0xae426082`, and by dumping the last 12 bytes of four unrelated PNGs on this Mac — all `0000000049454e44ae426082`.

This is what buys you the low latency. Because a truncated PNG *cannot* pass the tail check, you don't need a conservative 2-second stability window. Your existing byte-parsing validator makes this nearly free: you could even skip step 3 and just treat a parse failure as "retry", though checking explicitly gives you a cleaner error message.

Full function:

```js
async function readWhenComplete(abs) {
  const deadline = Date.now() + SETTLE_TIMEOUT_MS;
  let prev = null, stable = 0;
  for (;;) {
    let st;
    try { st = await fsp.stat(abs, { bigint: true }); }
    catch (e) { if (e.code === 'ENOENT') return { gone: true }; throw e; }

    const sig = `${st.size}:${st.mtimeNs}:${st.ino}`;
    if (sig === prev) stable++; else { stable = 0; prev = sig; }

    if (stable >= SETTLE_STABLE_N) {
      const fh = await fsp.open(abs, 'r');
      try {
        const a   = await fh.stat({ bigint: true });
        const buf = await fh.readFile();
        const b   = await fh.stat({ bigint: true });
        const untouched = a.size === b.size && a.mtimeNs === b.mtimeNs
                       && BigInt(buf.length) === a.size;
        if (untouched && isCompletePng(buf)) return { buf };
      } finally { await fh.close(); }
      stable = 0; prev = null;            // raced or truncated — go around
    }
    if (Date.now() > deadline) return { timedOut: true };
    await sleep(SETTLE_POLL_MS);
  }
}
```

# (f) ANSI board vs notifications

**The pinned terminal board is the primary UI. Notifications are a strictly optional FAIL-only secondary.** Four reasons, all of them about your actual loop:

1. **Notifications are unreliable by construction** — see above. A save-validate loop that can silently stop telling you things is worse than no loop.
2. **They hold ~200 characters and vanish.** "stale RGB under transparency at 12 pixels" plus which pixels does not fit in a banner. Your validator produces exactly the kind of detail a banner destroys.
3. **You are already looking at the screen.** Aseprite and the terminal share a monitor. A banner is for when you're away; you are 30 cm from the answer.
4. **State, not events.** With 20 slots, what you want after ⌘S is not "one thing changed" but "which of my 20 are green right now, and what's still unassigned". A board shows a standing answer; a notification shows a transient one.

Node gives you the redraw with zero deps via [`node:readline`](https://nodejs.org/docs/latest/api/readline.html) — `readline.cursorTo(stream, 0, 0)` and `readline.clearScreenDown(stream)`. Guard on `process.stdout.isTTY` so piping to a log still works.

I deliberately did **not** use the xterm alternate screen buffer (`\x1b[?1049h`). It hides your scrollback while running and wipes the final frame on exit. Plain redraw-at-origin leaves the last board on screen after Ctrl-C, which is what you want when you close the laptop mid-session.

```js
#!/usr/bin/env node
// tools/watch-art.mjs  --  zero dependencies, macOS-tuned.
//
// Design notes (each one is load-bearing):
//  * We watch the DIRECTORY, never the file. A per-file fs.watch dies silently
//    the moment anything replaces the file via rename (Node "Inodes" caveat).
//  * We ignore `eventType` entirely. On macOS a directory watch is FSEvents and
//    reports plain in-place writes as 'rename'. The string is noise.
//  * Every event is a *hint that something might have changed*, nothing more.
//    Truth comes from stat + content, never from the event.

import fs from 'node:fs';
import fsp from 'node:fs/promises';
import path from 'node:path';
import crypto from 'node:crypto';
import readline from 'node:readline';
import { execFile, execFileSync } from 'node:child_process';

// ---------------------------------------------------------------- config ----
const ROOT       = path.resolve(process.argv[2] ?? 'art');
const NOTIFY     = process.argv.includes('--notify');
const AUTOCOMMIT = process.argv.includes('--commit');
const VALIDATOR  = process.env.ART_VALIDATOR ?? 'tools/validate.mjs';

const DEBOUNCE_MS       = 120;   // collapse the event burst from one save
const SETTLE_POLL_MS    = 40;    // how often we re-stat while waiting for quiet
const SETTLE_STABLE_N   = 2;     // consecutive identical stats == quiet
const SETTLE_TIMEOUT_MS = 5000;  // give up rather than hang forever
const WATCH_EXT = new Set(['.png']);
const IGNORE_RE = /(^|\/)(\.git|node_modules|\.DS_Store|\._[^/]*|[^/]*\.tmp|[^/]*~)(\/|$)/;

const PNG_SIG  = Buffer.from([0x89,0x50,0x4e,0x47,0x0d,0x0a,0x1a,0x0a]);
const PNG_IEND = Buffer.from([0x00,0x00,0x00,0x00,0x49,0x45,0x4e,0x44,0xae,0x42,0x60,0x82]);

const sleep = ms => new Promise(r => setTimeout(r, ms));

// ------------------------------------------------- is the file done yet? ----
function isCompletePng(buf) {
  return buf.length >= PNG_SIG.length + PNG_IEND.length
      && buf.subarray(0, 8).equals(PNG_SIG)
      && buf.subarray(buf.length - 12).equals(PNG_IEND);
}

// Returns {buf} | {gone:true} | {timedOut:true}
async function readWhenComplete(abs) {
  const deadline = Date.now() + SETTLE_TIMEOUT_MS;
  let prev = null, stable = 0;
  for (;;) {
    let st;
    try { st = await fsp.stat(abs, { bigint: true }); }
    catch (e) { if (e.code === 'ENOENT') return { gone: true }; throw e; }

    const sig = `${st.size}:${st.mtimeNs}:${st.ino}`;
    if (sig === prev) stable++; else { stable = 0; prev = sig; }

    if (stable >= SETTLE_STABLE_N) {
      const fh = await fsp.open(abs, 'r');
      try {
        const a   = await fh.stat({ bigint: true });
        const buf = await fh.readFile();
        const b   = await fh.stat({ bigint: true });
        const untouched = a.size === b.size && a.mtimeNs === b.mtimeNs
                       && BigInt(buf.length) === a.size;
        if (untouched && isCompletePng(buf)) return { buf };
      } finally { await fh.close(); }
      stable = 0; prev = null;              // raced or truncated -- go around
    }
    if (Date.now() > deadline) return { timedOut: true };
    await sleep(SETTLE_POLL_MS);
  }
}

// ------------------------------------------------------------- pipeline ----
const timers   = new Map();  // rel -> Timeout   (debounce)
const inflight = new Map();  // rel -> Promise   (never two runs for one file)
const lastHash = new Map();  // rel -> sha1      (kills duplicate events)
const board    = new Map();  // rel -> {state,msg,at}
const logLines = [];

function touch(rel) {
  clearTimeout(timers.get(rel));
  timers.set(rel, setTimeout(() => { timers.delete(rel); enqueue(rel); }, DEBOUNCE_MS));
}

function enqueue(rel) {
  const prior = inflight.get(rel) ?? Promise.resolve();
  const next = prior.then(() => process_(rel)).catch(e => log(`ERR ${rel}: ${e.message}`));
  inflight.set(rel, next);
  next.finally(() => { if (inflight.get(rel) === next) inflight.delete(rel); });
}

async function process_(rel) {
  const abs = path.join(ROOT, rel);
  const r = await readWhenComplete(abs);

  if (r.gone)     { board.delete(rel); lastHash.delete(rel); render(); return; }
  if (r.timedOut) { setState(rel, 'WAIT', 'never settled / not a complete PNG'); return; }

  const hash = crypto.createHash('sha1').update(r.buf).digest('hex');
  if (lastHash.get(rel) === hash) return;   // duplicate event, or metadata-only touch
  lastHash.set(rel, hash);

  setState(rel, 'RUN', '');
  const t0 = Date.now();
  const { code, out } = await runValidator(abs);
  const ms = Date.now() - t0;

  if (code === 0) {
    setState(rel, 'PASS', `${r.buf.length}B  ${ms}ms`);
    log(`PASS ${rel}`);
    if (AUTOCOMMIT) commit(abs, rel);
  } else {
    const why = firstLine(out) || `validator exit ${code}`;
    setState(rel, 'FAIL', why);
    log(`FAIL ${rel}  ${why}`);
    if (NOTIFY) notify(rel, why);
  }
}

const firstLine = s => (s || '').split('\n').find(l => l.trim()) ?? '';

function runValidator(abs) {
  return new Promise(res => {
    execFile(process.execPath, [VALIDATOR, abs], { timeout: 30_000 },
      (err, stdout, stderr) => res({ code: err?.code ?? 0, out: `${stdout}${stderr}`.trim() }));
  });
}

function commit(abs, rel) {
  try {
    execFileSync('git', ['add', '--', abs], { cwd: ROOT, stdio: 'ignore' });
    execFileSync('git', ['commit', '-m', `art: ${rel}`, '--', abs], { cwd: ROOT, stdio: 'ignore' });
    log(`  committed ${rel}`);
  } catch { log(`  (nothing to commit for ${rel})`); }
}

// argv form: the filename NEVER becomes AppleScript source, so a sprite called
// `boss".png` cannot inject script. Exit code 0 does NOT prove it was shown --
// macOS drops it silently if your terminal lacks Notifications permission.
function notify(title, body) {
  execFile('osascript',
    ['-e','on run argv',
     '-e','display notification (item 1 of argv) with title (item 2 of argv)',
     '-e','end run',
     '--', body.slice(0, 200), `FAIL  ${title}`],
    () => {});
}

// ----------------------------------------------------------------- view ----
const C = { r:'\x1b[31m', g:'\x1b[32m', y:'\x1b[33m', d:'\x1b[2m', b:'\x1b[1m', x:'\x1b[0m' };
const BADGE = { PASS:`${C.g}✓ PASS${C.x}`, FAIL:`${C.r}✗ FAIL${C.x}`,
                RUN:`${C.y}… RUN ${C.x}`, WAIT:`${C.y}… WAIT${C.x}` };

function setState(rel, state, msg) { board.set(rel, { state, msg, at: Date.now() }); render(); }

function log(line) {
  const stamped = `${new Date().toTimeString().slice(0, 8)}  ${line}`;
  if (!process.stdout.isTTY) { process.stdout.write(stamped + '\n'); return; }
  logLines.push(stamped);
  while (logLines.length > 8) logLines.shift();
  render();
}

let pending = false;
function render() {                     // coalesce redraws to one per tick
  if (pending) return; pending = true;
  setImmediate(() => { pending = false; draw(); });
}

function draw() {
  const out = process.stdout;
  if (!out.isTTY) return;
  readline.cursorTo(out, 0, 0);
  readline.clearScreenDown(out);
  const fails = [...board.values()].filter(v => v.state === 'FAIL').length;
  out.write(`${C.b}art watch${C.x} ${C.d}${ROOT}${C.x}   ` +
            `${board.size} tracked   ${fails ? C.r : C.g}${fails} failing${C.x}\n\n`);
  for (const rel of [...board.keys()].sort()) {
    const v = board.get(rel);
    out.write(`  ${BADGE[v.state]}  ${rel.padEnd(38)} ${C.d}${v.msg}${C.x}\n`);
  }
  out.write(`\n${C.d}${'─'.repeat(60)}${C.x}\n`);
  for (const l of logLines) out.write(`${C.d}${l}${C.x}\n`);
  out.write(`\n${C.d}ctrl-c to stop${C.x}`);
}

// ---------------------------------------------------------------- driver ----
async function scan(dir = ROOT) {        // full pass: primes lastHash AND shows status
  for (const e of await fsp.readdir(dir, { withFileTypes: true })) {
    const abs = path.join(dir, e.name);
    const rel = path.relative(ROOT, abs);
    if (IGNORE_RE.test('/' + rel)) continue;
    if (e.isDirectory()) await scan(abs);
    else if (WATCH_EXT.has(path.extname(e.name).toLowerCase())) await process_(rel);
  }
}

let watcher = null;
function startWatch() {
  watcher = fs.watch(ROOT, { recursive: true, persistent: true }, (_eventType, filename) => {
    // _eventType is deliberately unused: on macOS FSEvents reports in-place
    // writes as 'rename'. filename can be null on some platforms/events.
    if (!filename) { scan().catch(() => {}); return; }
    const rel = filename.toString();
    if (IGNORE_RE.test('/' + rel)) return;
    if (!WATCH_EXT.has(path.extname(rel).toLowerCase())) return;
    touch(rel);
  });
  watcher.on('error', async (e) => {          // FSEvents can drop; self-heal
    log(`watcher error: ${e.message} -- restarting`);
    try { watcher.close(); } catch {}
    await sleep(500); startWatch(); scan().catch(() => {});
  });
}

process.on('SIGINT', () => { process.stdout.write('\x1b[?25h\n'); process.exit(0); });

if (!fs.existsSync(ROOT)) { console.error(`no such directory: ${ROOT}`); process.exit(1); }
process.stdout.write('\x1b[2J\x1b[?25l');     // clear, hide cursor
startWatch();
await scan();
draw();
```

## Corrections

**1. The FSEvents "~50 ms of OS-level coalescing before Node sees anything" claim is inverted.**
The flag values and line numbers are right (`latency = 0.05` at `src/unix/fsevents.c:340`, `flags = kFSEventStreamCreateFlagNoDefer | kFSEventStreamCreateFlagFileEvents` at `:354`, both verified in the fetched v1.x source). But `NoDefer` reverses the meaning of `latency`. Apple's own header, `/Library/Developer/CommandLineTools/SDKs/MacOSX15.4.sdk/System/Library/Frameworks/CoreServices.framework/Versions/A/Frameworks/FSEvents.framework/Versions/A/Headers/FSEvents.h:222`:

> "Affects the meaning of the latency parameter. If you specify this flag and more than latency seconds have elapsed since the last event, your app will receive the event immediately."

Measured on this machine: first DIR event landed 12 ms and 14 ms after the write in two independent runs (`probe/p1.mjs`, `probe/p2.mjs`), not ~50 ms. The 50 ms window coalesces *subsequent* events in a burst only. This does not change the design, but it removes one of the two stated justifications for `DEBOUNCE_MS = 120`.

**2. The stated root cause of "duplicates" is falsified by the briefing's own numbers and by direct test.**
Briefing: "One 3-chunk write produced 3 FILE events and 2 DIR events. Root cause is that a write raises `NOTE_EXTEND` and `NOTE_WRITE` separately, and libuv re-arms `EV_ONESHOT` after each." Three writes producing three events is 1:1, not duplication. And in `probe/p6.mjs` a single `appendFileSync` produced exactly one `'change'`, and a single same-length `r+` write produced exactly one `'rename'`. If the two note flags arrived as separate kevents you would see six events for three chunks. They arrive coalesced in one kevent. The observed pattern is one event per `write(2)`, plus FSEvents *under*-reporting on the directory side (2 for 3), which is the opposite of duplication.

**3. Three GitHub issues are mis-characterized (verified via the GitHub API).**
- `nodejs/node#3042` "fs.watch has double change events for file writes": **closed** 2015-12-30, `state_reason: completed`. Calling it "long-standing and won't-fix" is unsupported; it is not open.
- `nodejs/node#21902` "fs.watch trigger many times": closed 2 hours after filing, one comment, labeled **`invalid`**. Citing it as evidence of a Node defect is misleading.
- `nodejs/node#49916`: this is the one actually closed `state_reason: not_planned`. The "won't-fix" framing belongs here, not on the other two.

**4. The `throwIfNoEntry` "docs/reality mismatch" is not a mismatch.**
`doc/api/fs.md` on `nodejs/node@main` lists the change as added in **v26.1.0 and v24.16.0** (PR 61870). v25.6.1 sits between those two release lines and never received the backport, so documented behavior and observed behavior agree. I reproduced the throw (`probe/p3.mjs`: `ENOENT: no such file or directory, watch '/definitely/not/here'`), but there is no Node bug to flag here, only a version line that predates the feature. The briefing also cites only v24.16.0 and omits v26.1.0.

**5. The osascript permission mechanism is wrong.**
Briefing: "Permission attaches to the *calling* process, so iTerm2, Ghostty, Warp and Terminal.app each need their own grant." `display notification` run through `osascript` is attributed to **Script Editor** (`com.apple.ScriptEditor2`), which is the identifier that appears in System Settings > Notifications (MacScripter and swissmacuser both report this; Apple's own forum thread 808496 shows a user checking Script Editor and iTerm2 as separate entries). On this machine the picture is worse than a permission gate: after firing a probe notification that exited 0, `~/Library/Preferences/com.apple.ncprefs.plist` still holds 90 bundle-ids, **none** matching script/osa/term/iterm/ghostty/warp, and its mtime is still Apr 2. That is consistent with the notification never registering at all, matching the Apple forum report that osascript notifications silently stopped working on recent macOS. The conclusion ("unreliable, secondary channel only") survives; the explanation does not.

**6. Real defect in the shipped script: a validator timeout is reported as PASS.**
`/private/tmp/claude-501/-Users-juntaoli-todoFarm/50c2ffe9-f0e4-41c1-9520-3a40996e0cb8/scratchpad/out/watch-art.mjs`, in `runValidator`:

```js
(err, stdout, stderr) => res({ code: err?.code ?? 0, out: `${stdout}${stderr}`.trim() })
```

Measured (`probe/p5.mjs`): on the 30 s `timeout`, `execFile` yields `{ code: null, killed: true, signal: 'SIGTERM' }`. `null ?? 0` evaluates to `0`, so `process_` takes the `code === 0` branch, prints PASS, and under `--commit` commits the file. A validator that hangs on a pathological PNG is exactly the case where you least want an auto-commit. Fix by treating `err.killed || err.signal` as failure, or `err ? (err.code ?? 1) : 0`.

**7. "A PNG is complete iff it starts with the signature and ends with the IEND chunk" overstates the "iff".**
§11.2.4 requires IEND last, but the spec does not forbid trailing bytes, and some tools append them. For the only case Aseprite actually produces (truncate then grow) the check is sound. For anything else, a valid PNG with a trailing byte never satisfies `readWhenComplete`, loops for 5 s, and surfaces as `WAIT never settled / not a complete PNG`. Same path swallows genuinely corrupt saves: the artist gets "never settled" instead of the byte-parsing validator's real error message, which is the diagnostic he actually wants.

**8. "Truncates-then-grows in place. Your watcher will see the file at size 0 and at every intermediate size" is overstated.**
`png_format.cpp:732` is `png_write_rows(png, &row_pointer, 1)` per row with `fop->setProgress` per row (verified), but those rows go into a stdio `FILE*`. What reaches the filesystem is buffer flushes, not rows. A small pixel art PNG will typically flush once at `fclose`. The 0-byte window after `fopen(..., "wb")` is real and is the actual hazard; "every intermediate size" is not.

## Omissions

**1. Aseprite can push. The briefing never considers it.** Everything below is from official docs, no invented names. CLI (https://www.aseprite.org/docs/cli/): `--batch`/`-b`, `--save-as`, `--sheet`, `--sheet-type`, `--data`, `--format json-array`, `--split-tags`, `--list-tags`, `--filename-format`, `--script`, `--script-param key=value`, `--shell`. In-GUI scripting (https://github.com/aseprite/api): `app.events:on('aftercommand', function(ev) ... end)` with `ev.name` and `ev.params` (note the colon, `Events:on`, not `.on`), `sprite.events:on('change'|'filenamechange', ...)`, `app.params` fed by `--script-param`, `app.fs`, and `File > Scripts > Open Scripts Folder` as the install location. A script there can export the PNG at the exact canvas size and shell out on save, which deletes the entire truncated-read race class rather than defending against it.

**2. The "what do I draw next and at what size" half of the goal is unaddressed.** `Sprite(width, height[, colorMode])` and `Sprite(spec)` are documented constructors. With 20 slot JSONs and 9 art classes already carrying exact canvas sizes, a `--script` that opens the next unfilled slot at the right size is the obvious lever. The briefing gives this one sentence as "the natural extension" and never wires slots or classes into the watcher at all, so the shipped board tracks only files that already exist.

**3. A git pre-commit hook is the zero-daemon, zero-race gate, and is never mentioned.** He commits directly to a repo he owns. A hook running the existing validator over staged PNGs cannot read a half-written file, cannot miss an event, and needs no process running. The watcher gives latency; the hook gives the guarantee. They are complementary, and the briefing argues only for one.

**4. The manifest generator is never re-run.** The repo has one. On PASS it should regenerate, or the manifest drifts from the committed art.

**5. `fsPromises.watch()` and the `ignore` option.** The briefing verifies `ignore` works on v25.6.1 (I independently confirmed: control run saw `["b.tmp","c.png"]`, with `ignore: /\.tmp$/` saw `["c.png"]`, and `ignore: ['**/*.tmp']` behaved identically), then does not use it. Deliberate and defensible, but the docs on main now specify string globs via minimatch, RegExp, function, or array, which would replace `IGNORE_RE` outright. Also worth knowing: `fs.watch` silently accepts unknown options, so a typo in an option name fails open rather than throwing.

**6. Nothing watches `.aseprite` sources.** `WATCH_EXT` is `.png` only, so an edited but unexported sprite is invisible and the board keeps showing a stale PASS. That is the most likely way this loop lies to him.

**7. `--commit` is unguarded.** No branch check, no note on binary art versus LFS, one commit per file, and `execFileSync(..., {stdio:'ignore'})` inside a bare `catch` reports "(nothing to commit)" for *any* git failure, including a rejected hook or a detached HEAD.

**8. Zero-dependency cues that actually work.** BEL (`\x07`) and the terminal title escape (`\x1b]0;FAIL slot\x07`) need no permission grant and no `.app` bundle, and given the ncprefs finding above they are more likely to reach him than the notification is.

## Net assessment

Largely accurate, and unusually so on exactly the parts that are easiest to fake. No invented CLI flags, no invented Node APIs, no invented Lua. Every citation I checked is real and quoted correctly, line numbers included: `libuv/src/unix/kqueue.c:509-512` and `uv_fs_event_start` verbatim, `fsevents.c:340/354`, `aseprite/src/app/file/png_format.cpp:494`, `ase_format.cpp:230`, `laf/base/file_handle.cpp` `close_file_and_sync`, Node's Availability and Inodes paragraphs word for word, `fs.watchFile` `interval` default 5007, the v19.1.0 recursive history entry, `osascript(1)`'s argv sentence, PNG §5.2 and §11.2.4 with the correct 12 IEND bytes, chokidar's `awaitWriteFinish` 2000/100 and its "events are not reported twice" line.

I independently reproduced all three load-bearing macOS behaviors: a recursive directory watch reports `'rename'` for every event including in-place writes to a file that has been idle for four seconds; the per-file watcher goes permanently silent after a temp-plus-rename; a pure `utimesSync` fires a directory event. I also confirmed the mechanism the briefing infers from `kqueue.c:509`: a same-length `r+` write gives `'rename'`, an append gives `'change'`, a chmod gives `'change'`. And `mtimeNs` really does carry sub-microsecond resolution on this APFS volume, so the settle signature is sound.

The design conclusion stands unchanged: watch the directory, ignore `eventType`, debounce then stat-settle then check the IEND trailer, hash-dedupe, board over notifications. What is wrong is rhetorical inflation at the edges (the NoDefer inversion, an unsupported root cause for "duplicates", three mis-labeled issues, a version line gap sold as a docs bug), plus one real code defect where a validator timeout is silently promoted to PASS and auto-committed. The larger gap is scope rather than accuracy: it solves "detect the save without a race" thoroughly, and leaves the other half of the stated goal, "zero confusion about what to draw or what size", as a single aside, while never noticing that Aseprite has a documented scripting and CLI surface that could push the event instead of being polled for it.
