> Generated by a multi-agent research workflow on 2026-09-04.
> Five load-bearing mechanics verified against GitHub's own docs, then assembled into one brief.
> This caught a real bug in the shipped pipeline: a committed manifest deadlocked CI on every submission.

# Implementation Brief: Workshop → Assets → Game

## The stack

| Moving part | Technology | Why |
|---|---|---|
| Workshop frontend | Static SPA served from a Worker asset binding | Static asset requests are free and unlimited on Cloudflare, so only real API calls draw down the quota ([billing and limitations](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/)) |
| Workshop API | Same Cloudflare Worker, `/api/*` routes | One deployable, one secret store, no split between a Pages Functions runtime and a Worker ([migrate from Pages](https://developers.cloudflare.com/workers/static-assets/migration-guides/migrate-from-pages/)) |
| Hosting free tier | Cloudflare Workers, 100,000 req/day | Netlify Free charges 15 credits per production deploy out of 300/month and *pauses the site* at zero ([credits](https://docs.netlify.com/manage/accounts-and-billing/billing/billing-for-credit-based-plans/how-credits-work/)); Vercel Hobby cannot connect to org-owned repos and is non-commercial only ([limits](https://vercel.com/docs/limits), [fair use](https://vercel.com/docs/limits/fair-use-guidelines)) |
| Write credential | GitHub App installation access token | Fine-grained per-repo permissions and a 1 hour lifetime, versus an OAuth App's `public_repo` scope which grants write across *all* public repos the token holder can reach ([differences](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/differences-between-github-apps-and-oauth-apps), [OAuth scopes](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps)) |
| Artist sign-in | The *same* GitHub App, user authorization flow | "A token cannot grant additional access capabilities to a user", so an artist token structurally cannot write to `assets` ([on behalf of a user](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-with-a-github-app-on-behalf-of-a-user)) |
| JWT signing | `crypto.subtle`, RSASSA-PKCS1-v1_5, SHA-256 | Documented supported on Workers for `sign`/`importKey`; GitHub requires RS256 ([Web Crypto](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/), [App JWT](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-json-web-token-jwt-for-a-github-app)) |
| Token + session cache | Workers KV | 100,000 reads/day and 1,000 writes/day free, enough to cache one installation token per hour ([KV pricing](https://developers.cloudflare.com/kv/platform/pricing/)) |
| Commit mechanism | Git Data API: blob → tree → commit → ref | The Contents API writes one file per call and one commit per call, and concurrent writes are documented to conflict ("You must use these endpoints serially instead", [Contents API](https://docs.github.com/en/rest/repos/contents)) |
| Attribution | `Co-authored-by:` trailer plus `credits.json` in the repo | A custom `author` field forfeits the Verified badge on bot commits ([signature verification](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification)) |
| Assets CI | `pull_request` validate + `workflow_run` comment | On a fork PR, `permissions: write` is silently downgraded to read ([GITHUB_TOKEN reference](https://docs.github.com/en/actions/reference/github_token-reference)) |
| Atlas + manifest | Generated in the publish workflow on `main`, never committed | Removes the bot-push-to-protected-branch problem and the required-check deadlock entirely |
| Distribution | GitHub Release: `manifest.json` + `atlas-<tag>.tar.gz` | "There is no limit on the total size of a release, nor bandwidth usage" ([about releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)) |
| Browser-reachable copy | GitHub Pages, same `dist/` | Pages sends `access-control-allow-origin: *`; release assets send no CORS header at all |
| Game runtime | Phaser 4 `load.multiatlas` | Fewer source textures means fewer broken batches in the Phaser 4 render-node renderer ([Phaser 4 renderer](https://phaser.io/news/2026/04/phaser-4-renderer-faster-cleaner-and-built-for-modern-games)) |
| Desktop shell | Tauri v2, atlas as a bundled resource | `"bundle": { "resources": [...] }` ([Tauri resources](https://v2.tauri.app/develop/resources/)) |

## Auth and identity

**One GitHub App. Registered public, installed only on your org, scoped to the `assets` repository only.** Register it public because a private app "can only be installed on the user or organization account of the app owner" ([public or private](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/making-a-github-app-public-or-private)), and you want arbitrary artists to be able to authorize it. Public registration does not mean anyone can install it; installation and authorization are separate operations ("You can install a GitHub App without authorizing the app. Similarly, you can authorize the app without installing the app", [authorizing GitHub Apps](https://docs.github.com/en/apps/using-github-apps/authorizing-github-apps)).

**Permission set. Exactly this, no more:**

```yaml
permissions:
  contents: write        # blobs, trees, commits, refs
  pull_requests: write   # POST /repos/{owner}/{repo}/pulls
  metadata: read         # forced on, cannot be removed
default_events: []
```

`Metadata: read` cannot be disabled while any repository permission is set; GitHub overrides you ([choosing permissions](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app)). The endpoint-to-permission mapping is documented ([permissions required](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps)). Get this right on day one: adding a permission later prompts the org owner to re-approve, and the installation stays on the old permission set if they decline.

**Credentials and where each one lives:**

| Credential | Storage | Lifetime |
|---|---|---|
| App private key (PKCS#8) | Worker secret `GITHUB_APP_PRIVATE_KEY` (5 KB per-variable limit, [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)) | permanent, rotate manually |
| App client secret | Worker secret | permanent |
| App JWT | in-memory, per request | 9 minutes (GitHub ceiling is 10) |
| Installation token `ghs_` | Workers KV, ~50 min TTL | 1 hour ([generating an installation token](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app)) |
| Artist user token `ghu_` | KV, keyed by opaque session cookie, never sent to the browser | 8 hours |
| Artist refresh token `ghr_` | KV alongside it | 6 months, **rotates on every refresh** |
| Session cookie | HttpOnly, Secure, SameSite=Lax | 8 hours |

**Flow, artist opens the site to commit exists:**

1. Artist hits the SPA. No token, so the Worker returns the signed-out shell.
2. Click "Sign in with GitHub" → `https://github.com/login/oauth/authorize?client_id=...&redirect_uri=...&state=<csrf>&code_challenge=<S256>&code_challenge_method=S256`. Use PKCE; it is supported ([user access token](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app)).
3. Artist approves the *authorization* consent screen. This grants access to their GitHub account only. They are not installing anything and never see the `assets` repo.
4. Callback hits the Worker. Worker exchanges `code` + `code_verifier` + client secret at `POST https://github.com/login/oauth/access_token`, gets `ghu_` + `ghr_`, and `"scope": ""` because GitHub Apps do not use OAuth scopes.
5. Worker calls `GET /user` with the `ghu_` token, stores `id` (numeric, immutable), `login`, `avatar_url`. **Persist `id`, never key anything on `login`.** Usernames change and every attribution keyed on `login` rots.
6. Worker mints a session cookie. The `ghu_` token stays server-side forever.
7. On submit, the Worker mints an App JWT, exchanges it for an installation token scoped down per request, and does all git work with that token. The artist's `ghu_` token is never used for the write.

Down-scope the installation token on every mint. It costs nothing and bounds the blast radius of a bug in your own API:

```http
POST /app/installations/{INSTALLATION_ID}/access_tokens
Authorization: Bearer <app-jwt>

{ "repositories": ["assets"],
  "permissions": { "contents": "write", "pull_requests": "write" } }
```

**Attribution.** Do not set `author` or `committer`. Bot signature verification "will only work if the request is verified and authenticated as the GitHub App or bot and contains no custom author information, custom committer information, and no custom signature information" ([signature verification](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification)). Credit the artist with a trailer instead, which is ordinary message text and preserves the Verified badge:

```
add slot dragon-idle-01

Co-authored-by: Ada Pixel <1234567+adapixel@users.noreply.github.com>
```

Construct the noreply address from the numeric `id`, in the form `ID+USERNAME@users.noreply.github.com`, because the ID form survives username changes where the username form does not ([email addresses reference](https://docs.github.com/en/account-and-profile/reference/email-addresses-reference)).

**The trailer is decoration. `credits.json` is the record.** Write a `credits` entry in the same commit, keyed on your own `artist_id`, not on anything GitHub-shaped. Git trailers do not survive squash merges, history rewrites, or account deletion, and a trailer email that is on no GitHub account renders as plain text with no avatar and no contribution credit ([wrong user](https://docs.github.com/en/pull-requests/committing-changes-to-your-project/troubleshooting-commits/why-are-my-commits-linked-to-the-wrong-user)). Shipping GitHub sign-in only for v1 is the right call because it costs zero extra infrastructure and gives you fail-safe write isolation, but keep the credits schema provider-neutral so an email magic-link path can be added without a data migration.

## The submission path

Client-side validation is **UX only**. Everything is re-checked server-side, and again in CI. Assume the client validator does not exist.

**0. Client (browser).** Decode the PNG into a canvas, check dimensions against the slot spec, check the byte size, render a preview against the slot's neighbours. Fast feedback, no trust.

**1. `POST /api/submit`** to the Worker, multipart or JSON with a base64 `png` field plus `slot_id`. A 64x64 RGBA PNG is 16,521 bytes as pure noise and 158 bytes flat, so 22 KB base64 worst case. Cloudflare's request body limit is 100 MB on Free ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/)); body size is not a design input here.

**2. Worker: session check.** No valid session cookie → `401`, client redirects to sign-in.

**3. Worker: structural PNG validation.** Verify the 8-byte signature, parse IHDR (width, height, bit depth, colour type) from bytes 16 to 24, verify the IHDR CRC, and enforce a hard cap of **2 MB decoded**. Compare width/height/colour type against the slot spec JSON. Failure → `422` with a field-level error the SPA renders inline. This is cheap enough to stay well inside the 10 ms CPU budget; network wait on `fetch()` does not count toward it ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/)). Deep pixel-level checks (palette size, alpha coverage, bleed padding) belong in CI where CPU is unbounded.

**4. Worker: acquire a KV lock** on `submit-lock`, short TTL. All mutative GitHub work is serialized through it. GitHub's own guidance: "To avoid exceeding secondary rate limits, you should make requests serially instead of concurrently" and "If you are making a large number of POST, PATCH, PUT, or DELETE requests, wait at least one second between each request" ([best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)). Lock contention → `202` plus a poll URL, or a 503 with `Retry-After`.

**5. Worker: get or mint the installation token.** KV hit → use it. Miss or `401` → sign a fresh App JWT (`iat: now-60`, `exp: now+540`, `iss: <app id>`, RS256) and exchange it. Cache the result for 50 minutes. Do not mint per submission; there is a separate secondary limit of 2,000 OAuth access token requests per hour ([rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)).

**6. `GET /repos/ORG/assets/git/ref/heads/main`** → `object.sha` = `BASE_COMMIT`.

**7. `GET /repos/ORG/assets/git/commits/{BASE_COMMIT}`** → `tree.sha` = `BASE_TREE`.

**8. `POST /repos/ORG/assets/git/blobs`** with `{"content": "<base64>", "encoding": "base64"}`. **`encoding` defaults to `utf-8`** ([Git blobs](https://docs.github.com/en/rest/git/blobs)); omitting it silently corrupts every PNG you upload.

**9. `POST /repos/ORG/assets/git/trees`** with `base_tree: BASE_TREE` and three entries: the PNG (`mode: "100644"`, `type: "blob"`, `sha` from step 8), the slot metadata JSON (inline `content`, UTF-8 is fine for text), and the updated `credits.json`. **`base_tree` is mandatory in practice.** Without it, "all files which were a part of the parent commit's tree and were not defined in the `tree` parameter will be listed as deleted by the new commit" ([Create a tree](https://docs.github.com/en/rest/git/trees)). Omitting it wipes the repository in one commit. Also note you cannot pass both `sha` and `content` on the same entry.

**10. `POST /repos/ORG/assets/git/commits`** with `tree`, `parents: [BASE_COMMIT]`, and a message carrying the `Co-authored-by:` trailer. Omitting `parents` creates an orphan root commit ([Create a commit](https://docs.github.com/en/rest/git/commits)).

**11. `POST /repos/ORG/assets/git/refs`** with `{"ref": "refs/heads/submit/<slot>-<nonce>", "sha": "<new commit>"}`. Fully qualified only: "If it doesn't start with 'refs' and have at least two slashes, it will be rejected" ([Git refs](https://docs.github.com/en/rest/git/refs)). Creating the ref directly at the new commit saves a `PATCH` round trip. If you ever do `PATCH` an existing ref, keep `force: false`, which is your optimistic-concurrency guard.

**12. `POST /repos/ORG/assets/pulls`** with `head`, `base: main`, and a body naming the slot and the artist. This endpoint carries its own warning: "This endpoint triggers notifications. Creating content too quickly using this endpoint may result in secondary rate limiting."

**13. Release the lock. Return `201` with the PR URL.** The SPA polls the PR's check status and shows the CI validation comment inline.

**Failure handling per class:**

| Failure | Response |
|---|---|
| Bad session | `401`, re-auth |
| PNG fails structural check | `422` with field errors, no GitHub calls made |
| Installation token `401` | Purge KV, mint once, retry once, then `503` |
| `403`/`429` with `Retry-After` | Honour it exactly; "you should not retry your request until after that many seconds has elapsed" ([best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)). Return `503` with the same header |
| Ref already exists (`422`) | Regenerate the nonce, retry once |
| Ref update not fast-forward | Re-read `BASE_COMMIT` from step 6, rebuild the tree, retry once |
| Partial failure after blob/tree/commit | Nothing is referenced by any ref, so it is garbage. Do not attempt cleanup |
| CI fails on the PR | Artist sees the bot comment on the PR and in the SPA, fixes, resubmits. Resubmit reuses the same branch via `PATCH` with `force: false` |

**Capacity.** Five mutative calls per submission against the documented secondary limit of "no more than 80 content-generating requests per minute and no more than 500 content-generating requests per hour" gives roughly **100 submissions per hour**, long before the 5,000/hour primary installation budget matters ([rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)). A separate documented guidance caps you further: "Push rate: The recommended maximum limit is 6 pushes per minute" ([repository limits](https://docs.github.com/en/repositories/creating-and-managing-repositories/repository-limits)). If a rush ever materializes, batch multiple pending submissions into one tree and one commit, which the Git Data API makes trivial and the Contents API makes impossible.

## CI in the assets repo

**Two workflows, split by privilege. Never `pull_request_target`.**

That pattern is not just risky now, it is broken. `actions/checkout` v7 refuses to fetch fork PR code under `pull_request_target` and `workflow_run`, with enforcement backported to all supported majors on **2026-07-20** ([changelog](https://github.blog/changelog/2026-06-18-safer-pull_request_target-defaults-for-github-actions-checkout/)). Separately, since **2025-12-08**, `pull_request_target` always takes the workflow file and checkout commit from the default branch ([changelog](https://github.blog/changelog/2025-11-07-actions-pull_request_target-and-environment-branch-protections-changes/)). Any blog recipe that checks out the PR head under `pull_request_target` is dead. If you see `allow-unsafe-pr-checkout` in a diff, that is a security regression, not a fix.

**`validate.yml`, trigger `pull_request`, `permissions: contents: read`.** Checkout with `persist-credentials: false`, diff `base.sha..head.sha` for changed PNGs and slot JSON, run the full validator (Pillow: dimensions, colour depth, palette limits, bleed padding, filename-to-slot-spec match, `credits.json` schema). Mark the validator `continue-on-error: true`, render a Markdown report and the PR number into `out/`, `actions/upload-artifact@v7`, then fail the job explicitly. Without `continue-on-error` the artifact never uploads and the artist sees a red X with no reason.

**`report.yml`, trigger `workflow_run`, `permissions: pull-requests: write, actions: read`.** `actions/download-artifact@v8` with `run-id: ${{ github.event.workflow_run.id }}`, then upsert a marker comment on the PR. This is the only workflow that can write, because on a fork PR "the permissions are adjusted to change any write permissions to read only" unless the repo opts into sending write tokens to fork workflows, which you must not do ([GITHUB_TOKEN reference](https://docs.github.com/en/actions/reference/github_token-reference)). `workflow_run` "is able to access secrets and write tokens, even if the previous workflow was not" ([events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)).

**The artifact is attacker-controlled.** Parse it in JavaScript, coerce the PR number with `Number()` and reject non-positive integers, cap the body length, and never interpolate artifact content into a `run:` block. GitHub Security Lab is explicit that "Artifacts resulting from untrusted PR data are themselves untrusted and should be treated as such when handled in privileged contexts" ([preventing pwn requests](https://securitylab.github.com/resources/github-actions-preventing-pwn-requests/)). This is the live RCE path in this pattern.

**The required status check must be a fixed-name aggregator, not the path-filtered job.** When "A workflow is skipped by path filtering, branch filtering, or a commit message" its checks "stay in a 'Pending' state and block merging" ([troubleshooting required status checks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks)):

```yaml
gate:
  if: always()
  needs: [validate]
  runs-on: ubuntu-latest
  steps:
    - if: needs.validate.result == 'failure' || needs.validate.result == 'cancelled'
      run: exit 1
    - run: echo ok
```

Register only `gate`. `if: always()` is required or the gate is skipped when `validate` fails.

**Fork PRs are the secondary path, not the primary one.** The workshop bot has write access and pushes a same-repo branch, so its PRs are not fork PRs and never hit the first-time-contributor approval gate, which is scoped specifically to "fork pull request workflows" ([approving runs from forks](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/approve-runs-from-forks)). Set that setting to "Require approval for all external contributors" anyway, since the repo is public and drive-by fork PRs are possible.

**`publish.yml`, trigger `push` to `main`.** Validate everything, pack the atlas, generate `manifest.json`, cut a release tagged `assets-v<N>` with `manifest.json` and `atlas-assets-v<N>.tar.gz` attached, and deploy the same `dist/` to Pages.

**`manifest.json` and the atlas are build outputs, not source files. They are never committed to the repo.** This single decision deletes an entire class of problems: no bot push to a protected branch, so no need for a GitHub App in a ruleset bypass list; no `GITHUB_TOKEN` push that "will not create a new workflow run" ([GITHUB_TOKEN concepts](https://docs.github.com/en/actions/concepts/security/github_token)); no head-SHA-changed deadlock where a CI-pushed commit invalidates the checks that were about to let the PR merge; and no merge conflicts on `manifest.json` between two open submission PRs. The repo holds slot specs and PNGs. Everything derived lives in the release.

Set `concurrency: { group: pages, cancel-in-progress: false }` on the publish job so two merges landing together do not race. Custom Actions workflows also escape the documented soft limit of 10 Pages builds per hour ([Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)).

Pin: `actions/checkout@v7`, `actions/upload-artifact@v7`, `actions/download-artifact@v8`, `actions/upload-pages-artifact@v3`, `actions/deploy-pages@v4`.

## Serving art to the game

**The game build fetches exactly two files from a GitHub Release, pinned by tag.**

```bash
TAG=$(jq -r .assetsTag game.config.json)
curl -fsSL --proto '=https' --tlsv1.2 -o manifest.json \
  "https://github.com/ORG/assets/releases/download/${TAG}/manifest.json"
curl -fsSL --proto '=https' --tlsv1.2 -o atlas.tar.gz \
  "https://github.com/ORG/assets/releases/download/${TAG}/atlas-${TAG}.tar.gz"
sha256sum -c manifest.sha256
tar xzf atlas.tar.gz -C src/assets/
```

**The rate limit that forces this: 60 requests per hour per IP, unauthenticated.** GitHub's changelog states the unauthenticated limits "will apply to operations like cloning repositories over HTTPS, anonymously interacting with our REST APIs, and downloading files from raw.githubusercontent.com" ([changelog](https://github.blog/changelog/2025-05-08-updated-rate-limits-for-unauthenticated-requests/)), and the REST docs give the number: "The primary rate limit for unauthenticated requests is 60 requests per hour" ([rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)). This is worse than it sounds in CI, because GitHub-hosted runners "are hosted in Azure and subsequently have the same IP address ranges as the Azure datacenters" ([runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)), so your 60/hour bucket is shared with every other anonymous consumer on that egress IP. Fetching 300 PNGs anonymously from a runner is a coin flip. Worse, `raw.githubusercontent.com` returns **no `x-ratelimit-*` headers**, so you get no warning before you are throttled.

Two release-asset fetches sidesteps this entirely, and releases carry the strongest guarantee on the platform: "There is no limit on the total size of a release, nor bandwidth usage", with "Each file included in a release must be under 2 GiB" and up to 1000 assets per release ([about releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)).

**Pack the atlas. For a build-time fetch the threshold is 2 files**, because one archive is one request regardless of what is inside it. There is no file count at which N separate fetches wins. HTTP/2 does not make this free either; RFC 9113 only recommends `SETTINGS_MAX_CONCURRENT_STREAMS` "be no smaller than 100" ([RFC 9113](https://www.rfc-editor.org/rfc/rfc9113.html)), so hundreds of PNGs still serialize into waves. Cap each atlas page at **4096x4096** and use `load.multiatlas` beyond that; WebGL2 guarantees only 2048 as the `MAX_TEXTURE_SIZE` minimum and roughly half of devices exceed 4096 ([cross-platform issues](https://webgl2fundamentals.org/webgl/lessons/webgl-cross-platform-issues.html)). Query `gl.getParameter(gl.MAX_TEXTURE_SIZE)` rather than assuming. Ship full-screen backgrounds as standalone PNGs; they waste atlas area and force an extra page.

**Pages is the second output, for the browser only.** The workshop's slot preview and any web build of the game read from Pages, because Pages sends `access-control-allow-origin: *` while release assets send **no CORS header at all** and arrive as `content-disposition: attachment` behind a signed URL that expires in about an hour. Pages `cache-control` is fixed at `max-age=600` with no purge API, which is fine for a preview and irrelevant for a build-time fetch.

**Pin by tag, never by branch.** A branch-pinned build is not reproducible, and on any CDN in front of it you inherit stale-cache behaviour. jsDelivr is optional as a runtime mirror on `@assets-v<N>` tag URLs only, where `cache-control: public, max-age=31536000, immutable` applies; its branch URLs set `max-age=604800`, seven days in the visitor's browser, which no purge can clear ([jsDelivr](https://github.com/jsdelivr/jsdelivr)).

**Do not use Git LFS.** LFS is a client-side clean filter, and the REST and GraphQL write APIs create blob objects server-side without invoking a local git client, so an API-committed PNG into an LFS-tracked path lands as raw bytes where the repo expects a pointer ([git-lfs spec](https://github.com/git-lfs/git-lfs/blob/main/docs/spec.md)). Beyond that, "When you download a Git LFS file, the bandwidth you use is included in the repository owner's bandwidth usage", the free quota is 10 GiB, and exhausting it with a $0 budget means "Git LFS usage is blocked for the rest of the calendar month" ([LFS billing](https://docs.github.com/en/billing/concepts/product-billing/git-lfs)). That is your art pipeline dark until the first. Slot PNGs are kilobytes and nowhere near the 100 MiB block ([large files](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)).

## Public or private assets repo

**Recommendation: public.**

**What public buys you.** Release assets and Pages both work anonymously, so the game build needs no credential at all. jsDelivr and Statically become available as mirrors. Contributors can see the art library, browse open slots, and file issues without an invite. The workshop's preview path is a plain `<img src>` against Pages, with no proxy to write or maintain. And every credential in the system stays write-only, which is a much smaller surface to defend.

**What public costs you.** Every approved PNG is world-visible the moment its PR merges, and every open submission PR is world-visible before merge. If a character reveal is a marketing beat, that beat is spoiled by a merged PR. Draft-quality work an artist would rather nobody saw is permanently in history.

**If it must be private, the framing changes from "serve" to "authenticated fetch", and three things break.** Every CDN is out: jsDelivr has no credential mechanism in its URL scheme, and Statically states plainly "Only public repositories are supported" ([Statically](https://github.com/staticallyio/statically/blob/main/README.md)). Pages is out for anything confidential, because publishing a site *from* a private repo does not make the *site* private: "To publish a GitHub Pages site privately, your organization must use GitHub Enterprise Cloud" ([changing visibility](https://docs.github.com/en/pages/getting-started-with-github-pages/changing-the-visibility-of-your-github-pages-site)). And browser preview is out on `raw.githubusercontent.com`, because a browser cannot attach an `Authorization` header there; the CORS preflight returns 403.

The private-repo build then looks like this. Game CI checks out `assets` with a second GitHub App installation token, `sparse-checkout: dist/`, or pulls one authenticated tarball from `GET /repos/ORG/assets/tarball/assets-v42` against a 5,000/hour budget. `GITHUB_TOKEN` will not work, because it is scoped to the current repository only. Private releases still work via `GET /repos/{owner}/{repo}/releases/assets/{asset_id}` with `Accept: application/octet-stream`, and keep the no-bandwidth-limit property. Workshop previews go through a new Worker route that calls the Contents API with `Accept: application/vnd.github.raw` and streams the bytes back under your own origin. Never ship the installation token to the browser, even though `api.github.com` would accept it cross-origin.

**Take public.** The extra route, the extra App installation, and the loss of every CDN option are a real ongoing cost, and pre-launch secrecy is better solved by keeping unreleased *slot specs* out of the public repo until you are ready to open them, which needs no infrastructure at all.

## Sharp edges

**1. GitHub hands you a PKCS#1 private key. Web Crypto only accepts PKCS#8.** "the PEM file you download will be in `PKCS#1 RSAPrivateKey` format" ([managing private keys](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/managing-private-keys-for-github-apps)), and `universal-github-app-jwt` confirms "the WebCrypto API only supports `PKCS#8`" ([README](https://github.com/gr2m/universal-github-app-jwt)). The failure is an opaque `DataError` from `importKey` at request time in production with nothing pointing at the key format. Tell them apart by the first line: `-----BEGIN RSA PRIVATE KEY-----` is PKCS#1, `-----BEGIN PRIVATE KEY-----` is PKCS#8. Convert locally with `openssl pkcs8 -topk8 -inform PEM -outform PEM -nocrypt`, pipe the result into `wrangler secret put` to preserve newlines, then delete the file. **Never paste a GitHub App private key into a web-based converter**; that hands over commit access to the assets repo.

**2. `POST /git/trees` without `base_tree` deletes the entire repository in one commit.** Documented behaviour, not a bug ([Create a tree](https://docs.github.com/en/rest/git/trees)). Assert it is present before every call.

**3. `POST /git/blobs` defaults `encoding` to `utf-8`.** Every PNG you upload without an explicit `"encoding": "base64"` is silently corrupted ([Git blobs](https://docs.github.com/en/rest/git/blobs)).

**4. Setting a custom `author` silently forfeits the Verified badge.** Nobody discovers this until a branch protection rule requiring signed commits starts rejecting the bot's PRs. Use the `Co-authored-by:` trailer.

**5. `actions/checkout@v7` refuses fork PR checkout under `pull_request_target` and `workflow_run`, since 2026-07-20.** Most existing blog advice on commenting from CI is now wrong. Grep for `allow-unsafe-pr-checkout` in review and treat any occurrence as a security incident.

**6. A path-filtered job registered as a required status check blocks merges forever.** Its check sits Pending and never resolves. Use the fixed-name `gate` aggregator with `if: always()`.

**7. `workflow_run` workflows only run from the default branch, and their context has no PR number.** You cannot test changes to `report.yml` in a PR; expect to iterate on a scratch repo or merge blind. Pass the PR number through the artifact, and validate it as untrusted input.

**8. A bad token against `raw.githubusercontent.com` returns 404, not 401.** An expired bot credential is indistinguishable from a missing file. One more reason the read path does not go through raw.

**9. Directory width is capped at 3,000 entries.** With a PNG and a JSON per slot, a flat `art/` directory hits the wall at 1,500 slots ([repository limits](https://docs.github.com/en/repositories/creating-and-managing-repositories/repository-limits)). Shard as `art/<category>/<two-char-prefix>/slot-042.png` from day one, because changing the scheme later rewrites every manifest path.

**10. User access token expiration is on by default**, 8 hours for `ghu_` and 6 months for `ghr_`, and **each refresh returns a new refresh token**. Persist the new one or you break the chain and log every artist out ([refreshing tokens](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/refreshing-user-access-tokens)).

**11. Changing App permissions after installation requires the org owner to re-approve**, and the installation stays on the old permission set if they decline. Ship `contents: write` and `pull_requests: write` together on day one.

**12. Never route the write through the artist's `ghu_` token.** The permission-intersection rule makes it fail closed with a `403` at commit time rather than at design time, which is a debugging afternoon you do not need.

### Things I could not verify, flagged rather than asserted

- **No official GitHub docs page states a rate limit for `raw.githubusercontent.com` itself.** The 60/hour figure comes from the documented unauthenticated REST limit combined with the changelog sentence naming raw, and raw returns no rate-limit headers to measure against. The architecture above does not depend on the exact number, since it avoids raw entirely.
- **GitHub publishes no size limit for `PUT /contents` or `POST /git/blobs` writes.** The documented 1 MB / 100 MB figures are read-side. Community reports put the write cutoff between 10 MB and 50 MB. The 2 MB server-side cap keeps you permanently clear.
- **Whether `github-actions[bot]` can be selected as a ruleset bypass actor is undocumented either way.** Moot here, because CI never pushes to `main`.
- **The claim that the REST and GraphQL write APIs bypass the LFS clean filter is inferred from the git-lfs spec**, not from a GitHub docs statement. It is the reason not to adopt LFS, and it would be the first thing to smoke-test if anyone argues for it.
- **`actions/github-script` major version** was not re-verified; confirm before pinning.
